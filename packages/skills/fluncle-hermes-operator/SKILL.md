# Fluncle Hermes operator

Fluncle's Hermes box is a long-lived container on rave-02, built from a digest-pinned `oven/bun` Debian base plus the sweep toolchain; "Hermes" is only the name of the box, its container, its `hermes` user, and its image tag. Its main process (`tini` → `box-entrypoint`, a `sleep infinity`) does no work; it only keeps the container alive so the host systemd timers can `docker exec` the baked sweeps, which act on the archive through the authenticated `fluncle` CLI and the agent-scoped token. This skill is the operator's map for **changing** it: which lever to pull for a given change, the invariants not to break, and how a change actually reaches the running box.

The architecture, security model, and the **exact build / run / verify commands and secret locations** live in `docs/agents/hermes-agent.md` — that doc is the source of truth, and this skill routes to it rather than restating it. Read the doc's relevant section before you touch anything; come here for the decision and the guardrails. The build context (Dockerfile, the entrypoint, the sweeps, the timer units) is `docs/agents/hermes/`.

The authoring doctrine of individual sweeps (the note, observation, newsletter, and bio agents) lives in their own docs under `docs/agents/`; this skill covers the box they run on.

## The mental model: the repo is the truth, the box is a deploy target

Make every change **in the repo and commit it** — never hand-edit on the box as the canonical version. An on-box edit drifts from git and is erased the next time the box is redeployed or rebuilt; keeping the change in the repo is what makes the security-relevant bits (the role boundary, the sweeps, the pins) reviewable and a rebuilt box identical to the committed state.

From the repo, a change reaches the live box through **one of two deploy targets**, and picking the right one is most of the job:

- **The Worker** (`apps/web`) — _what the agent may do_. The operator/agent permission boundary is enforced **server-side**, not on the box. A push to `main` auto-deploys it. So "let the agent do X" or "stop the agent doing Y" is a code change to a route's role guard, reviewed in git.
- **The box** — _how the sweeps run_. The image (with its baked sweeps and skills), the host timers, and the secrets live on the devbox (reached over SSH on the tailnet; the address is in the operator's ops notes). The image self-deploys from `main` via pin-watch; timers install with `install-host-timers.sh`; secrets re-sync from 1Password.

## Invariants

- **Changes go through git.** The repo is canonical; the box mirrors it. This keeps the role boundary and the sweeps reviewable and reproducible, and means a rebuilt box matches the committed state. An ad-hoc box edit is a one-off the next deploy erases.
- **The permission boundary is server-side, full stop.** The box deliberately holds only a low-privilege `agent`-scoped token; the Worker refuses publish-/irreversible-class actions for that role. You never make the agent "more powerful" by editing the box — you change a Worker role guard, in git. (This is also why a leaked box token can't publish.)
- **Pin the image.** The base is pinned by tag + digest and every tool by version; never float `latest`. Same-major bun, `fluncle`, Claude Code, and yt-dlp bumps arrive as `hermes-pin-drift` PRs; majors and the manual-watch pins (node, uv, gh, boat.dev) are the operator's call.
- **Public repo: no host names, IPs, or secret values in committed files.** Those live in the operator's ops notes and the secret store. The committed docs and this skill stay at the architecture / procedure level — match that when you edit them.

## The change → ship → verify loop

1. **Edit in the repo** and commit; the relevant doc section names the exact file.
2. **Ship to the right target.** A Worker/role change deploys on push to `main`. An image change (a sweep, a skill, a pin, the base) bakes on merge and pin-watch rebuilds + swaps the container; the doc's § Run has the exact commands for a hand rebuild. A secret is re-populated from the secret store + restart, no rebuild.
3. **Verify.** Run the doc's § Verify smoke test (CLI present; an agent-allowed read returns `{ok:true}`; a publish-class command is refused with a 403). For a Worker role change, confirm the agent token now gets the new allow/deny against the deployed API.
4. **Quality checks for Worker changes.** Per `AGENTS.md`, run the `apps/web` typecheck / lint / build before pushing — a push to `main` is a production deploy.

## Crons (automation)

The box is Fluncle's automation runtime: trusted, no-untrusted-input loops over the `fluncle` CLI. These crons are **live on the box** — deterministic `--no-agent` sweeps (no agent loop, no model-call storms). Canonical source is the `.sh`/`.ts` pairs under `docs/agents/hermes/scripts/`. Every automation cron uses a repo-checked-in host systemd `.timer`/`.service` pair, making schedules reproducible across re-provisioning (docs/agents/hermes-agent.md § Crons). The sweep bakes to `/opt/hermes-scripts` (+ the enrichment DSP skill to `/opt/hermes-skills`) and auto-updates from `main` via pin-watch; the timer only triggers it. Nothing inside the container schedules anything; its main process only keeps it alive.

**Reset boundary:** a re-provision restores **code** (baked), **schedule** (the timers, via `docs/agents/hermes/install-host-timers.sh`), and **secrets** (`fluncle-secrets-sync`) — all three because they are derived from the repo, not accumulated on the box. The fourth layer, accumulated box state (cron-output history, the render conductor's `box-id` + poison ledger, the prober's memory, the hand-placed `0600` env files including the sweep secrets file), is captured by **leg 2** of the nightly `fluncle-backup`: AES-256-GCM-sealed to the private backup bucket under `box-state/`, 14-daily / 6-monthly, proven by `docs/agents/hermes/scripts/box-state-restore-drill.ts`. Leg 1 is the separate production-database dump. **Two things to know before you rely on it:** leg 2 uploads nothing without `FLUNCLE_BOXSTATE_KEY` and reports `ok: true` when it skips, and the bootstrap token plus the `op` templates live outside every backup — they are re-placed by hand from the private companion. Restore into a STOPPED container, so no sweep writes mid-restore; `tar` preserves the `0600` modes and that is load-bearing. **Putting a LOST box back is a different job from changing a live one** — the ordered rebuild, the rest of the ordering traps, and a read-only preflight for "could we restore right now?" are the [fluncle-box-restore](../fluncle-box-restore) skill.

- **The `--no-agent` sweep roster** is dozens of jobs and grows, so **no doc holds a roster table**. Read the roster from the timer directories, registry entries, and live `systemctl` output (§ The cron roster in [`docs/agents/hermes/cron/README.md`](../../../docs/agents/hermes/cron/README.md)): `ls -d docs/agents/hermes/*-timer` for what exists in the repo, the `cron.*` entries in `@fluncle/registry` for what each one does and at what cadence (the only copy whose drift build-fails, via the registry + healthcheck-coverage tests), and `systemctl list-timers 'fluncle-*'` for the live set + next-run times. Don't hardcode a count here or anywhere. All are `--no-agent`: a pure trigger ships deterministic stdout; a **hybrid** (an authoring sweep such as note, observation, or newsletter) wraps exactly **one** bounded `claude -p` authoring call (subscription auth, zero OpenRouter tokens) inside a deterministic gather/persist/deliver shell. All sit under the agent ceiling — reversible, internal, no public footprint — so scheduling them raises no authority an injection could abuse.
- **The weekly newsletter (`fluncle-newsletter`):** Friday 15:00 Amsterdam, author the edition with the inline voice canon, persist a draft via `fluncle admin newsletter draft` (admin tier — the box's agent token can draft). Two operator-visible extras the other sweeps don't have: (1) the timer declares `OnCalendar=Fri 15:00 Europe/Amsterdam`, so the slot follows CET/CEST independently of the host timezone; (2) the **send stays operator-gated** — the agent token 403s on `newsletter send`, so the sweep delivers a one-line **Discord summary + the exact `fluncle admin newsletter send <id>` command** for the operator to run. Nothing auto-sends; an un-sent draft is re-offered by the next Friday run. `RESEND_*` stays a Worker secret.
- **Mechanism (host systemd timers):** each cron is a `Type=oneshot` `.service` that `docker exec`s the baked sweep + a `.timer` (`OnBootSec` staggered, `OnUnitActiveSec` cadence, `Persistent=true`); the newsletter uses `OnCalendar`. Timers run in parallel. A `docker exec` sends stdout to journald, while the `fluncle-healthcheck` prober reads markers under `~/.hermes/cron/output/<job>/` — so each sweep SELF-WRITES its `/status` marker via the shared `cron-output.sh` helper.
- **Operating them:** smoke-test each command by hand on the box before enabling its timer (`sudo systemctl start fluncle-<job>.service`, then `journalctl -u fluncle-<job>.service`), and watch the first ticks + the marker under `/opt/data/cron/output/fluncle-<job>/`; the observation sweep spends Cartesia credits per render. Install all timers with `sudo bash docs/agents/hermes/install-host-timers.sh`.

### The render box (fluncle-render)

The video conductor is its own beast — a rave-02 host timer driving a scale-to-zero boat.dev render box (rave-03; renders on software GL, `FLUNCLE_GL=swangle`, no GPU). **The full pipeline doctrine is [`docs/agents/render-conductor.md`](../../../docs/agents/render-conductor.md)**: the state machine, the poison ledger + `FLUNCLE_RENDER_LOG_ID` coherence contract, the headless `claude -p` rails, the version trap, snapshot forensics, and the boat.dev CLI quirks. The two operator levers you reach for most:

- **Reap recovery** (a stale/wedged box — freshen silently failing on boat.dev `boat ssh` errors, `machine_not_running` loops, resumes that produce no render): recovery uses `boat stop <id>` followed by `boat extend <id> --ttl 60`. The conductor never deletes a sandbox, so the recovery does not either. Then clear the conductor's box-id state file, set the conductor state to `idle`, and trigger the render service. The conductor cold-provisions a fresh box that clones current `main` by construction. Exact box IDs + state-file path are the ops runbook in the private companion repo (`fluncle-labs`).
- **Re-render a shipped finding:** `fluncle admin tracks requeue-video <id|logId>` (operator tier) clears both `video_url` (the render-queue gate) and `video_squared_at` (radio eligibility), leaves the vehicle/grain ledger so the next render diversifies away, and `finalize_track_video` auto-purges the cached Cloudflare Media-Transformation renditions so the re-render replaces cleanly. The conductor picks it up on the next hourly idle tick.

### Adding or changing a cron — the fan-out checklist

A cron is a fan-out surface like any other (the `fluncle-surfaces` skill's shape, for a `cron` kind): one job touches the sweep, the timer, the bake, the freshness marker, the registry, `/status`, and the on-box prober. Miss one and the cron runs but is invisible (no `/status` row) — or shows a wrong next-fire. Everything is **in the repo** (canonical) and reaches the box by baking on merge to `main`; nothing is created on the box by hand. To add a new `fluncle-<job>` cron, touch all of these:

1. **The sweep** — write `docs/agents/hermes/scripts/<job>-sweep.{sh,ts}` (a thin bash entry the timer runs as `bash /opt/hermes-scripts/<job>-sweep.sh`, which runs the bun orchestrator). Model it on an existing sweep: `enrich-sweep` for a pure trigger; `note`/`observe`/`newsletter-sweep` for a **hybrid** wrapping exactly one bounded `claude -p` authoring call. If it needs creds, source the shared `0600 ${HOME}/.fluncle-secrets.env` (op-injected by `fluncle-secrets-sync`; the container env carries only the agent token and the alert webhook, so every other credential arrives via that file). Export `PATH` + pin `BUN_BIN`/`FLUNCLE_BIN` absolutely so the sweep never depends on its caller's environment.
2. **The freshness marker** — the sweep MUST self-write its `/status` marker via the shared [`cron-output.sh`](../../../docs/agents/hermes/scripts/cron-output.sh) helper (a `# Cron Job: fluncle-<job>` header + a JSON summary as the **last line**, `ok !== false` = healthy) to `~/.hermes/cron/output/fluncle-<job>/<ts>.md` (= `/opt/data/cron/output/fluncle-<job>/`). A `docker exec` sends stdout to journald, not to that dir, so without this the `/status` row is permanently "no data". (The `fluncle-healthcheck` prober is the ONE cron that writes none — a self-read would be circular.)
3. **The bake** — nothing to do: the `Dockerfile` copies `docs/agents/hermes/scripts/` to `/opt/hermes-scripts/`, so a new file in that dir bakes automatically (the `RUN rm -f` right after strips `*.test.ts` + the un-deployed `clip-drip-sweep.sh` — add to that filter only if the file must NOT ship).
4. **The timer** — add `docs/agents/hermes/<job>-timer/` with a `.service` (`Type=oneshot`, `ExecStart=docker exec -u hermes … bash /opt/hermes-scripts/<job>-sweep.sh`), a `.timer`, and a `README.md`. For a pure cadence use `OnBootSec` (staggered) + `OnUnitActiveSec` + `Persistent=true`. For a **fixed wall-clock** slot use `OnCalendar=*-*-* HH:MM:SS Europe/Amsterdam` — **the host clock is UTC**, so a wall-clock cron MUST carry the explicit `Europe/Amsterdam` TZ suffix (systemd ≥252; check with `systemctl --version`) or it fires at the wrong hour. Register the unit in [`install-host-timers.sh`](../../../docs/agents/hermes/install-host-timers.sh).
5. **The registry surface** — add a `cron.<job>` entry to `@fluncle/registry` ([`packages/registry/src/index.ts`](../../../packages/registry/src/index.ts)): `kind: "cron"`, `probeConfig: { kind: "cron", cronName: "fluncle-<job>", cadenceMs }`, `weights: { status: … }`, `exposedContent`, and — REQUIRED for the `/status` row — `title` (the display name, e.g. "Audio enrichment") + `statusDescription` (a quiet, public-safe one-liner). The registry test build-fails a cron missing either. For a **fixed wall-clock** cron add `schedule: { time: "HH:MM", tz: "Europe/Amsterdam", weekday? }` so `/status` computes the TRUE next-fire (DST and all) instead of a cadence estimate. `cronSurfaces()` is the single source of truth every consumer reads.
6. **`/status`** — the registry entry flows into [`status.tsx`](../../../apps/web/src/routes/status.tsx) via `cronSurfaces()` automatically: the row's title + subtitle come from the surface's `title`/`statusDescription`, and `CRON_SCHEDULE` from its `schedule` — NO edit to `status.tsx`. Add the id to `OPS_AUTOMATION_IDS` if it's an ops cron (backups/self-deploy/audits/health) — otherwise `groupServices` files it under "Track automation" by default.
7. **The on-box prober mirror** — add a row to `AUTOMATION_CRONS` in [`fluncle-healthcheck.ts`](../../../docs/agents/hermes/scripts/fluncle-healthcheck.ts) (it mirrors `cronSurfaces()`) so the box prober reads the new marker dir at the right cadence and POSTs its `/status` row.
8. **Verify** — smoke on the box (`sudo systemctl start fluncle-<job>.service` → `journalctl -u fluncle-<job>.service` + a fresh marker), confirm the `/status` row goes green, and run `bun packages/registry/src/index.test.ts` (catalog invariants) + `bun run --cwd apps/web typecheck`.

**Changing** an existing cron is a subset: edit the sweep and/or the `<job>-timer/` unit, keep the registry `cadenceMs`/`schedule` in step with the timer (a drifted cadence makes `/status` freshness lie), and re-verify. A merge to `main` bakes the sweep into the image (pin-watch auto-deploys); the box is the deploy target, the repo is canonical.

## When the box misbehaves

- Sweep logs are in journald (`journalctl -u fluncle-<job>.service`) and in each run's marker under `/opt/data/cron/output/fluncle-<job>/` (its stderr tail included); the container's own stdout carries nothing, because its main process only idles.
- A "refused" publish is the role boundary working as designed: a publish-class command **should** come back 403 for the agent token. The operator runs those actions with the full token, not the box.
