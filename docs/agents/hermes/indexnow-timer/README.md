# Daily catalogue IndexNow submission

`fluncle-indexnow` observes the material version of every sitemap-visible finding and catalogue page, then submits one batch of due URLs to IndexNow. Search-engine notification is operator plumbing, so its registry surface stays off the public status board while the prober and run ledger still watch it. The primary slot is 06:00 Europe/Amsterdam, after the nightly hub-count reconciliation and its 05:25 retry. The 07:15 retry slot is clear of the other daily timers. Both slots have up to 60 seconds of jitter and catch up after downtime.

## Why observed page versions

Catalogue writes do not share a material-change timestamp. The Worker fingerprints the fields that public pages render, records only new or changed versions, and supplies their observed change dates to the sitemap. A first observation preserves an existing page lastmod proxy when available. Attempt counters and other bookkeeping do not change a version. Accepted submissions stamp exactly the submitted fingerprint; concurrent changes and rejected requests stay due.

## Model

The Worker uses 1,000-subject keyset windows for every kind. Entity replies contain their own displayed columns, maintained summaries and indexed identity/alias/social/lineage lookups. Finding replies retain their displayed video and observation material; mixtapes project their ordered member list into title, credits, coordinate and cue time without loading full track DTOs. Ledger reads stay inside each window's primary-key range and selected subject IDs. Each window commits changed versions and pruning together in one batch. Local integration fixtures measure response bytes and complete walk time; these are correctness and response-size evidence rather than hosted-Turso latency claims.

A local integration sample measured complete 1,000-subject walks at 60 ms for artists, 55 ms for labels, 64 ms for albums, 96 ms for tracks and 162 ms for logs. Entity replies were 1,117,235, 1,078,287 and 999,287 bytes respectively, with 720-character biographies and artist alias/social lookups. Finding material carries the observation alignment as its length beside `observation_generated_at` rather than the full word timing, so a log window stays far below the local 10 MiB response cap. These measurements support one window size for all kinds without replicating graph-page child rendering.

Track fingerprints include title, artist credits and public graph links, album and label identity, release date, effective cover, linked Spotify/Apple/Beatport/Deezer/Discogs/official YouTube destinations, BPM, key, duration, ISRC/recording identity, preview availability, and finding log ID. Owned covers suppress hidden fallback URLs. Entity fingerprints include name, bio, effective image, maintained renderable/certified counts and latest release date; artists also carry public identity links, aliases and socials, albums carry their catalogue number, UPC and release-group identity, and labels carry identity, founding facts, aliases and parent/child lineage. Finding fingerprints include displayed track metadata, effective cover and graph links, note, video and observation material, galaxy identity under the public naming gate, chronological neighbor links and published social links. Generic update timestamps are excluded except when they supply the rendered video upload date. Published mixtapes include title, note, dates, duration, sequence, set-video date, external links, member count and ordered member coordinates, titles, credits and cue times. Bio attempt/status fields do not gate the current loaders' displayed text and are excluded with other bookkeeping.

An entity's observed date moves when its own facts, artwork or maintained counts and release summary change. Editing a child track's title moves that track's own date, rather than re-dating every related graph page. Dynamic sonic-neighbour recommendations do not enter the fingerprint.

The walk prunes departed subjects in the current kind's `(cursor.after, last]` interval and clears the remaining suffix when that kind finishes. It preserves earlier cursor intervals and other kinds. `removed` counts deleted versions. Queue depth counts due ledger versions through the partial index alone; it can include departed subjects whose interval has not yet been walked. Submission independently re-checks liveness while selecting its batch, so those subjects are never posted.

The baked [`indexnow.sh`](../scripts/indexnow.sh) wrapper sources the existing agent token and runs [`indexnow.ts`](../scripts/indexnow.ts). The orchestrator calls the agent-tier `submit_indexnow` op at `POST /api/v1/admin/indexnow/submit` directly, without relying on the box's pinned CLI release.

1. Send `{ "phase": "walk" }`, then `{ "phase": "walk", "cursor": <next> }` until `next` is null. Each completed window atomically checkpoints its next cursor under `INDEXNOW_STATE_DIR` (default `~/.indexnow`), so a partial pass resumes across nights instead of repeatedly walking the same prefix; a complete pass removes the checkpoint. When resuming a later catalogue kind, the tick first refreshes the finding windows from the start, then returns to its saved catalogue cursor. Each bounded window acquires its own database-admission phase and retries a yielded acquisition once. New windows start only inside a 600-second budget, with at most 2,000 windows per tick.
2. Send `{ "phase": "submit" }` in a separate admitted phase even when the walk stops early. The Worker selects at most 10,000 currently indexable due URLs, prioritizing findings, artists, labels, albums, then tracks, newest first within each kind. Only HTTP 200 and 202 are accepted.
3. Emit the audit line and JSON summary through `cron-output.sh`, which writes the freshness marker and fleet run-ledger row. A budget stop after completed windows is a successful partial run. A rejected submission, failed phase, or zero completed windows sets `errors: 1` and `ok: false`; its daily retry can run once at 07:15. A successful partial run completes the day's slot.

The operator can inspect the first submission with `{ "phase": "submit", "dryRun": true }`: this returns the URL count, current due count, and a small sample without sending or stamping. The sweep's `--dry-run` flag performs the observation pass and uses that dry submission; `produced` stays zero because no URL was accepted.

## Audit

Every tick logs an `AUDIT` line with `checked`, `inserted`, `changed`, `removed`, `submitted`, `due`, `status`, and `errors`. Its last stdout line is the JSON run summary: `checked` counts subjects walked, `produced` counts URLs accepted, `queueDepth` counts due URLs remaining, and `errors` counts run failure. `submitted` is the submitted URL count, `status` is the IndexNow HTTP status or null when no response was received, and `partial` / `reason` describe an unfinished walk. Unknown queue depth remains null instead of pretending to be zero. A rejection remains visible as `ok:false`, with its HTTP status and short error message. If IndexNow accepts a batch but stamping its versions fails, `produced` retains the accepted URL count while `errors: 1` reports the failed run and the unstamped versions remain due.

```text
[indexnow] AUDIT checked=2000 inserted=10 changed=3 removed=2 submitted=13 due=0 status=202 errors=0
```

## Activation

Activation is operator-gated: deploy the Worker and its generated migration, redeploy the box image so the scripts are baked, inspect a dry submission, then install and enable the host timer. The existing [`install-host-timers.sh`](../install-host-timers.sh) discovers this timer directory automatically; a targeted refresh uses `--refresh-unit fluncle-indexnow.service --refresh-unit fluncle-indexnow.timer`. A refresh installs units without activating them. Enabling the timer and starting a real submission require the operator's approval. No new secret is needed; the existing agent token carries this reversible internal-footprint action. The registry's `cron.indexnow` entry supplies the prober cadence and expected run-ledger writer.
