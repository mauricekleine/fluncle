# Daily catalogue IndexNow submission

`fluncle-indexnow` observes the material version of every sitemap-visible finding and catalogue page, then posts due URLs to IndexNow from the box in paced batches. Search-engine notification is operator plumbing, so its registry surface stays off the public status board while the prober and run ledger still watch it. The primary slot is 06:00 Europe/Amsterdam, after the nightly hub-count reconciliation and its 05:25 retry. The 07:15 retry slot is clear of the other daily timers. Both slots have up to 60 seconds of jitter and catch up after downtime. The service has a 75-minute timeout covering two catch-up attempts, admission waits, observation and submission budgets, and the final in-flight batch.

## Why observed page versions

Catalogue writes do not share a material-change timestamp. The Worker fingerprints the fields that public pages render, records only new or changed versions, and supplies their observed change dates to the sitemap. A first observation preserves an existing page lastmod proxy when available. Attempt counters and other bookkeeping do not change a version. Accepted submissions stamp exactly the submitted fingerprint; concurrent changes and rejected requests stay due.

## Model

The Worker uses 1,000-subject keyset windows for every kind. Entity replies contain their own displayed columns, maintained summaries and indexed identity/alias/social/lineage lookups. Finding replies retain their displayed video and observation material; mixtapes project their ordered member list into title, credits, coordinate and cue time without loading full track DTOs. Ledger reads stay inside each window's primary-key range and selected subject IDs. Each window commits changed versions and pruning together in one batch. Local integration fixtures measure response bytes and complete walk time; these are correctness and response-size evidence rather than hosted-Turso latency claims.

A local integration sample measured complete 1,000-subject walks at 60 ms for artists, 55 ms for labels, 64 ms for albums, 96 ms for tracks and 162 ms for logs. Entity replies were 1,117,235, 1,078,287 and 999,287 bytes respectively, with 720-character biographies and artist alias/social lookups. Finding material carries the observation alignment as its length beside `observation_generated_at` rather than the full word timing, so a log window stays far below the local 10 MiB response cap. These measurements support one window size for all kinds without replicating graph-page child rendering.

Track fingerprints include title, artist credits and public graph links, album and label identity, release date, effective cover, linked Spotify/Apple/Beatport/Deezer/Discogs/official YouTube destinations, BPM, key, duration, ISRC/recording identity, preview availability, and finding log ID. Owned covers suppress hidden fallback URLs. Entity fingerprints include name, bio, effective image, maintained renderable/certified counts and latest release date; artists also carry public identity links, aliases and socials, albums carry their catalogue number, UPC and release-group identity, and labels carry identity, founding facts, aliases and parent/child lineage. Finding fingerprints include displayed track metadata, effective cover and graph links, note, video and observation material, galaxy identity under the public naming gate, chronological neighbor links and published social links. Generic update timestamps are excluded except when they supply the rendered video upload date. Published mixtapes include title, note, dates, duration, sequence, set-video date, external links, member count and ordered member coordinates, titles, credits and cue times. Bio attempt/status fields do not gate the current loaders' displayed text and are excluded with other bookkeeping.

An entity's observed date moves when its own facts, artwork or maintained counts and release summary change. Editing a child track's title moves that track's own date, rather than re-dating every related graph page. Dynamic sonic-neighbour recommendations do not enter the fingerprint.

The walk prunes departed subjects in the current kind's `(cursor.after, last]` interval and clears the remaining suffix when that kind finishes. It preserves earlier cursor intervals and other kinds. `removed` counts deleted versions. Queue depth counts due ledger versions through the partial index alone; it can include departed subjects whose interval has not yet been walked. Claim independently re-checks liveness while selecting due versions, so those subjects are never posted.

The baked [`indexnow.sh`](../scripts/indexnow.sh) wrapper sources the existing agent token and runs [`indexnow.ts`](../scripts/indexnow.ts). The orchestrator calls the agent-tier `submit_indexnow` op at `POST /api/v1/admin/indexnow/submit` directly, without relying on the box's pinned CLI release.

1. Send `{ "phase": "walk" }`, then `{ "phase": "walk", "cursor": <next> }` until `next` is null. Each admitted window atomically checkpoints its next cursor under `INDEXNOW_STATE_DIR` (default `~/.indexnow`). A partial pass resumes across nights, refreshing finding windows before returning to its saved catalogue cursor. New windows start inside a 600-second budget, with at most 2,000 windows per tick. A complete real pass removes the cursor and atomically records `walk.json` with `completedAt`. A completion less than 12 hours old skips observation on a retry; missing or corrupt completion state requires a walk.
2. Send `{ "phase": "claim", "limit": 10000 }` in one admitted phase, even when observation stops early. The Worker selects live due versions through the partial index, prioritizing findings, artists, labels, albums, then tracks, newest first within each kind. It returns the current due count, exact versions and IndexNow host/key/key location. Claim sends nothing and stamps nothing.
3. The box POSTs those URLs directly to `https://api.indexnow.org/indexnow` in batches of 1,000, up to 10,000 per run, with a 15-second request timeout and a five-second pause between batches. New batches stop after a 300-second submit budget. The box supplies a dedicated source IP; Worker egress IPs are shared, and Bing-operated endpoints rate-limit by source IP. On primary HTTP 429, the same batch goes once to participating endpoint `https://yandex.com/indexnow`; participating engines share accepted submissions. If both endpoints return 429 and the primary supplies `Retry-After` of at most 120 seconds, the box waits that delta or HTTP-date interval and retries the primary once. Only 200 and 202 count as acceptance.
4. Each accepted batch gets its own admitted `{ "phase": "ack", "versions": [...] }`. Admission children read private temporary request files, avoiding single-argument limits for full batches; the parent removes them after each phase. The Worker uses its clock to stamp only matching kind, subject ID, fingerprint and changed date in one write batch. A changed or unaccepted version stays due. An ack failure or admission yield stops submission, retains the accepted `produced` count and sets `errors: 1`; unacknowledged versions remain due and can be harmlessly resubmitted.
5. Emit the audit line and JSON summary through `cron-output.sh`, which writes the freshness marker and fleet run-ledger row. A walk or submit budget stop is a successful partial run. An unresolved 429 stops with `partial: true` and `reason: "rate_limited"`: accepted work keeps `errors: 0`, while zero accepted URLs sets `errors: 1` so the daily retry runs. Every other rejection or transport failure sets `errors: 1`. No claimed URLs is a clean success. Zero walked windows fails unless the recent complete walk was skipped.

The operator's read-only inspection is `{ "phase": "claim", "limit": 5 }`. The sweep's `--dry-run` observes and claims, reports `wouldSubmit` and the first five URLs, POSTs nothing and acks nothing. It never writes `walk.json`, so it cannot suppress the next real observation. Its marker and ledger row carry `dryRun: true` and `gateState: "dry-run"`; daily retry state ignores them for every job, so no marker needs moving before a real start.

## Audit

Every tick logs an `AUDIT` line with `checked`, `inserted`, `changed`, `removed`, `submitted`, `due`, `status`, `errors`, accepted/attempted `batches` and `vendorCalls`. Its last stdout line is the JSON run summary: `checked` counts walked subjects, or claimed items when `walkSkipped: true`; this makes a retry's inspected work visible. `produced` counts accepted URLs, `submitted` counts URLs POSTed across all endpoint attempts, `vendorCalls` counts HTTP requests and `queueDepth` is the last claim/ack due count. `status` is the last IndexNow HTTP status, or null when that request receives no response. Unknown queue depth stays null.

`batches` records each request's `size`, `status`, `endpoint` (`indexnow` or `yandex`), `accepted`, and optional parsed `retryAfterSecs`. `rateLimited` records any HTTP 429; an unresolved limit also retains a supplied `retryAfterSecs` in the summary. `partial` / `reason` name budget, observation or rate-limit stops. A rejection stays visible as `ok: false` with a short error. Dry runs keep `produced`, `submitted` and `vendorCalls` at zero.

```text
[indexnow] AUDIT checked=2000 inserted=10 changed=3 removed=2 submitted=13 due=0 status=202 errors=0 batches=1/1 vendorCalls=1
```

## Activation

Activation is operator-gated: deploy the Worker and its generated migration, redeploy the box image so the scripts are baked, inspect a claim or dry run, then install and enable the host timer. The existing [`install-host-timers.sh`](../install-host-timers.sh) discovers this timer directory automatically; a targeted refresh uses `--refresh-unit fluncle-indexnow.service --refresh-unit fluncle-indexnow.timer`. A refresh installs units without activating them. Enabling the timer and starting a real submission require the operator's approval. No new secret is needed; the existing agent token carries this reversible internal-footprint action. The registry's `cron.indexnow` entry supplies the prober cadence and expected run-ledger writer.
