# Tonight's domain: DB query shape at scale

Fluncle's archive grows on its own — the catalogue crawler mints `tracks` rows every ten minutes, the resolver mints `track_artists` edges and `artist_socials` links, and `crawl_frontier` grows with both. The certified archive stays small (tens of findings); everything around it does not. So the one failure mode that matters here is **recompute-by-full-scan on a grown table**: a query that was fine at 5k rows, is a wall at 48k, and takes the page (or the sweep, or the deploy) down at the 150k target. `docs/db-scale-backlog.md` is the audit that found and priced this — read its **Root verdict** first; it names the two shapes everything collapsed to, and the per-item `tier=… · <table> · T…` headers are that audit's shape-family tags for the families below.

**The four growing tables: `tracks`, `crawl_frontier`, `track_artists`, and `findings` used as an anti-join** (`artist_socials` is the resolver-grown neighbour — same rules). Tonight's job is the **semantic** half of the guardrail. Its sibling is a static build-fail net, `apps/web/src/lib/server/db-query-shape.test.ts`, which greps the server SQL surface for the literal forbidden shapes and fails the deploy on a new one; if that file is in this checkout, read its allowlist first and treat it as ground truth for what is already known — never re-file an allowlisted entry. You hunt what a grep cannot see: an O(tracks) group-by reached through a helper, an anti-join hidden behind a view or a shared SQL fragment, a per-row query issued inside a loop, an unbounded materialization into the isolate.

## The hunt

**1. The catalogue anti-join, reached indirectly (highest value — the most-repeated shape in the app).** Keystone 1 shipped (#859): `tracks.is_catalogue` is a maintained flag with a partial index, written atomically with the `findings` insert at every certify/publish site. So the discriminator is **materialized** — a query that still derives it (`findings.track_id is null`, `not exists (select 1 from findings …)`, `left join findings … where f.track_id is null`) without an accompanying `is_catalogue`/certified predicate is re-deriving by full scan what one indexed column answers by seek. A grep finds the literal join; **you** find it assembled from a shared SQL fragment, a helper that returns a `where` clause, a builder that composes the predicate from parts, or a second query joined to the first. Two deliberate survivors — do **not** re-flag them: `funnel.ts` (its findings join is pinned by the `certified` arm and the shared `kindClause`, so converting buys nothing) and `labelFindingCountsByIds` (the `/admin/labels` per-page count stays on the raw `findings` aggregate on purpose — the one place a certification mismatch should show from truth, not from the mirror, and it is bounded to one page of ids).

**2. The entity-hub group-by, and the mirrors that must not drift.** Keystone 2 shipped: `labels`/`albums`/`artists` each carry a maintained `renderable_track_count` + `certified_finding_count`, every consumer reads them through the ONE shared gate `hubInclusionWhere(alias)` (`apps/web/src/lib/server/labels.ts`), the deltas are written by `apps/web/src/lib/server/hub-counts.ts`, and the nightly `reconcile_hub_counts` sweep is the drift backstop. Two findings live here. (a) A **new** entity-list/count/worklist/sitemap read that re-derives inclusion by joining `tracks` or `track_artists` and grouping — `group by <fk> having (sum(certified) > 0 or count(*) >= floor)` — instead of filtering the small entity table by the stored columns. At 150k that gate measured 5.8× (labels) / 46× (artists, over ~225k edges); `EXPLAIN QUERY PLAN` on a correct gate references no `tracks`/`track_artists`/`findings` at all, so **EXPLAIN is your check**. (b) A **new edge-moving write path** — one that stamps `label_id`/`album_id`, inserts a `track_artists` row, links during crawl, dismisses, marks a duplicate, merges, or certifies — that does not move the counters through `hub-counts.ts`. That is silent drift the nightly sweep papers over; the write path is the bug. (Two bulk backfill scripts skip the counters on purpose and are covered by the sweep — not findings.)

**3. Per-row queries: the loop and the correlated subquery.** A query inside a `for`/`for await`/`map` over a list that grows with the archive is N+1 by construction (the demand batch's per-artist frontier scan was this, inside a write lock). So is a correlated subquery in a select list that the planner evaluates once per output row — the label cover `limit 1` sorting a big imprint's rows per tile, a `…MissingBio`-style per-row `exists`. And so is a CTE referenced more than once: `docs/local-database.md` trap 4 — the planner flattens it and re-runs it per `union all` branch or per outer row of a nested loop (63 s hosted on `/recommendations`; p95 27 s on the rank sweep). A batch bounded by a page size or a fixed id list is fine; a batch bounded by "however many rows exist" is a finding.

**4. Unbounded materialization into the isolate.** Never pull a growing column or an unbounded row set into the Worker to rank, count, or dedupe it in JS. `turso dev` throws at its 10 MiB response cap so this looks like a bug locally; **hosted has no cap**, so in production it silently grows toward OOMing the 128 MB isolate — the failure mode is backwards from safe. Rank, aggregate, and `limit` in SQL. Same family: `select *` or the fat `TRACK_SELECT` on a public list read where `LEAN_TRACK_SELECT` is the right projection, and any read that joins `track_embeddings` for its 4 KB vector on a path that only needs to know WHETHER a vector exists (that question is `tracks.has_embedding`).

**5. Non-sargable predicates and an ORDER BY no index can serve.** A filter or sort column wrapped in a function defeats its btree: `lower(tracks.label)`, `substr(release_date, 1, 4)`, `coalesce(a, b)` in an `ORDER BY`, a collation mismatch, a leading-wildcard `like '%' || ? || '%'` over unindexed JSON. So does a raw expression as a leading sort key (`(f.track_id is not null) desc`), or a cross-table `exists` where a maintained mirror exists (`has_embedding`, `has_isrc`, `is_catalogue`) — a partial index is only considered when the query's WHERE provably implies its predicate, which no `exists` over another table can and a deep-tail `OFFSET` pager (O(offset) per request — a crawler walking to the tail reads ~144k index entries). **The hard-won lesson: adding an index usually does NOT fix these** — five backlog items proved exactly that, because the ORDER BY forces a table read the index can't serve. The durable fix is almost always the **rewrite** (make the predicate sargable, make the sort match a real index prefix, seek instead of offset), not a new index. Rewrites you can verify are fixes; index proposals are files.

**6. Recompute-per-call that a hoist or a memo kills outright (the safest, highest-yield fix class).** Wave 1's whole result: seven of eight full scans per rank tick were removed with **zero schema change and zero dependence on the planner** — a count recomputed on every call for a drain signal a cheaper boolean already answers; an aggregate gated to the wrong branch so it ran per call instead of per tick; a value read twice in one call; a status read whose numbers no caller consumes; three independent scans of the same join fired in one `Promise.all`. These are pure code reasoning — provable by reading the call graph, verifiable by test, no hosted proof needed. **Lean hard toward fixing this class.** Hunt it in the recurring sweeps first (they pay the cost 144×/day): the rank sweep, the crawl tick, the funnel snapshot, the work queues.

**7. The hosted-Turso reality rails.** `docs/local-database.md` → "Local is not production" is law: a local number is not evidence, and local is misleading in the dangerous direction (it makes slow code look fast and broken code look fine). Two rails are outright findings wherever they appear: a `create index … libsql_vector_idx` against a populated table (hosted, it errored `database is locked` and **wedged the write path for 20+ minutes**; locally it silently builds an EMPTY index and returns garbage with no error) and a query vector bound as **text** rather than a raw BLOB (26,700 ms vs 1,883 ms hosted at 100k — a 14× cliff that does not exist locally). Both are file-and-flag, never a fix you improvise.

## Never re-propose these — they are settled

- **Shipped and live:** Keystone 1 (`is_catalogue`), Keystone 2 (the stored hub counts, the shared `hubInclusionWhere` gate, the nightly reconcile sweep), the Wave-1 hoists, and the proven index/rewrite batch. `docs/db-scale-backlog.md` → "Shipped (live)" is the list. Re-proposing shipped work reads as an audit that didn't read the room.
- **Proven dead on hosted at 150k — do NOT ship as specified** (backlog "Wave 1 — outstanding"): **12** the analyze-worklist partial index (the WORK_ORDER `ORDER BY` defeats it; needs an explicit `INDEXED BY` — a design call), **14** the capture terminal-status composite (the anti-join drives the scan first), **15** the `tracks(label_id, release_date)` composite (unused because the ORDER BY leads with `release_date is null asc`, and a 24 s build), **17** the artist-review `(reviewed_at, created_at)` index (can't bound the GROUP BY alone; needs the bounded-head-walk rewrite), **19** the Ear-lens duplicate-prefix partial index (used, but marginal, and a 16 s build). If you believe one of these is now live-again, the only admissible argument is a fresh hosted measurement — which you cannot run. File the reasoning; don't ship the index.

## Ownership boundaries — do not touch

- **All vector-distance math** — every `vector_distance_cos` / similarity / sonic-search / "sounds like" path. The vector-serving stack owns it (`apps/sonar` + `docs/vector-serving.md`). Only the **non-vector** shape around it (a candidate-set anti-join pre-filter, a missing cache) is in scope, and even then prefer filing.
- **The artist-image backfill worklist** (`apps/web/src/lib/server/backfill-artist-images.ts`, the `image_url is null` scan) — owned by the artist edges/credits/visibility session. Known; not yours.
- **The reconciliation sweep's own SQL** (`apps/web/src/lib/server/hub-counts-reconcile.ts`) — it recomputes by design; that IS the job. Its artists source is pinned to `track_artists ⋈ tracks` deliberately (prod carries orphaned edges), so "optimize it to count raw edges" is a correctness regression, not a fix.

## Disposition — what you may ship tonight

**Fix** the shapes you can prove by reading and verify by test: a hoist, a memo, a removed unused read, a predicate made sargable, a per-row loop folded into one bounded query, a projection trimmed to the lean select, an anti-join swapped onto `is_catalogue`, a hub read swapped onto `hubInclusionWhere`. Run the checks (`bun run --cwd apps/web typecheck`, the module's own `*.test.ts`, `bun run --cwd apps/web lint`) and add or extend a focused test that pins the new shape.

**File** to `docs/audit-backlog.md` — never ship — anything that needs a **migration, a new index, or a stored column**. Migrations are on the preamble's hard-rails list, and an index is unprovable from here: Turso keeps no planner statistics, so whether the planner picks an index is an empirical question that only a **hosted** scratch DB answers. Every filed index/column row must state, in its fix column, that it is gated on a hosted-Turso proof at 150k via the `apps/web/scripts/bench-db-scale.ts` pattern (seed with `scripts/lib/scale-seed.ts`, measure p50 + `EXPLAIN QUERY PLAN` before/after through `@libsql/client/web`, destroy the DB) — operator-only, since Turso Cloud credentials are not on this box. A filed row without that gate stated is an incomplete row.
