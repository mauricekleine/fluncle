# fluncle-device-mirror-timer — the shared device-replica publisher

## Dormant

This job is parked. The iOS app has no users, and the mirror's embedded-replica sync of the 2.2 GB main database halves the primary's write capacity while it runs and costs about half of the account's embedded-sync volume. The code, the units, and the `fluncle-device` database stay as they are; nothing on the Worker produces work that only the mirror consumes, so nothing queues up while it sleeps. The app keeps reading the last published generation.

One marker parks it: the [`DORMANT`](./DORMANT) file in this directory. [`install-host-timers.sh`](../install-host-timers.sh) installs these units but never enables the timer; a full install or a `--refresh-unit` of either unit disables it and verifies it is neither enabled nor active, and fails if it is or if its state cannot be read (a timer that was never installed counts as already parked). [Pin-watch](../pin-watch/README.md) disables it the same way before a rebuild and never puts it back on when it restores the sweep timers. [`cron-roster.ts`](../scripts/cron-roster.ts) lists the timer as dormant instead of expected, and `cron.device-mirror` carries a `dormant` reason in `@fluncle/registry`, which takes it out of `/status`, the healthcheck prober, and the run-ledger missing-writer roster. `cron-roster.test.ts` fails if the marker, the registry, and the healthcheck prober ever disagree.

To revive it:

1. Delete `DORMANT` from this directory.
2. Delete the `dormant` field from `cron.device-mirror` in `packages/registry/src/index.ts`, and raise the run-ledger roster count in `packages/registry/src/index.test.ts` by one.
3. Add `{ cadenceMs: 60 * 60_000, match: "device-mirror", service: "cron.device-mirror" }` back to `AUTOMATION_CRONS` in [`fluncle-healthcheck.ts`](../scripts/fluncle-healthcheck.ts).
4. Run `bun test --cwd docs/agents/hermes/scripts cron-roster.test.ts` and `bun run --cwd packages/registry test`; merge, and let pin-watch bake the image.
5. On the rave-02 host, from an up-to-date checkout, as root: `bash docs/agents/hermes/install-host-timers.sh --refresh-unit fluncle-device-mirror.service --refresh-unit fluncle-device-mirror.timer`, then `systemctl enable --now fluncle-device-mirror.timer`, then run one attended tick (`systemctl start fluncle-device-mirror.service`) and check the activation criteria at the end of this page. The first sync after a long sleep replays every frame the replica missed; if `~/device-mirror` was removed it is a full 2.2 GB sync.

The host trigger for the hourly, zero-LLM device publisher tick. The replica is what the live mobile app's offline-first store pulls, so freshness is a product property: the tick publishes once the live replica is older than `DEVICE_MIRROR_PUBLISH_INTERVAL_MS` (default 1 h) and otherwise reports `gateState: "paused"` with the replica's age, costing no sync, no derivation and no writes. `DEVICE_MIRROR_FULL_REBUILD=true` forces a publish. [`device-mirror.sh`](../scripts/device-mirror.sh) runs the baked [`device-mirror.ts`](../scripts/device-mirror.ts), explicitly syncs the production database once into a persistent local embedded replica, and closes the sync client before any SQLite reader opens the file. The anchored IDs are selected into one local TEMP relation; every allowlisted tracks/findings/edges/entity copy, count, closure proof, and fingerprint then reads local storage. A corrupt or incomplete replica/generation is discarded and rebuilt automatically, while `DEVICE_MIRROR_FULL_REBUILD=true` is the explicit convergence escape hatch.

The service starts the mirror wrapper directly. The orchestrator checks the local source replica, including `PRAGMA quick_check`, before asking `database-admission-runner.sh phase fluncle-device-mirror` to admit the remote embedded sync against the primary database. After the phase releases, it checkpoints, validates, and protects the local replica, then performs the local SQLite derivation and all reads, writes, comparison, staging, and verification against the separate derived device database. A corrupt embedded-client metadata file is removed outside the lease before one fresh admitted sync attempt. The registry records the target as `derived-remote`; admitting each target page would consume a primary-database coordinator write for work that cannot contend on the primary lane. Target reads still use primary-key pages of at most 200 rows, and stage uploads still use at most 200 rows with their checkpoint in the same transaction. The normal delta path writes only drifted rows and the metadata watermark in one transaction. If the source-sync phase yields, the tick reports `admissionOutcome: "phase-yielded"`, `gateState: "paused"`, and `reason: "database_admission"`; a staged generation from an earlier interrupted tick remains resumable. A yield cannot publish an incomplete live generation. Remote embedded sync remains one primary-database call whose hold time must be measured, especially on a forced full rebuild.

## What a publish writes

A publish writes only the rows that drifted. The verified local generation and the live target are walked together in primary-key order — the generation streams off local disk, the target is read one bounded keyset page at a time — and two rows are equal when their digests agree. The digest is derived from `DEVICE_DB_COLUMNS` and the same canonical encoding the generation fingerprint uses, so a column added to the allowlist enters the comparison automatically and a target whose stored columns disagree with the allowlist is rejected before the walk starts. Every local row also feeds a projected fingerprint, the generation's own fingerprint recomputed from the rows the walk actually saw; a disagreement is a walk that skipped or double-counted a row and falls back rather than ships. The resulting inserts, updates and deletes land in ONE target transaction — dependent-first deletes, parent-first upserts, the `device_sync_meta` fingerprint cutover — exactly as the whole-generation cutover does, so a device reads the old complete generation or the new complete generation and the watermark says which. The run summary reports `publishPath` (`delta` / `rewrite` / `replay`), `rewriteReason`, `deltaRows` and `produced` (rows written), so the ledger shows which path a tick took.

The staged whole-generation rewrite is the fallback, and the `rewriteReason` names why it was taken: `schema_change` (the stage shape no longer matches the shipped column list, so the live rows are of the old shape), `no_prior_generation` (the target carries no content fingerprint to diff against), `delta_over_threshold` (more drift than one transaction should carry — `DEVICE_DELTA_MAX_SHARE` of the generation, capped at `DEVICE_DELTA_MAX_ROWS`; the walk abandons itself the moment the ceiling is crossed, so an over-threshold tick pays a partial read rather than a wasted full one), or `delta_validation_mismatch`. On that path the generation is uploaded to bounded, restart-checkpointed target staging tables; staging row counts, every copied pointer, and a canonical typed-row fingerprint are proven before publication, and a fixed server-local delta measurement precedes the cutover transaction.

Neither path can expose partial live rows, and a lost response after commit is recognized as an idempotent replay on restart. Staging cleanup happens only after live counts, closure, version, and fingerprint metadata validate, and the live tables are never dropped or recreated, preserving libSQL replication history.

`bun run --cwd apps/web scripts/db-performance/device-resources.ts --profile <1x|2x>` is the local resource proof. It materializes the manifest cardinality with 4,096-byte embeddings, proves the source census and initial source-file fingerprint, and drives the real local sync, checkpoint, anchored derivation, staged publication, full-rebuild, corrupt-replica, and interrupted-stage recovery paths. Each lifecycle window records its own start and completion before the next phase begins, and direct target row-count/watermark parity follows incremental refresh, full rebuild, and both recovery paths. It reports the OS-process RSS high-water separately from sampled heap and RSS, a real nonzero local WAL before the production checkpoint and zero WAL after it, semantic candidate/last-verified generation overlap, target-stage disk, and aggregate temporary disk. The aggregate sample covers the complete directory awaited before atomic rename while the populated derivation `.tmp`, target files and sidecars, and prior generation coexist; semantic overlap labels remain limited to the candidate and last verified generations. Its source sync is an explicit local file-copy stand-in and its target is local Bun SQLite, so it measures neither production/hosted-libSQL behavior nor network replication latency; each reported window has one sample and is compared separately with the 3,430-second service deadline.

Overlap is guarded twice: systemd does not start a second instance of an already-active oneshot, and the sweep acquires an atomic directory lock before syncing either database. A RUNNING tick touches its own lock every minute, so the stale window (`DEVICE_MIRROR_LOCK_STALE_MS`, default 15 minutes) bounds how long a lock left by a DEAD tick blocks its successors rather than how long a publish may take. A tick that finds the lock held by a live tick skips at once and reports `ok: false` with `gateState: "locked"` and `reason: "lock_held"`, so a lost publish is visible rather than green; a stale lock that cannot be removed (a non-empty directory or a file at the lock path) fails the tick with an error instead of looping. After every sync the tick truncates the replica's WAL and checks the checkpoint's result: a checkpoint still busy after its retries fails the tick loudly instead of reporting a half-finalized replica. The tick releases its lock on SIGTERM/SIGINT/SIGHUP; each admitted child has its own process containment if the admission lease is fenced.

## Activation is operator-gated

The repo half deliberately does not create a Turso database, provision credentials, or enable a timer. Before activation, the operator must create the derived database at the code's exact `device_sync_meta.schema_version`, provision the four source/target URL and token variables in the box's shared secrets file with the source token read-only and the target token write-scoped, rebuild the Hermes image so the phased orchestrator, native embedded-replica client, and canonical deriver are baked, and then run the repository's `install-host-timers.sh --refresh-unit fluncle-device-mirror.service`. Preview that replacement with `--dry-run --refresh-unit fluncle-device-mirror.service` first. Roll out the image before refreshing the unit: while the old whole-payload unit remains installed, its runner context makes the new script bypass nested phase acquisition and run the whole tick under the inherited lease; after the unit refresh, only source sync acquires a phase lease. The new direct unit requires the new image. A first attended service tick must finish with `errors: 0`, `queueDepth: 0`, `validation: "verified"`, and a moving `produced` count when drift exists; inspect admission runner `hold_ms` for the source sync and compare sibling wait expiries before increasing cadence.
