## Root verdict

CONFIRMED — the root is recompute-by-full-scan on grown tables, and it collapses to two shapes, both consequences of the tracks/findings subtype split: (A) the catalogue anti-join `tracks LEFT JOIN findings WHERE findings.track_id IS NULL` (equivalently `NOT EXISTS (SELECT 1 FROM findings …)`) with NO materialized "is-catalogue" discriminator, which forces a full left-join scan of the growing tracks table — this is the most-repeated shape in the audit and it drives the largest measured costs (the ~31s/19s/14s rank-sweep walls, up to 8×/tick, plus crawl status, the funnel scans, the search entity gate, and the Apple/fresh feeds); and (B) the O(tracks)/O(track_artists) grouped `having` scan behind the catalogue-scale entity hubs (labels/albums/artists), reused verbatim by the web hub, the public API list ops, the MCP browse, and the sitemap. The SINGLE denormalization that kills the largest share is a maintained per-track `is_catalogue`/`certified` flag with a partial index: it converts every `findings.track_id IS NULL` from a full scan into a seek, retiring shape (A) everywhere at once — the biggest recurring cost in the app (now Wave-2 Keystone 1, SHIPPED via #859). The per-entity `renderable_track_count`/`certified_finding_count` columns are the close-second keystone, retiring all of shape (B) in one stroke (web hub + API + MCP + sitemap + bio worklists + the search entity gate) — now Wave-2 Keystone 2, proven and recommended. Important nuance for sequencing, borne out by the ship data: the rank-sweep walls were ALSO substantially retired by the Wave-1 pure hoists alone (short-circuit countStale off batch-fullness, gate computeCatalogueCounts to the drain-end branch with a per-tick bucket delta, compute readArchiveAffinity once per call) — those removed 7-of-8 full scans per tick with zero schema change and zero dependence on Turso's (absent) planner stats, so Wave 1 bought the biggest immediate relief (SHIPPED via #847/#848) while the Wave-2 is_catalogue flag makes the residual scan and every on-demand consumer seek-fast and future-proof.

**7. KEYSTONE — the funnel stage scan, covered (`tracks_funnel_scan_idx` + the `has_embedding` mirror)**
`tier=denormalize · tracks · T2`
**STATUS: SHIPPED.** And it is the item that corrects a wrong diagnosis elsewhere in this doc, so the reasoning matters more than the fix.

- loc: apps/web/src/lib/server/funnel.ts (`runFoldedFunnelScan` / `foldedFunnelScanStatement`), apps/web/src/db/schema.ts (`has_embedding`, `tracks_funnel_scan_idx`)
- **the mis-diagnosis it corrects:** Keystone 1 recorded `funnel.ts` as a deliberate anti-join survivor because "its findings join is pinned by the `certified` arm and the shared `kindClause`, so converting buys nothing", and the module's own SCALE NOTE claimed "sub-second COUNT scans" and that `embedding_blob is not null` "reads the cell's null flag, not its bytes". Every one of those statements is true in isolation and the conclusion drawn from them was wrong. The findings probe was never the cost. **`embedding_blob` is a ~4 KB `F32_BLOB(1024)` that spills to overflow pages, and SQLite must walk that chain to reach any column stored AFTER it in the record.** The funnel's arms read `dismissed_at`, `duplicate_of_track_id`, `nearest_finding_score`, `spotify_anchor_attempted_at`, `isrc` — every one post-blob (cid 33 is the vector; those are 36-58) — so the scan dragged every vector in the archive to count null flags it never selected.
- **measured (hosted, 2026-07-26).** Isolating the mechanism on prod at 52k: three PRE-blob columns 0.23s vs three POST-blob columns 3.32s cold; `embedding_blob is not null` alone 0.26s (null-ness reads the record header — the cost is SKIPPING PAST the blob, not testing it). The folded scan itself: 9.5s cold / 0.38s warm, and Sentry caught a **15.08s** `GET /admin/funnel` span when a concurrent `catalogue/rank` sweep had evicted the page cache.
- **the before/after, on a 54,860-row clone of production** (`turso db create --from-db fluncle`, destroyed after — never `turso dev`, per AGENTS.md): **12.6-19.9s → 1.70s first-touch, 0.30s after**, plan `SCAN t USING COVERING INDEX tracks_funnel_scan_idx`, reading a **5 MB index against a 125 MB table**, with all twelve counts byte-identical to the pre-fix query. The one-time migration cost on the same rig: `ALTER TABLE ADD COLUMN` 0.45s (metadata only, no rewrite), the backfill 108s (21,088 rows rewritten), the index build 63s — **~3 minutes added to the single deploy that lands them**, and nothing on the deploys after. Worth watching against the "a Workers Build over 5 minutes is an alarm" rule.
- **fix:** a stored `has_embedding` mirror (item #4's column) + ONE covering index leading with `is_catalogue`, and rewrite the folded pass to read both mirrors so it names neither `findings` nor the blob. The select list is still assembled in the CANONICAL spelling and mechanically rewritten (`onMirrors`), so the funnel keeps counting the sweeps' own predicates rather than a copy — and the rewrite THROWS if a shared fragment is ever respelled past recognition.
- **three shapes that FAILED, recorded so nobody retries them:** (a) an index on the raw EXPRESSION `(embedding_blob is not null)` is never chosen by the planner; (b) a **VIRTUAL generated column** mirroring the same expression is not covered either — it measured 12-15s, ~3× WORSE than the join form, because every row recomputes from the table; (c) a partial index `where embedding_blob is not null` plans as `USING INDEX`, not `USING COVERING INDEX`, because the query's own reference to the blob column defeats coverage. A plain stored column is the only shape that covers. Also: the new index MUST LEAD with `is_catalogue` — demoted to a partial `where`, the planner prefers the narrower `tracks_is_catalogue_idx` seek and falls back to table rows, losing the entire win.
- **coverage is all-or-nothing, and is now enforced.** One arm reading a column the index lacks and the planner abandons it for the whole statement — same numbers, the full cold scan back, nothing else failing. The first draft of this index hit exactly that: `kindClause("anchor")` had grown an unanchorable-credits filter (`coalesce(spotify_anchor_attempts,0) < N`, `lower(artists_json) not in (…)`) after the shape was proven, and the two columns were missing. `funnel.integration.test.ts` now EXPLAINs the REAL statement and requires `COVERING INDEX tracks_funnel_scan_idx`, so the index/predicate contract is checked rather than remembered.
- **the general lesson, worth applying elsewhere:** "no blob crosses the wire" is not the same claim as "the scan does not read the blob's pages". Any scan of `tracks` touching a post-cid-33 column pays this toll — including keystone 2 slice C's nightly reconciliation, which groups by `label_id` (cid 40) and `album_id` (cid 39) and pays it by design (nightly, off the hot path). The durable alternative not taken: move `embedding_blob` to a side table, which would retire the toll for every scan at once but is a table rebuild on the load-bearing vector column.

### Index drop candidates (hosted-proof gated)

Every index on a growing table is paid for on every write to it, so a REDUNDANT index is pure cost. Two look redundant by definition. A DROP is still a schema change, so it lives under the same rule as an ADD: prove it against a scratch HOSTED Turso clone with `apps/web/scripts/bench-db-scale.ts` (`EXPLAIN QUERY PLAN` on the real consumers, then the timings), never on local evidence — `turso dev` will happily agree with a wrong answer.

- **`artist_socials_artist_id_idx` — the clean candidate.** `index("artist_socials_artist_id_idx").on(artistId)` (schema.ts:2890) is a STRICT PREFIX of `uniqueIndex("artist_socials_artist_platform_idx").on(artistId, platform)` (schema.ts:2886). Any seek or ordering the single-column index can serve, the unique composite serves from its leading column, and the composite cannot be dropped (it carries the uniqueness constraint). Nothing pins the plain index by name — there is no `INDEXED BY` anywhere in `apps/web/src`.
- **`tracks_anchor_fill_queue_idx` — orphaned by item 4, not yet provably redundant.** `index("tracks_anchor_fill_queue_idx").on(nearestFindingScore).where(spotifyUri is null)` was built for ONE query — the anchor worklist's ranked drain — and item 4 moves that query onto `tracks_anchor_order_idx`, which carries the same partial predicate with `has_embedding` ahead of the score. Nothing pins the old index by name (no `INDEXED BY` in `apps/web/src`), so it is a candidate the moment item 4's index is proven. What blocks a same-PR drop: the new index is NOT a superset by prefix (different leading column), so the planner could still be choosing the old one for a `spotify_uri is null` reader that wants score order without a `has_embedding` lead. Settle it the usual way — a hosted `EXPLAIN QUERY PLAN` over its remaining readers (`anchor-apify.ts`'s requeue UPDATE, funnel.ts's anchor arm, `anchor.ts`'s review read) once item 4 merges, then drop in its own PR.
- **`tracks_capture_priority_idx` — mostly shadowed, NOT clean yet.** `index("tracks_capture_priority_idx").on(capturePriority)` (schema.ts:601) is shadowed for every consumer that carries `capture_priority is not null` (or `>= 0`, which implies it) by the partial composite `tracks_capture_priority_track_id_idx` — `(capture_priority, track_id) where capture_priority is not null` (schema.ts:744) — which is both narrower and serves the full `capture_priority desc, track_id` order. The exception blocks the drop: `listCatalogueAppleWork` (`apps/web/src/lib/server/backfill.ts`, the Wave-1 #13 rewrite) orders by `capture_priority desc, t.track_id` with **no** non-null predicate, so SQLite cannot use a partial index there at all. The repo also contradicts itself about what that query rides — item 13 above says the partial composite, the query's own comment says the plain index — so settle it with a hosted `EXPLAIN QUERY PLAN` first. If the plain index is what serves it, the drop is gated behind that query gaining the non-null predicate (its ORDER BY already treats NULL as lowest), not behind a benchmark.
