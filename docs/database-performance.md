# Database performance contract

This document is the canonical, public contract for measuring Fluncle's database work. The Turso scalability program integrates from commit `f0b368203d42a3b92d5b5025c8064e27baa9f632` on the non-production `program/turso-scale` branch. Program work targets that branch only; the branch is implementation state, is never a production deployment source, and does not authorize a deploy, production query, hosted database creation, paid action, credential use, timer change, or mutation.

The harness lives in [`apps/web/scripts/db-performance`](../apps/web/scripts/db-performance). It owns one manifest, one synthetic fixture stream, one extensible contract registry, one runner, and one explicit budget vocabulary. It changes no production table, query, index, projection, or mutation path. The checked-in `perf_*` schema exists only inside a scratch or in-memory harness database.

## Evidence manifest

[`manifest.json`](../apps/web/scripts/db-performance/manifest.json) is the machine-readable audited 1× baseline. Scaling is deterministic integer multiplication: every audited cardinality and backlog is multiplied by exactly two or four. The 4× profile is a warning curve rather than a promise that every product SLO already holds.

These values are not projected to 2×/4× because schema-object counts and storage bytes do not scale as row arithmetic. The final program schema contains 171 explicit indexes, 29 on `tracks`; the executable final-index inventory compares that state with the 178-index, 32-track-index pre-contraction schema and records 55 keeps, seven drops, no additions, 67 named consumer contracts, and no unclassified consumer. Consumer plans are unforced unless the declared source coordinate has a production `INDEXED BY` lock; the executable `INDEX_EVIDENCE_RUNTIME_LOCKED_INDEXES` allowlist mirrors every such inventory lock, while forced replacement variants remain supplemental equivalence evidence. The release-date contraction includes exact mirrors of `/fresh`'s findings lane and its complete album aggregate, including the lead-artist lookup, `json_each` credit fold, cover fallback, grouping, distinct counts, and final order. The capture-priority singleton contraction proves both unforced Apple and Deezer worklists with their complete predicates, selected result columns, nullable/failure gates, capture-priority/track-id order, and limit; both forced `tracks_vendor_worklist_idx` variants are supplemental output-equivalence evidence and neither path needs a temporary sort.

The generator preserves the distributions that make the known shapes meaningful: 96 of 122,151 tracks are findings-backed; 43,372 have an embedding and 78,779 have a null/missing embedding; 154,551 artist edges give a mean fan-out of approximately 1.2652, modeled as one edge for every track and an exact 32,400-row second edge slice; 117,710 tracks, or approximately 96.4%, sit under enabled labels; 130,864 of 211,980 frontier rows are pending; the two measured non-empty work backlogs contain exactly 30,260 and 44,473 rows; and the measured empty full-analysis queue remains empty. Findings, embeddings, edge positions, label scope, frontier state, nulls, and backlog flags are spread deterministically rather than randomly. The audited vector reference is 43,372 embeddings × 1,024 float32 values × 4 bytes = 177,651,712 raw bytes, approximately 178 MB decimal, before table/index overhead.

Every value is derived from a row index and uses a `synthetic-*` ID or name. The generator has no production-data input, URL, credential reader, or network path. It yields at most 500 statements by default and reuses one deterministic 4,096-byte embedding blob, so a 4× run does not allocate all generated rows or vectors in the JavaScript heap. A small ratio-preserving derivative is available for CI, but its report says `exactProfileCardinality: false`; it is never presented as 1× evidence. An exact local run uses a fresh file-backed disposable libSQL database in an isolated sidecar, deletes it on exit, records fixture construction separately as `fixture.writeDurationMs`, and budgets raw contract-phase client resources through the explicit `process.memoryUsage.isolated-local-libsql-client` source. A post-write database census reads every fixture table plus every manifest distribution and requires their committed row counts to match the exact profile; generator input and attempted-insert counts alone are not cardinality evidence. Database pages remain outside the measured client process, matching hosted Turso's process boundary, while raw application heap, RSS, and wall budgets remain unchanged.

## Budgets

The registry encodes budgets as assertions and reports p50, p95, p99, maximum, result-row counts, affected-row counts, batch counts, queueing, plan output, and pass/fail. Current and 2× are required where specified. A red required budget is a failure; an average cannot waive it. A 4× timing miss is reported as a warning unless the invariant is explicitly required at 4×, but correctness, bounded memory, and plan laws still fail at every profile.

| Work class                         | Required steady-state contract                                                               |
| ---------------------------------- | -------------------------------------------------------------------------------------------- |
| Public route database spans        | p95 ≤ 250 ms and p99 ≤ 750 ms at 1× and 2×                                                   |
| Public route end-to-end            | p95 ≤ 1 s and p99 ≤ 2.5 s at 1× and 2×                                                       |
| Queue empty check or bounded claim | p95 ≤ 250 ms at 2×                                                                           |
| Background writer admission        | p95 ≤ 250 ms when uncontended at 2×; contention must be bounded and observable               |
| Ordinary mutation transaction      | no successful ordinary write above 2 s at 2×                                                 |
| Ambiguous mutation                 | every timeout resolves to committed, rejected, or safely retryable; zero unresolved outcomes |
| Sonar steady-state refresh         | zero remote full-corpus scans at 1×, 2×, and 4×                                              |
| Device derivation                  | zero repeated production-corpus scans beyond replica synchronization at 1×, 2×, and 4×       |

## Query-plan laws

A request-time or per-tick query must not scan a growing corpus merely to prove an empty queue, compute a count, or select a bounded batch. A bounded claim starts from an index whose leading columns express eligibility, due time, and ordering, or from a maintained work projection whose cardinality follows the backlog. Separate identity keys use separate sargable branches; a `CASE` or `OR` join that defeats every candidate index is forbidden on growing tables. A tiny selective relation such as `findings` must be able to drive its join because hosted Turso provides no production `ANALYZE` statistics for this workload. Request-time window sampling, expression grouping over a full catalogue, and repeated `UNION`/`GROUP BY` reconstruction belong in maintained projections or aggregates rather than hot reads.

Every critical contract asserts output correctness and plan shape. The runner records every `EXPLAIN QUERY PLAN` detail and detects a growing-table `SCAN` and `USE TEMP B-TREE`; contracts name the growing tables, allowed exceptional scans, required index/driver details, and whether temporary sorting is forbidden. Timing is evidence, never the only regression oracle.

Schema-neutral rewrite contracts execute the optimized statement alone during every warm-up and measured iteration, so the latency distribution is the final production statement rather than reference/proof overhead. After every selected contract has finished its mutation-capable work, one terminal read-only phase executes registry plan audits plus each comparison's reference plan, reference result, optimized equivalence result, cardinality check, and index structural proof; this ordering prevents an embedded-driver `EXPLAIN QUERY PLAN` statement lifetime from blocking a later transactional batch while retaining every correctness and plan law. Reports merge terminal evidence only into its owning contract and record exact request counts across warm-ups, measured iterations, terminal plan, and terminal proof without raw SQL. The artist-link fixture includes claimed and unclaimed MBIDs, same-name collisions, name drift, null identity, duplicate credits, catalogue flags, and position ordering; its optimized plan must probe the track primary key plus the MBID and NOCASE-name artist indexes without a growing-table scan or temporary sort. Sitemap finding rows, counts, and entity lastmods must drive from `perf_findings`, probe outward by indexed keys, and preserve the reference count, null, lastmod, and ordered-row results. The shared single-row optional-finding, single-row required-finding, plural identity-reference, and bounded bulk track/Log-ID resolver families each retain their reference output while probing both the track primary key and unique Log-ID index; no consumer may restore the cross-table `OR` shape.

## Mutation laws

Every registry-classified recurring writer and explicitly heavy reader enters `database-admission-runner.sh`; a mechanical registry/unit test rejects a classified unit that bypasses it. The coordinator has two global resources (`write` and `heavy-read`) with durable FIFO order by database-clock enqueue time and contender id. A mixed operation such as galaxy clustering owns its physical writer row while consuming both resources; its stored operation coordinate carries a reserved `|heavy-read` resource suffix, so a rolling registry rename or reclassification cannot weaken an already-held lease. That durable predicate is applied symmetrically to active exclusion and oldest-contender selection inside one serialized short transaction. The partial unique index backs each physical lane, while the transaction enforces cross-resource exclusion. At most one background writer and one heavy reader can therefore run, and a mixed contender cannot be passed by a later single-resource contender. Per-firing `RandomizedDelaySec` remains on every classified timer to spread harmless arrival load, but jitter is supplemental and never the concurrency authority.

`database_admission_enforced` in the shared `settings` KV is the remote default-off cutover: only the exact value `true` enforces; absent, malformed, or unreadable stays on the shadow compatibility path. `DATABASE_ADMISSION_FAIL_CLOSED=true` is a second, local default-off readiness gate in each unit's operator environment. Before rollout both are off, so shadow resolves the same committed owner/classification, reads the live queue and guardrails, and emits the same bounded vocabulary without inserting, waiting, stopping, or otherwise changing the sweep. Cutover order is exact: deploy the compatible code, arm the local gate on every host/container unit and verify that shadow firings yield without starting payloads, then set the database flag. Rollback reverses that order: clear the database flag, then clear the local gates. A locally armed firing never starts without an enforced grant, and a firing that has observed enforcement never continues after an unavailable or downgraded heartbeat. This closes an initial-partition bypass without making code deployment itself a behavior change.

Enforced acquisition uses one absolute deadline of at most 120 seconds, caps each HTTP request and poll sleep to the remaining budget, rejects a late grant, then cancels or releases its row so the next timer firing can resume the durable sweep work. Overrides may only reduce that ceiling. Every classified service preserves its prior payload budget beyond admission; the network-heavy rave watchdog retains a separately asserted 180-second payload floor. The runner requires `setsid` plus `setpriv --pdeathsig` before starting an enforced payload, owns the resulting process group, and yields without work if complete containment is unavailable. The kernel parent-death signal reaches the group leader if the heartbeat owner dies abruptly; the child verifies the expected parent after arming, and TERM is escalated to a group KILL after the bounded grace period. Deterministic process tests cover pre-arm death and a TERM-ignoring descendant independently from heartbeat-partition fencing.

An active owner holds a 90-second lease and heartbeats every 30 seconds. All lease times, queue ages, expiry, and stale-owner decisions use the database clock, never a contender timestamp. Granting advances a per-lane monotone fencing token; heartbeat and release require the exact owner, run, token, active state, and unexpired lease. A missing heartbeat response, expired/stolen token, or guardrail rejection terminates the payload process group; the next grant receives a greater token. Queue heartbeats older than 120 seconds and active leases past expiry are recovered inside the next short write transaction. Payload work remains chunked/resumable and never shares the lease transaction.

Admission and renewal give public traffic priority in this order: current harmless `select` latency above 250 ms yields as `direct-read-latency`; a non-`ok` or older-than-20-minute `db` snapshot yields as `database-health`; a non-`ok`, older-than-20-minute, or above-500-ms `web` snapshot yields as `public-latency`. Missing stored health rows do not deadlock a fresh deployment. The `health.snapshot` writer is the recovery probe: it still must pass the current harmless database read, but it does not gate on its own previous stored snapshot, because otherwise no writer could clear a recovered degraded row. While stored health blocks ordinary writers, the eligible FIFO contains only recovery probes, so the oldest recovery probe can pass older health-blocked queued writers but can never pass an active writer; blocked rows remain durable in their original order. The same eligibility predicate guards both fencing-token advancement and queued-to-active transition. As soon as stored health is healthy, every conflicting queued writer is eligible again and the original FIFO resumes, so neither a later health snapshot nor an ordinary writer can leapfrog older work.

Each server turn emits one bounded `database.admission` structured event with contender, owner/run, operation, physical access class, heavy-reader consumption, queue age, wait, hold, yield reason, recovery, enforcement mode, and outcome. The unit runner emits the corresponding lifecycle event to journald. The ordinary fleet run ledger continues to own payload exit/result evidence in the separate telemetry database, so admission-table contention cannot make the payload ledger share the primary writer it diagnoses.

Every externally retryable or timeout-prone logical mutation selected for receipt coverage carries an operation key and writes its receipt atomically with its effect. An unknown response is reconciled before replay. Projections define a source of truth, transactional maintenance where practical, an idempotent rebuild, and a drift audit. Backfills are resumable, chunked, observable, and reversible until verified; schema expansion, shadow/backfill, cutover, and contraction remain separate phases. The operation registry, receipt path, due-work and public projections, admission coordinator, artifact protocol, Sonar local replica, device derivation, and their fail-closed completeness tests implement those laws.

### Retry disposition and atomic receipts

[`database-operation-registry.ts`](../apps/web/src/lib/server/database-operation-registry.ts) is the executable retry-policy inventory for every recurring timer/CLI database operation and every incident mutation it names. A write is exactly one of `receipt-backed`, `replay-safe-idempotent`, or `deliberately-non-replayable`; reads and no-database work are `not-applicable`. Each disposition carries a checked-in mechanical source plus its proof or bounded reconciliation rule, and the completeness test fails when a write or incident lacks one. A replay-safe label does not authorize the generic database retry wrapper to retry writes: the owning caller must still use the registered stable-state proof. A deliberately non-replayable path must inspect its bounded queue item, artifact identity, or external publication state instead of blindly repeating the action.

`health.snapshot` is the sole receipt-backed operation. Each caller carries a bounded stable producer ID and derives `health.snapshot:<producer>:<canonical-UTC-at>` after normalizing the accepted timestamp to UTC. The caller and Worker compute the same SHA-256 digest over the normalized snapshot plus producer using canonical JSON with sorted object keys and stable array order; the Worker rejects a caller digest or operation key that does not match before executing the effect. Contract-bound operation keys use a printable ASCII grammar whose character cap equals the runtime UTF-8 byte cap. `operation_receipts.operation_key` is the unique logical identity. An `accepted` row has no result; a terminal `committed` or `rejected` row has a bounded stable `result_identity`, canonical `result_json`, and terminal timestamp. The snapshot's status rows, transition events, check samples, status-event/sample pruning, spent `rate_limit_counters` pruning, and terminal receipt share one libSQL write transaction. A rollback therefore leaves neither effect nor a false terminal receipt.

Same-producer/same-timestamp retries retain the same key. Same-key/same-digest replay returns the stored terminal result without running the effect. Same-key/different-digest is a conflict. An accepted receipt is in progress. Any transaction failure, transport failure, or ambiguous 5xx response (including 524) performs digest-bound reconciliation before the caller may decide what to do: terminal returns the original result, absence under the enabled health cutover is safely retryable, accepted remains in progress, and conflict, rejection, lookup failure, or an unreadable cutover never authorizes replay. Duplicate callers converge through the operation-key primary key and the same reconciliation path.

The `health_snapshot_receipts_enabled` setting is default-off and opens only for the exact value `true`; missing or malformed values keep the legacy writer, while a failed flag read fails closed because the Worker cannot safely select a write path. Flag-off accepts the legacy keyless body and ignores complete validated receipt metadata after verifying it. Flag-on rejects keyless writes. The healthcheck, Hermes pin-watch, sonar freshen, SSH freshen, and rave watchdog callers carry producer, key, and digest before the flag opens, so schema expansion, initialization/shadow, and caller cutover remain independently deployable. The legacy path remains the rollback path until contraction.

Inspection is available through `fluncle admin receipts get <operation-key> [--json]`. Inspection and digest-bound read-only reconciliation (`fluncle admin receipts reconcile <operation-id> <operation-key> <request-digest> [--json]`) use bounded POST bodies, never path or query coordinates. The keyed GET route is removed; the minimum compatible caller is commit `a58f9441088728efa03f8745813ac17425229c18`, or any build containing its POST inspection and reconciliation cutover. Before the contraction leg is deployed, the operator must prove every deployed CLI, healthcheck, pin-watch, Sonar freshen, SSH freshen, and watchdog caller meets that floor; rollback below it requires restoring the keyed route before rolling a caller back. The stale-key Sentry scrub remains as defense for delayed telemetry or an overlooked caller. `fluncle admin receipts repair --stale-before <ISO> [--limit 50] [--json]` is the explicit operator-only mutation: it rejects at most 100 accepted rows strictly older than the supplied fence. These commands return bounded state, operation ID, stable result identity, and timestamps, never the request digest or stored result payload. The Worker disables Sentry request-body capture. Reconciliation and repair emit low-cardinality spans and structured evidence containing the operation ID, outcome, state, and aggregate counts only; operation keys, digests, request/result bodies, secrets, and private topology never enter Sentry or logs.

### Due-work projection

Recurring track and graph-entity selectors materialize eligibility in `due_work`. One physical `work_kind` owns each eligibility and priority policy, while `subject_type` and `subject_id` identify the source row. `ready` rows are claimed through the ready-order index; future retry windows remain `scheduled` until a bounded promotion; leased rows carry an owner, token, and expiry; and `repair` rows are transactionally coupled proof that a source mutation still needs projection repair. An absent or terminal source has no projected row.

The source tables remain authoritative. Each registered definition provides a primary-key-ordered bounded reader, a pure evaluator, and an explicit source-version token. Rebuild checkpoints make zero-row, interrupted, and completed runs idempotent. A new generation upserts the rows it observes and deletes only older-generation rows after the source walk completes, while concurrent repair markers survive that contraction. Drift comparison reads bounded source and projection pages and reports missing, unexpected, and field-mismatched rows without mutating either side.

The local backfill command is `bun run --cwd apps/web db:backfill-due-work`; it rejects every non-local database URL before opening a client. Backfill and shadow comparison populate and verify the projection without changing selector behavior. The completed rebuild also caches the catalogue-rank fingerprint and finding counts, so a projected empty rank tick can preserve its response contract through one KV probe without recomputing the live corpus. The `track_work_due_cutover_enabled` setting opens runtime reads only for the exact value `true`; missing, malformed, and failed setting reads stay on the legacy path. With the flag open, every recurring consumer repairs a bounded marker page, promotes elapsed retries, and reads the maintained ready-order index without falling back to a source-table scan or second count. The legacy selectors remain as the ordered default-off rollout and rollback path; the release manifest forbids contracting that compatibility before the attended cutover evidence exists.

Eligibility-changing writers append a subject repair marker in the same libSQL write transaction as their source mutation. A bounded consumer pass expands generic markers into the registered physical queues in sequential set-based batches of at most 50 source subjects, clearing each source marker in the same version-guarded transaction, then repairs only the queue being read from the authoritative source rows. A physical repair page resolves its bounded subject set through one indexed source query and flushes the page as at most one set-based guarded upsert plus one set-based guarded delete; each candidate retains its source-version race guard and the same transaction advances the audit fence. The checked-in producer inventory parses every mutation site across the base and satellite eligibility tables, proves that the marker shares that site's write batch or explicit transaction, and follows statement builders through every callsite to a coupled producer. Exact SQL-fingerprinted dispositions cover serialization, fixtures, and fields no evaluator consumes, so another mutation in an already-reviewed file still fails closed. Rebuild and drift audit remain the independent convergence proof.

### Crawl and public shadow projections

The crawler's separate `crawl_due_work` projection preserves its two-lane law: up to `ceil(limit / 2)` release slots use the storable-first release index, then the general breadth-first index fills the rest. Pending nodes are ready, retryable failures are scheduled at their failure-scaled due time, and every drained allowed MusicBrainz artist becomes a daily tail subscription once its allow has no unstamped rearm request. Claims carry an owner, token, ordered position, and expiry; promotion, lease reaping, direct node repair, and label/artist-rule fanout are bounded by the projection's partial and fanout indexes. The source frontier remains authoritative. The `crawl_due_cutover_enabled` setting is default-off and opens only for the exact value `true`; missing, false, malformed, and failed reads retain the unchanged legacy selector. An open pass runs forward seed/rule maintenance first, drains only bounded repair pages, promotes retries independently and tail-rearms at most the oldest ten due stale artists, claims the maintained two-lane order with one pass owner/token and a lease longer than the bounded HTTP pass, and hydrates only the claimed frontier primary keys in `claim_position` order. Stale-artist promotion atomically moves the authoritative row and its due row and preserves the pass counter even when the caller claims zero nodes, so the open path never executes the legacy double artist-rule probe or its sort. Success or failure settlement transactionally verifies the node/token lease, mutates the authoritative frontier row, deletes only that lease, and appends the exact repair marker; a stale token changes nothing and contributes no pass counters.

The public shadow projections materialize only the stable global facts: total tracks; exact non-NULL literal `substr(release_date, 1, 4)` and key buckets; the invalidation epoch for the default `release_date DESC, track_id DESC` hub order; and artist qualification. Qualification counts one certified finding per credited artist and enabled-label credits as two half-units for a primary artist or one for a remixer, with membership at any certified finding or six half-units. Per-track memberships and per-track/artist contributions retain the old side of every delta, label rulings fan out through `tracks_label_id_idx`, and repair epochs prevent a newer source marker from being consumed by an older repair.

The public invalidation contract follows source dependencies, never subject type. `public_aggregates` depends only on track existence, `tracks.track_id`, `tracks.release_date`, and `tracks.key`. `artist_qualification` depends only on `track_artists(track_id, artist_id, role)`, finding existence by `findings.track_id`, `tracks(track_id, label_id)`, and `labels(id, seed_state)` where the exact `enabled` value qualifies. The closed producer-impact registry covers every producer in `DUE_WORK_PRODUCER_INVENTORY` exactly once as aggregate-only, artist-only, both, neither, or one of three justified dynamic policies; missing, duplicate, unknown, or unjustified entries fail closed. `track-update` targets aggregates only when `key` is supplied, `label-seed-state` targets artist qualification only when a ruling supplies `seed_state`, and `hub-entity-relink` targets artist qualification only for label relationships. Static producers cannot override their registered impact.

The shadow maintenance contract remains a transactionally coupled rail beside independent legacy due-work eligibility maintenance. New-track and key writers target only aggregates; finding-existence certification, artist edge or role changes, and label link or enabled-state ruling changes target only artist qualification; `publish-track`, which inserts both its track and finding, targets both. Rank and capture metadata, anchors, covers, bios, artwork, notes, identity metadata, maintained hub counts, and social or publish bookkeeping target neither public projection, so they create no public repair and advance no public source epoch while still retaining their legacy source-repair marker. Explicit targets are validated against their subject family, selection markers preserve the same dependency policy, guarded source no-ops append no public work, and the synthetic catalogue-rank corpus subject never enters a public projection. For both targets the fixed statement order is legacy marker, aggregate epoch, aggregate repair, artist epoch, artist repair; every `changes()` admission gate, race token, bounded fanout, and rollback boundary remains intact. Every `crawl_frontier` mutation in the crawler appends the exact node repair in the same bounded write batch, and label seed/scope plus artist-rule verdict/rearm writes append indexed label-slug or artist-MBID fanout markers in their source transaction. The source tables remain authoritative throughout shadow operation.

Both projection families rebuild by stable sorted IDs with durable generation checkpoints, preserve live repairs newer than the rebuild start, compute exact source/projection digests, schedule only bounded drift repairs, and expose legacy shadow comparators. A logical rebuild page carries at most 500 tracks, while source reads and writes execute in 50-track subpages and artist plans are packed under a fixed statement ceiling; the durable cursor moves only after every subpage commits, and execution-time live-generation guards preserve a repair that lands after the page snapshot. Once the source walk ends, bounded production cleanup persists the last ordered primary-key coordinate and inspects at most the requested limit of consecutive rows per call; stale-generation predicates are evaluated only inside that page, and completion follows a subsequent empty page. Default hub anchors are rebuilt deterministically outside request time into generation-addressed page shards. Each call stores only anchors discovered in that bounded source page plus a strictly validated constant-size cursor; malformed or internally inconsistent state first purges its partial generation through the same bounded primary-key cursor, then restarts from source. The validity row publishes the generation only after the complete sharded document passes the runtime parser, records the previous valid generation as the explicit rollback generation, and cursor-cleans every other superseded generation after publication. A complete anchor document makes each numbered default page an exact strict `(release_date, track_id)` suffix over `tracks_release_date_track_id_idx`; source traversal persists an explicit non-NULL/NULL phase, uses a row-value indexed range for resumed non-NULL pages and a `release_date IS NULL`/`track_id` range for NULL pages, so neither ties, restarts, nor the phase boundary can force a corpus scan or temporary sort. Arbitrary filtered public queries deliberately remain indexed source queries rather than a combinatorial aggregate cube. The `public_projection_cutover_enabled` setting is default-off and opens only for the exact value `true`; every other value or settings read failure retains the exact legacy query. Aggregate reads are usable only when the `tracks` state is `complete`, `aggregate_epoch = source_epoch`, and no `public_aggregates` repair exists. Artist qualification is independently usable only when its `artists` state is `complete`, `projection_epoch = source_epoch`, and no `artist_qualification` repair exists. Default release-hub anchors additionally require the exact hub/clause address, the current anchor format, a non-empty generation matching aggregate state, `order_epoch = release_hub_order_epoch`, a complete page-boundary document for the projected total, and defensively valid JSON. Usable projections serve the default total, literal release-year and key buckets, qualified artist IDs, and default-hub anchors; filtered hub reads and every unusable/error case keep the legacy source query. Public requests only probe readiness and read projections; recurring repair authority is narrowed separately below.

Source mutations append exact public repair debt transactionally. After the shared public cutover opens, the admission-wrapped `fluncle-projection-maintenance` host sweep reads bounded status every five minutes and gives each affected public family at most four repair calls of 500 subjects; public aggregate repair continues through the bounded anchor cursor after marker debt drains. A dark cutover and an open idle cutover issue no mutation. The agent token can read status and repair only `public_aggregates` or `artist_qualification`; rebuild, audit, track/crawl targets, and every cutover mutation remain attended operator work.

The local command is `bun run --cwd apps/web db:backfill-shadow-projections`; it resumes existing generations by default, accepts `--new-generation`, `--audit-only`, `--limit`, and `--repair-limit`, and refuses hosted or non-loopback database URLs before opening a client.

Production convergence uses the authenticated control plane, never the local backfill scripts or an interactive SQL client. The recurring agent exception is limited to the bounded status read and public-family repair described above; every other control remains operator-only. `fluncle admin projections get --json` returns fixed-schema backlog, rebuild, repair, digest, epoch, anchor, cutover, and `readyToOpen` evidence for track due-work, crawl due-work, public aggregates, and artist qualification. Growing backlog and repair totals are capped index probes represented as `{ "count": number, "truncated": boolean }`: `truncated: false` makes the count exact, while `truncated: true` makes it an observed lower bound and readiness still uses a bounded empty/non-empty proof. `fluncle admin projections advance --target <track_due_work|crawl_due_work|public_aggregates|artist_qualification> --action <rebuild|repair|audit> --limit <1-500> --json` still advances exactly one durable page by default. An optional `--max-steps <1-100>` makes the CLI issue that many sequential requests at most, stopping as soon as the server reports `complete: true`; `--limit` remains the page size for each request, while `--max-steps` is the client request budget. Multi-step calls omit the global status snapshot from each intermediate response, use only target-local indexed preconditions, and fetch the global evidence exactly once after the serial budget completes, so every mutation keeps its hosted-safe bound without repeating the complete projection suite after every durable page. The default one-step operator contract remains status-bearing for existing callers; the statusless response is private to the bundled CLI's multi-step control path. The JSON result keeps that terminal status and adds exact aggregate `steps`, `processed`, and `scheduled` totals; when the budget ends before completion, `complete` remains false and the server-owned cursor makes the next invocation resumable. Rebuild cleanup, public hub-anchor extraction, superseded anchor cleanup, and exact audits retain their own cursors, so no request hides a corpus scan. Public anchor extraction remains independently capped at 100 rows per transaction. Rebuild and repair invalidate prior audit proof. Track and crawl repair consumption also advances a persistent monotonic audit fence in the same transaction as the guarded marker drain, so a source mutation cannot leave a previously matched digest reusable after its repair debt returns to zero. An audit runs only while the relevant cutover is dark, the rebuild is complete, and repair debt is zero. Public aggregate evidence is fenced by source epoch, aggregate generation, and release-hub order epoch, and its exact sharded-anchor lane compares every canonical source boundary's identity, key, page, and order with the published current generation. A digest mismatch returns a conflict and the next rebuild starts a fresh generation while source tables remain authoritative.

Flags are changed only through `fluncle admin projections set --target <track_due_work|crawl_due_work|public_projections> --enabled <true|false> --json`. An enable request uses one conditional database write that re-proves the matching current audit digest and its current source fence, zero repair debt, complete rebuilds, and, for public projections, both independent epochs plus the exact audited generation/order fence and a runtime-valid current anchor generation; a zero-row write fails closed if any proof changed after the preceding status read. A disable request remains an unconditional rollback write and always succeeds. The settings remain default-dark, runtime reads retain the legacy fallback for every absent, false, malformed, unreadable, or unusable projection state, and no operator endpoint accepts SQL, table names, database coordinates, or credentials.

### Mixable artist projection

The mix artist picker reads `artists.rankable_track_count`, the exact number of credited tracks whose key is non-NULL and whose embedding mirror is present. Key and embedding transitions move every credited artist in the same transaction, artist-edge writers carry the source track's rankability into their counter delta, guarded embedding clears run an exact difference-only artist repair after source-maintenance marker accounting, and the hub-count reconciliation pass repairs out-of-band drift. The partial `artists_mixable_order_idx` serves the exact `track_count DESC, name ASC` order directly from the artist table, so the request path never groups or sorts the growing `track_artists` graph.

The migration adds only the zero-defaulted counter and its partial index. Post-deploy activation is a no-op when the readiness fence is already complete because production writers maintain the counter transactionally; an absent, dirty, or interrupted fence instead keeps reads on the legacy source query while activation keyset-reconciles bounded artist pages and repeats full passes until one complete stabilization pass observes zero corrections. Interrupted resumes restart the current pass so its zero-correction proof remains whole. Reads re-check the fence on every request so fallback remains immediate and use the maintained index only after stabilization.

## Test-data laws

Raw production data and identifiers never enter the repository or CI artifacts. Fixtures are deterministic and synthetic while preserving audited cardinality, selectivity, null distribution, fan-out, and backlog distribution. Exact 1×, 2×, and 4× profiles derive only from the checked-in manifest. Local SQLite/libSQL is mandatory for correctness and deterministic plan tests. Hosted Turso is a separate scratch-only replay because local behavior is not hosted performance evidence.

Mutation contracts must operate only on a disposable harness database, use stable synthetic keys, and be idempotent or reset their fixture between samples. A timing contract must warm up explicitly, use deterministic iteration counts, report every distribution, and retain result/affected-row counts so a fast empty or wrong query cannot pass. A plan assertion must name every growing table and narrowly justify any allowed scan. Fixture changes update the manifest contract and determinism/selectivity tests in the same change.

## Local and hosted are different

Local libSQL is the correctness oracle, not a hosted-performance substitute. Four known divergences are mandatory interpretation context:

1. A query vector bound as text has a hosted probe-binding cliff that local `sqld` does not show. At 100,000 rows the observed hosted p50 was 26,700 ms for text versus 1,883 ms for a raw BLOB, while both were 175 ms locally. Bind vectors as raw BLOBs.
2. Do not build `libsql_vector_idx` on a populated table. Hosted creation can block writes while local creation can yield an empty index. Use an exact `vector_distance_cos` scan behind a B-tree prefilter.
3. The response cap fails loudly above 10 MiB in local development, while hosted queries can continue until they exhaust the Worker's 128 MB isolate. Rank growing vector columns in SQL instead of returning them for application-side ranking.
4. A flattened CTE fanned out by `UNION ALL` branches or outer cross-join rows is re-executed per branch or row. Fold multi-probe distances into one select expression; materialize bounded pair scans and pin the small findings relation as the driver.

Any query scanning a table that grows with the archive needs an attended hosted scratch replay before anyone claims that it scales. That replay confirms planner and network behavior; it never targets production or development databases.

## Client bounds and mixed-load evidence

`@libsql/client`'s remote HTTP default is 20 operations per client, and `concurrency: 0` also resolves to 20. Local `:memory:` and `file:` clients ignore that option. The explicit numbers below bound one client instance; they do not limit aggregate Workers, requests, isolates, processes, timers, or fleet units.

| Client class                         | Bound | Rationale                                                                                                                                                                                                                                         |
| ------------------------------------ | ----: | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Primary Worker client                |     4 | Preserves ordinary route fan-out while preventing one logical caller from issuing 20 remote operations. Known request fan-outs include three, five, and seven reads; four is the explicit compromise to test rather than a global capacity claim. |
| Fleet telemetry client               |     3 | The ledger reader intentionally performs page, rollup, and count concurrently; inserts remain a single statement.                                                                                                                                 |
| Catalogue public-entity count script |     3 | Its only deliberate direct-client fan-out is three concurrent counts.                                                                                                                                                                             |
| Maintenance/operator scripts         |     1 | One-shot migration, backfill, inspection, and destructive tooling is sequential or explicitly batched.                                                                                                                                            |
| Hosted benchmarks                    |     1 | Measurement must not accidentally manufacture same-client parallel load.                                                                                                                                                                          |
| Seed clients                         |     1 | Fixture and seed writes are ordered, chunked batches.                                                                                                                                                                                             |
| Readiness and smoke clients          |     1 | Readiness, migration, and smoke steps are serial.                                                                                                                                                                                                 |
| Local HTTP helpers                   |     1 | Local server setup and browser fixture paths are serial even though a local engine may ignore the transport option.                                                                                                                               |
| File clients                         |     1 | Restore, derivation, and other file-backed paths are serial; this records intent where the local driver ignores the option.                                                                                                                       |
| Test clients                         |     1 | Tests declare their expected shape and use a separate controlled scheduler for concurrency evidence.                                                                                                                                              |

The deterministic mixed-load contract starts one held 100 ms heavy reader, three 5 ms public reads, and two serialized write batches on the primary four-slot model. It records per-class queue and latency p50/p95/p99 plus observed maximum concurrency. The public reads start while the heavy reader is held, and write batches do not overlap. Replacing the primary bound with one makes the test report the avoidable public convoy; replacing it with the library default of 20 makes the explicit-bound check fail.

This is per-client evidence only. The mixed-load simulator's write lane models SQLite transaction serialization inside that scenario; it must not be described as cross-unit admission evidence. Cross-unit FIFO fairness, writer/heavy-reader leases, fencing, guardrail yield, process containment, and recovery are proven separately by the admission model and source-shape checks against the implemented coordinator.

## Telemetry and privacy vocabulary

Database query spans and fleet run records share a bounded vocabulary: `operation_id`, `access_class`, `release`, `attempt_count`, nullable `batch_count`, `duration_ms`, and `outcome`. Operation IDs are stable, validated, low-cardinality identifiers with a deterministic sanitized fallback. Access class is exactly `read`, `write`, or `heavy-read`. Release identifies committed code, attempts count actual attempts, batch count is null when unknowable, duration is measured elapsed time, and outcome is exactly `success` or `failure`.

SQL arguments, interpolated literals, raw rows, names, email addresses, track or user identifiers, secret values, tokens, hostnames, URLs, ports, and private topology never enter that vocabulary. `db.query` remains the Sentry operation, and `sendDefaultPii: false` remains mandatory. Query descriptions are normalized grouping labels rather than raw SQL when literals could leak. The runner's JSON contains plan text and aggregate counts only for registered synthetic or reviewed statements; a new contract must audit its statement and metadata before registration.

## Run and interpret the harness

Run the lightweight local suite, which materializes only a 512-track derivative:

```bash
bun run --cwd apps/web db:performance --profile 1x
bun run --cwd apps/web db:performance --profile 2x
bun run --cwd apps/web db:performance --profile 4x
```

Select or list contracts independently:

```bash
bun run --cwd apps/web db:performance --list
bun run --cwd apps/web db:performance --profile 2x --contract fixture.frontier-pending-claim
```

An exact local profile is explicit because it may write millions of rows while remaining memory-bounded:

```bash
bun run --cwd apps/web db:performance --profile 1x --full-fixture
bun run --cwd apps/web db:performance --profile 2x --full-fixture
bun run --cwd apps/web db:performance --profile 4x --full-fixture
```

Exact full-fixture local runs require `sqld` on `PATH`. The harness follows the repository's `turso dev` lifecycle pattern but launches the local libSQL server through its own offline supervisor, avoiding the Turso launcher's version check. It uses a fresh database on an ephemeral loopback port, requires a per-attempt Ed25519-signed token, proves readiness with a bounded authenticated `SELECT 1` plus sidecar ownership check, and retries a bind collision on a fresh port. Every HTTP request and exact-profile process has an absolute deadline. The HTTP client performs fixture and contract work, and the release runner places its database scratch outside the detached candidate source. Normal close, interrupt/termination, or abrupt benchmark-owner death causes the supervisor to terminate the sidecar process tree and remove the database directory; the supervisor owns and drains bounded log tails rather than forwarding into owner pipes, and parent cleanup retains a TERM-to-KILL process-group fallback. Isolation, readiness, census, and cleanup fail closed. Database pages therefore remain resident in the sidecar rather than being counted as application RSS, matching hosted Turso's process boundary; heap, raw client-process RSS, and wall thresholds remain hard and no baseline subtraction or missing-sample coercion is allowed. Lightweight non-`--full-fixture` commands retain the 512-track embedded fixture so CI stays small.

For one clean release proof, run the exact profiles and the real local component suites through the non-production release runner:

```bash
candidate_commit="$(git rev-parse --verify HEAD^{commit})"
bun run --cwd apps/web db:performance:release --candidate-commit "$candidate_commit"
```

The release runner executes sequentially and never accepts hosted or operator gates. It passes an allowlisted environment to child processes without credential values; it does not provide OS-level network isolation, so the local/offline command set is an execution contract rather than a sandbox. It first requires a clean invocation checkout, resolves the candidate, and creates a detached candidate worktree in a temporary execution root. Every proof child runs from that detached root, while the release artifacts, database scratch, and Cargo target remain outside its source directory. Before any proof child runs, the detached root receives its own dependency tree from a bounded `bun install --offline --frozen-lockfile --ignore-scripts --backend=copyfile`; an unavailable cache, changed lockfile, failed install, missing `node_modules`, or deadline is a no-go. Copy-file installation keeps the candidate independent of both the invocation worktree's mutable `node_modules` and mutable links into Bun's cache, while the frozen lock supplies package-integrity coordinates. The runner reuses its own Bun executable for install and Bun child commands, and the manifest records the exact install method, candidate `bun.lock` SHA-256, and Bun version. Live edits to either invocation source or invocation dependencies after isolation therefore cannot affect proof execution. The runner records the actual candidate commit, source-tree cleanliness, committed-tree hash, and index hash at detached execution start, immediately before and after every child, and at completion; the candidate defaults to the invocation `HEAD`, while `--candidate-commit` lets an attended run pin the intended full SHA explicitly. Dirty invocation evidence, unavailable or changed detached source, cleanup failure, or candidate mismatch is a machine-readable no-go even when every command passes. Worktree setup and removal, dependency installation, and filesystem cleanup are bounded, and cleanup failure is retained in the final verdict. Every child has an absolute command deadline and runs in an owned process group that receives TERM and then KILL if it does not exit. It runs exact full-fixture SQL at 1×, 2×, and 4×, then the actual dominant-regression inventory, operation-registry classification, rollback cutovers, mixed-load, admission schema/enforced/shadow, operation-receipt schema/ambiguity/restart, public-projection convergence, device derivation/mirror/scaled convergence/resource, and Sonar Rust/scaled delta-to-full-local-rebuild suites. The fast Sonar/device/admission checks embedded in each SQL report remain honest source-shape models; the separately captured component processes are the release evidence that executes those implementations.

By default, artifacts land under the operating system's temporary directory at `fluncle-db-performance-release/<run timestamp>/`. The destination must be new and outside the invocation repository; no Git pathspec is built from it. `profiles/{1x,2x,4x}.json` are the complete validated schema-version-five reports, `logs/<command>.{stdout,stderr}.log` preserves every child process, and `release-manifest.json` is the root evidence envelope: it records detached execution mode, candidate-local dependency install method, installer version and candidate lock hash, source freshness, commands and their deadlines, portable execution-root label plus relative working directories, exact expected and database-censused cardinality, category coverage, duration, exit status, portable relative artifact filenames, every child profile/log artifact's SHA-256 and byte size, the candidate commit in each profile envelope, warnings and thresholds, and the final `pass` or `no-go` verdict. Its `artifactRoot` is the SHA-256 of the candidate plus the complete sorted child-artifact descriptors; the manifest deliberately does not claim to hash itself. No absolute local source, dependency, scratch, or artifact directory enters the manifest. Pass `--output-dir <new-directory>` to choose another empty destination outside the repository. The runner exits nonzero for an in-repository artifact destination, dirty or mismatched invocation source, detached setup or cleanup failure, changed execution source, any failed or timed-out child, malformed profile report, inexact census, false `report.passed`, artifact-integrity drift, or missing/failed required category; a test command that has no JSON reporter is still represented by its exit status and duration with both logs retained while the top-level manifest remains JSON.

Each standalone SQL command writes one schema-version-five JSON document. `report.passed` is false for any required budget, correctness, resource, index-audit, census, or plan-law failure. It includes distributions, equivalence, queue convergence, mixed-client load, admission, ambiguity, projection, Sonar/device source-shape model checks, database process-boundary evidence, and process resource samples. `resources.availability` and `sampleSource` make missing measurements explicit; no missing sample is coerced to zero. Exact local reports name `process.memoryUsage.isolated-local-libsql-client`, `local-sidecar-process`, and `benchmark-client-process`; the release validator rejects embedded or adjusted evidence. At 4×, only the aggregate contract-phase `resources.peak.wallDurationMs` threshold becomes a warning curve. Projection contracts explicitly require 4×, so their p95 timing budget remains a hard failure there, as do correctness, invariants, plan violations, heap, and RSS limits. Inspect `criteria`, `durationMs`, `queueMs`, `resultRowCount`, plan `details`, `fullScans`, `tempSorts`, validation failures, `database`, `resources`, `indexAudit`, the fixture's `writeDurationMs`, post-write `census`, and `exactProfileCardinality` before comparing runs. Exact local fixture construction and census are reported but deliberately outside contract-phase wall and Worker-memory budgets; the sidecar owns its database resident pages while the measured client retains the same hard Worker/application thresholds.

## Add a contract

Register a stable lowercase ID in [`contracts.ts`](../apps/web/scripts/db-performance/contracts.ts), choose the matching work class, set deterministic warm-up and measured iteration counts, and provide either a SQL statement through `sqlContract` or one custom observation callback. A SQL contract adds its `EXPLAIN QUERY PLAN` statement and names growing tables, forbidden temporary sorting, required driver/index details, and any narrowly allowed scan. Its correctness hook asserts ordered values or a stable digest where needed and always asserts result cardinality. Add a focused test that demonstrates the intended result and that the old or malformed plan fails.

If the contract needs new fixture state, extend the one manifest/generator rather than adding a bespoke seed script. Preserve stable synthetic identifiers, exact distributions, chunking, and the 1×/2×/4× multiplication law. Do not add a production index, rewrite product SQL, or copy a row from any live database as part of a harness change.

## Operator-gated hosted replay

Hosted replay is inert unless `--hosted`, `--operator-approved`, and `--preseeded-fixture` are all present. Invalid combinations fail before the runner reads `FLUNCLE_DB_PERF_SCRATCH_URL` or `FLUNCLE_DB_PERF_SCRATCH_TOKEN`. It rejects missing values, local/file URLs, embedded credentials, and targets whose identifiers look like production, development, local, or the live product. The hosted runner creates no database or infrastructure. Its bootstrap performs no fixture reset, schema creation, or data writes: it first verifies the imported fixture's format/profile/integration-base/counts/schema identity, then runs the exact post-import census as one read statement per request over deterministic windows of at most 50,000 fixture rows plus separate rowid underflow/overflow sentinels. Ordinary tables use rowid windows; the wide embedding table uses its covering `track_id` primary-key index so counting never traverses the 4,096-byte embedding payloads. Registered contracts execute only after those proofs and may mutate their harness-owned rows, which is why every profile requires a fresh disposable scratch database.

The manifest's exact 1×/2×/4× censuses make 90/124/202 bounded requests respectively. The hosted whole-process deadline adds a positive scale-matched bootstrap allowance for those round trips; it does not loosen the fixed 60-second deadline on any individual request or any contract budget.

Hosted replay treats only the aggregate registry `resources.peak.wallDurationMs` threshold as a warning curve at every scale because it accumulates remote round trips across the complete contract set rather than measuring one route or queue SLO. The 60-second per-request timeout, bounded absolute profile process deadline, correctness and plan checks, aggregate heap/RSS limits, and every per-contract SLO required for the selected profile remain hard failures; no contract budget changes in hosted mode. Exact-local 1×/2× release evidence keeps resource mode `required`; exact-local 4× keeps its existing bounded-memory/timing-warning mode.

Build the deterministic import artifact locally into a **new absolute directory outside the repository**. The materializer refuses overwrite, uses the existing schema and generator, proves the exact census and `quick_check`, writes identity only after those proofs pass, checkpoints and closes the file, rejects WAL/SHM residue, and emits a manifest containing the database SHA-256, byte size, and identity. `PERFORMANCE_FIXTURE_FORMAT_VERSION` must increase whenever generated row or distribution semantics change, even when schema, counts, and integration base remain unchanged.

```bash
bun run --cwd apps/web db:performance:materialize \
  --profile 1x \
  --output-dir /absolute/new/outside-repo/profile-1x
```

Repeat with a different new output directory for `2x` and `4x`. Each profile requires a fresh disposable hosted database; never reuse a larger profile's target for a smaller proof. The authenticated Turso database creation and file-import command, concrete database topology, credentials, and any paid infrastructure effect belong only in the private attended operator harness, not this public repository. The import step must use the materialized `fixture.sqlite3` unchanged. Neither the materializer nor hosted replay runs `ANALYZE` or `VACUUM`, preserving the audited hosted planner conditions.

```bash
FLUNCLE_DB_PERF_SCRATCH_URL='libsql://<scratch-database>' \
FLUNCLE_DB_PERF_SCRATCH_TOKEN='<scratch-token>' \
bun run --cwd apps/web db:performance --profile 1x --hosted --operator-approved \
  --preseeded-fixture
```

The presence of credentials alone does nothing on normal/local/CI paths, and approval alone is rejected. Never use a production or shared development URL, never run the gate unattended, and never treat local timings as a substitute when the hosted confirmation remains pending. The public command above is only the post-import verification/proof step; it does not authorize or describe the authenticated import itself.

The older per-item `apps/web/scripts/bench-db-scale.ts` proof engine also mutates its supplied database by applying migrations, seeding synthetic rows, and trial-dropping indexes. Before that script constructs a client, `SCRATCH_TURSO_DATABASE_IDENTITY` must exactly match the canonical host parsed from `SCRATCH_TURSO_DATABASE_URL`; a production/development/local denylist remains defense in depth rather than the authority. Use placeholders in shared instructions and supply the real scratch identity only in the attended shell:

```bash
SCRATCH_TURSO_DATABASE_URL='libsql://<scratch-database-host>' \
```
