# Database performance contract

This document is the canonical, public contract for measuring Fluncle's database work. The implementation lives on the normal product release path. Neither the harness nor a passing local result authorizes a deployment, production query, hosted database creation, paid action, credential use, timer change, or mutation; operator authorization and the documented deployment workflow still apply.

The harness lives in [`apps/web/scripts/db-performance`](../apps/web/scripts/db-performance). It owns one manifest, one synthetic fixture stream, one extensible contract registry, one runner, and one explicit budget vocabulary. It changes no production table, query, index, projection, or mutation path. The checked-in `perf_*` schema exists only inside a scratch or in-memory harness database.

## Budgets

The registry encodes budgets as assertions and reports p50, p95, p99, maximum, result-row counts, affected-row counts, batch counts, queueing, plan output, and pass/fail. Current and 2× are required where specified. A red required budget is a failure; an average cannot waive it. A 4× timing miss is reported as a warning unless the invariant is explicitly required at 4×, but correctness, bounded memory, and plan laws still fail at every profile.

| Work class                         | Required steady-state contract                                                               |
| ---------------------------------- | -------------------------------------------------------------------------------------------- |
| Public route database spans        | p95 ≤ 250 ms and p99 ≤ 750 ms at 1× and 2×                                                   |
| Public route end-to-end            | p95 ≤ 1 s and p99 ≤ 2.5 s at 1× and 2×                                                       |
| Queue empty check or bounded claim | p95 ≤ 250 ms at 2×                                                                           |

| Device derivation                  | zero repeated production-corpus scans beyond replica synchronization at 1×, 2×, and 4×       |

## Query-plan laws

A request-time or per-tick query must not scan a growing corpus merely to prove an empty queue, compute a count, or select a bounded batch. A bounded claim starts from an index whose leading columns express eligibility, due time, and ordering, or from a maintained work projection whose cardinality follows the backlog. Separate identity keys use separate sargable branches; a `CASE` or `OR` join that defeats every candidate index is forbidden on growing tables. A tiny selective relation such as `findings` must be able to drive its join because hosted Turso provides no production `ANALYZE` statistics for this workload. The same missing statistics make the planner rate an equality or `IS NULL` predicate on any indexed column as selective, however common the value; when a partial index or the primary key is the intended access path, a unary `+` on that column (`+state = 'done'`, `+spotify_uri is null`) removes it from index consideration without changing the predicate, and a plan assertion pins the resulting plan. A partial index serves a statement only when one of its WHERE terms is the same expression as the index's WHERE, with every constant spelled as the same literal: a bound parameter of equal value still lets the plan name the partial index, but the term is then re-evaluated for every index entry, so each entry seeks its table row. `entity-hub-seek.integration.test.ts` pins that difference in bytecode for the entity hub listing indexes. Request-time window sampling, expression grouping over a full catalogue, and repeated `UNION`/`GROUP BY` reconstruction belong in maintained projections or aggregates rather than hot reads.

Every critical contract asserts output correctness and plan shape. The runner records every `EXPLAIN QUERY PLAN` detail and detects a growing-table `SCAN` and `USE TEMP B-TREE`; contracts name the growing tables, allowed exceptional scans, required index/driver details, and whether temporary sorting is forbidden. A revision maximum spanning live event bodies and durable receipts must aggregate each indexed subject-prefix branch before `UNION ALL`, so the outer aggregate consumes bounded branch results; its contract proves the SQL and bytecode shape rather than claiming a timing improvement from `EXPLAIN` alone. Timing is evidence, never the only regression oracle.

Schema-neutral rewrite contracts execute the optimized statement alone during every warm-up and measured iteration, so the latency distribution is the final production statement rather than reference/proof overhead. After every selected contract has finished its mutation-capable work, one terminal read-only phase executes registry plan audits plus each comparison's reference plan, reference result, optimized equivalence result, cardinality check, and index structural proof; this ordering prevents an embedded-driver `EXPLAIN QUERY PLAN` statement lifetime from blocking a later transactional batch while retaining every correctness and plan law. Reports merge terminal evidence only into its owning contract and record exact request counts across warm-ups, measured iterations, terminal plan, and terminal proof without raw SQL. The artist-link fixture includes claimed and unclaimed MBIDs, same-name collisions, name drift, null identity, duplicate credits, catalogue flags, and position ordering; its optimized plan must probe the track primary key plus the MBID and NOCASE-name artist indexes without a growing-table scan or temporary sort. Sitemap finding rows, counts, and entity lastmods must drive from `perf_findings`, probe outward by indexed keys, and preserve the reference count, null, lastmod, and ordered-row results. Sitemap row children for artists, labels, albums, logbook, and archive tracks derive exact current boundaries through fixed-size indexed keyset windows, then read one capped window in their stable slug, sector, or track-ID order; every producing statement must be an index search with no growing-table scan, temporary sort, or offset, and the union of the children must equal the unwindowed membership reference in the same order. The `sitemap.track-window` registry contract runs the production archive-track projection and membership predicate against deterministic cover and outbound-listen evidence, pins the `track_id` seek plus album primary-key probes, and rejects the offset-shaped plan. Findings and galaxies remain the explicit no-migration exceptions because their established orders are not served by an existing index. The shared single-row optional-finding, single-row required-finding, plural identity-reference, and bounded bulk track/Log-ID resolver families each retain their reference output while probing both the track primary key and unique Log-ID index; no consumer may restore the cross-table `OR` shape.

## Mutation laws

Every registry-classified recurring writer and explicitly heavy reader enters `database-admission-runner.sh` except the exact database-independent control-plane set: `health.snapshot`, `ops.pin-watch`, `ops.rave-watchdog`, `ops.sonar-freshen`, and `ops.ssh-freshen`. A mechanical registry/unit test rejects any other classified unit that bypasses admission and rejects any expansion of that exemption set. Those five units execute their essential probes, beacons, rebuilds, verification, swaps, and rollback work directly during a primary-database outage; their optional receipt-backed `health.snapshot` write runs afterward as best-effort recovery telemetry and never authorizes suppressing the essential payload. The coordinator has two global resources (`write` and `heavy-read`) with durable FIFO order by database-clock enqueue time and contender id. A mixed operation such as galaxy clustering owns its physical writer row while consuming both resources; its stored operation coordinate carries a reserved `|heavy-read` resource suffix, so a rolling registry rename or reclassification cannot weaken an already-held lease. That durable predicate is applied symmetrically to active exclusion and oldest-contender selection inside one serialized short transaction. The partial unique index backs each physical lane, while the transaction enforces cross-resource exclusion. At most one admitted background writer and one heavy reader can therefore run, and a mixed contender cannot be passed by a later single-resource contender. Per-firing `RandomizedDelaySec` remains on every classified timer to spread harmless arrival load, but jitter is supplemental and never the concurrency authority.

`database_admission_enforced` in the shared `settings` KV is the remote default-off cutover: only the exact value `true` enforces; absent, malformed, or unreadable stays on the shadow compatibility path. `DATABASE_ADMISSION_FAIL_CLOSED=true` is a second, local default-off readiness gate in each admitted unit's operator environment. Before rollout both are off, so shadow resolves the same committed owner/classification, reads the live queue and guardrails, and emits the same bounded vocabulary without inserting, waiting, stopping, or otherwise changing the sweep. Cutover order is exact: deploy the compatible code, arm the local gate on every admitted host/container unit and verify that shadow firings yield without starting payloads, then set the database flag. Rollback reverses that order: clear the database flag, then clear the local gates. A locally armed firing never starts without an enforced grant, and a firing that has observed enforcement never continues after an unavailable or downgraded heartbeat. This closes an initial-partition bypass without making code deployment itself a behavior change.

Enforced acquisition uses one absolute deadline of at most 120 seconds, caps each HTTP request and poll sleep to the remaining budget, rejects a late grant, then cancels or releases its row so the next timer firing can resume the durable sweep work. Overrides may only reduce that ceiling. Within that budget a transient acquire failure (a request past the `DATABASE_ADMISSION_HTTP_TIMEOUT_SECS` ceiling, a transport error, or a 5xx) is retried on the poll interval rather than forfeiting the tick, because the coordinator's own single-row UPDATE waits behind the database's single writer and a slow answer is the ordinary shape of write contention; the contender is keyed on owner and run id, so the retry finds the row a timed-out request already created and never mints a second one. A window that ends with no coordinator answer at all yields `coordinator-unavailable`; a window that ends after at least one answer yields `wait-expired` with the last admitted reason; a 401, a 4xx, or `database_busy` yields immediately. A transient heartbeat failure is likewise retried on the poll interval while the local lease deadline still stands, and only that deadline or a definitive rejection stops the payload. `DATABASE_ADMISSION_POLL_SECS` defaults to two seconds only when absent; an explicit value must be an integer from 1 through 30, so empty, zero, nonnumeric, and out-of-range values fail validation before the first request. Every committed admitted service passes the standing two-second value explicitly, so the runner does not depend on ambient container configuration, and preserves its prior payload budget beyond admission. The poll interval buys queue-wait latency with coordinator requests: a waiting owner spends one short admission POST — one small serialized transaction — per interval, so halving it halves a queued sweep's expected wasted wait and doubles the request rate of the waiting ticks alone. It is sized against the ledger's measured queue-wait distribution, never raised past what a queued tick's own timeout absorbs. The runner requires `setsid` plus `setpriv --pdeathsig` before starting an enforced payload, owns the resulting process group, and yields without work if complete containment is unavailable. The kernel parent-death signal reaches the group leader if the heartbeat owner dies abruptly; the child verifies the expected parent after arming, and TERM is escalated to a group KILL after the bounded grace period. An independent payload-group watchdog refreshes its local deadline only after a successful acquisition or heartbeat and begins that bounded termination early enough to finish before the 90-second lease expires, including when the heartbeat owner remains alive but is paused. Deterministic process tests cover pre-arm death, a paused owner, and a TERM-ignoring descendant independently from heartbeat-partition fencing.

An active owner holds a 90-second lease and heartbeats every 30 seconds. All lease times, queue ages, expiry, and stale-owner decisions use the database clock, never a contender timestamp. Granting advances a per-lane monotone fencing token; heartbeat and release require the exact owner, run, token, active state, and unexpired lease. A missing heartbeat response, expired/stolen token, or guardrail rejection terminates the payload process group; the next grant receives a greater token. Queue heartbeats older than 120 seconds and active leases past expiry are recovered inside the next short write transaction. The default `database-admission-runner.sh <owner> -- <payload>` form retains one lease for the payload's whole lifetime. `fluncle-enrich`, `fluncle-embed`, `fluncle-capture`, `fluncle-crawl`, `fluncle-rank`, `fluncle-reconcile-hub-counts`, `fluncle-artist-bio`, `fluncle-album-bio`, and `fluncle-label-bio` instead use phased admission. Each synchronously invokes `database-admission-runner.sh phase <owner> -- <database-command>` for its bounded database windows while its unadmitted work (DSP, source-audio fetches and MuQ inference, capture providers, Claude, or MusicBrainz) runs between phase processes with no lease, heartbeat, `fence_lost` state, or admission-owned stop path. Hub-count reconciliation has no unadmitted work; its phases exist so no single lease spans the pass. Each window reads at most eight keyset pages of at most 250 entity rows, and each page's truth is one read joined by the entity's own index. The window writes only the rows that disagree as primary-key compare-and-set statements, guarded by the counters that page read, so every write batch is point writes and never aggregates the track graph inside a write transaction. A correction that loses to a concurrent maintained delta leaves that delta intact; the page is re-read once, and a second loss is reported as deferred to the next pass. Embedding reads its worklist in one window and applies the tick's vector writes, with their cost rows, in ONE further window (`update_track_embeddings`); a failed or yielded write is never re-issued in the run, and the next admitted worklist read, which excludes a track once `has_embedding` is set, is its durable fence. The crawl claims a bounded run of nearby nodes per prepare window, processes their provider requests serially, and settles the whole claim in ONE commit window (`commit_crawl_nodes`), preserving its release/general lane balance without pre-claiming the pass. Capture freezes its batch in one prepare window (`prepare_track_captures`) and settles its authorized rows in commit windows of at most six (`commit_track_captures`). Each item carries its exact due-work token, source version, frontier snapshot, and expiry through a signed provider envelope, then checks those durable fences inside its receipt transaction before any expansion mutation. Expansion, settlement, and receipt terminalization commit or roll back together. An unknown commit response is reconciled first; a terminal receipt is read through the same operation coordinates, an absent receipt permits one exact commit retry, and the enclosing pass is never blindly replayed. A deliberately dark crawl projection produces a disabled-gate summary and no fallback mutation. During a rolling service update, only a scheduled invocation with the inherited runner context selects the retained whole-pass compatibility branch. The bodyless manual CLI/API action remains a direct retained single pass and has no phase-level admission of its own. Entity-bio voice-gate rewrites may add bounded write windows, never one acquisition per entity. Every phase gets its own acquisition, fenced heartbeat loop, process-group containment, and release.

**A BATCHED PHASE IS STILL ONE PHASE, AND STILL PER-ITEM INSIDE.** A phase that carries K items is bound by three rules, and each exists because the lease is what it spends. (1) PER-ITEM RECEIPTS: every item carries its own operation key, its own signed token and its own receipt, so a batch never mints a batch-wide operation id and `resolve_operation_receipt` can still be asked about exactly one item. That is what keeps `catalogue.crawl`, `track.capture` and `track.embed` at `yieldRetries: 0` — batching changes nothing about replay, because a retry settles one item and not a group. (2) A SERVER-SIDE WALL BUDGET: K × p99(per-item server time) must stay inside the ~75-second watchdog window, so each batched op checks a wall budget before every item after the first and returns the unprocessed tail as its own retryable per-item verdict rather than running long and losing its fence mid-transaction. A batch therefore overshoots by at most one item.

That budget is checked BETWEEN items and never inside one, so a batch's exposure to a single pathologically slow item grows in proportion to K: one item that runs past the watchdog window loses the fence for the whole phase, where the per-item shape would have lost only itself. What bounds the damage is not the budget but the three DURABLE FENCES each lane already carries — the crawl's claim state plus its per-item receipts, capture's fsync'd journal plus its reconcile path, and embedding's worklist read, which excludes a track the moment `has_embedding` is set. A phase that loses its fence mid-batch therefore leaves reconcilable state for the next tick rather than a half-applied batch, which is exactly what it left before.

K is chosen from the natural unit of work (one claim; the sweep's batch cap) rather than from a measured p99, so the bound is asserted rather than derived. That is made answerable rather than argued: every batched response carries an additive per-item `elapsedMs`, and each sweep publishes `itemMsMax` / `itemMsP50` / `itemSamples` per tick, so a day of ordinary ticks yields the distribution K should be re-derived from. (3) BOUNDED BODIES: request and response bodies carry coordinates, never per-item state — the box keeps that on its own disk as it always has — and where an item's payload is inherently large (the crawl's signed MusicBrainz envelope, capped at 2 MiB each) the batch carries a total cap of its own and the caller splits at the same number the server enforces. K is set per lane from the per-item cost, not from the caller's convenience: the crawl commits one claim, capture prepares twelve and commits six, and embedding writes its tick's batch.

**VERSION TOLERANCE RUNS BOTH WAYS.** The box CLI is a pinned release and lags the Worker as often as it leads it, so every batched op ships beside the per-item op it batches, and neither is removed. A NEW Worker keeps answering an OLD sweep's per-item calls. A NEW sweep feature-detects the batch on a response it already reads — the crawl's prepare, the pipeline worklist — and takes the per-item path when the field is absent. It is never detected by catching a 404 mid-batch: by then the claim is held or the downloads are paid for. Each sweep also carries an environment kill switch (`FLUNCLE_CRAWL_COMMIT_BATCH`, `FLUNCLE_CAPTURE_BATCH_PHASES`, `FLUNCLE_EMBED_WRITE_BATCH`) that forces the per-item path without a rebake.

**THE LEDGER COUNTS LEASES.** Each batched sweep publishes `leases` — the admitted phases that tick actually took — so the effect is measured rather than asserted. A phase that yields before starting or after fencing its command emits only its journald lifecycle event and returns 75 (`EX_TEMPFAIL`) to the caller; it never writes the enclosing run's cron-output marker or ledger row. The payload discards the yielded window's output, stops the run, and emits one exit-zero `gateState: "paused"`, `throttled: true` summary through its ordinary cron-output wrapper, which writes the marker and run-ledger row without counting the window's writes as applied. An in-run replay is permitted only when the operation's `DATABASE_MUTATION_POLICIES` disposition is `replay-safe-idempotent`; entity-bio deliveries receive one retry, while deliberately non-replayable enrichment receives none. Payload work remains chunked/resumable and never shares the lease transaction.

The crawl commit packs complete source-and-repair groups into calls of at most 500 statements, preserving each group's adjacency and `changes()` dependency while removing network round trips proportional to tracks, children, or remixers. This bound limits known client-call fan-out; it is not a universal hosted-latency guarantee, and supported releases are chunked rather than rejected when they need more than one call.

Admission and renewal give public traffic priority in this order: current harmless `select` latency above 250 ms yields as `direct-read-latency`; a non-`ok` or older-than-20-minute `db` snapshot yields as `database-health`; a non-`ok`, older-than-20-minute, or above-500-ms `web` snapshot yields as `public-latency`. Missing stored health rows do not deadlock a fresh deployment. While stored health blocks ordinary admitted writers, their rows remain durable in their original FIFO order. The database-independent healthcheck continues its live probes and external beacon outside admission, then attempts the receipt-backed snapshot that can clear recovered stored health; failure of that optional write cannot turn a completed control-plane tick into skipped payload work. As soon as a healthy snapshot is stored, every conflicting queued writer is eligible again and the original FIFO resumes.

Each server turn emits one bounded `database.admission` structured event with contender, owner/run, operation, physical access class, heavy-reader consumption, queue age, wait, hold, yield reason, recovery, enforcement mode, and outcome. The unit runner emits the corresponding lifecycle event to journald, including whether the invocation was phase-scoped. Exhausted top-level `SQLITE_BUSY` admission retries report `database-busy`; 502, 503, 504, 520, 522, and 525 report `gateway-transport`; and admin authentication failure reports `authentication-failed`. These typed HTTP failures never start or retry the payload. The database client's separate `isRetryableGatewayError` policy remains limited to confidently classified reads. When an enforced whole-lifetime container firing yields before payload start, the runner hands a bounded skip summary to the ordinary cron-output wrapper, which writes the normal marker and fleet-ledger evidence with `gateState: "admission-skipped"`, `payloadStarted: false`, and the admission outcome, wait, and yield reason. A phase-scoped yield omits both because the enclosing payload is already running and owns that evidence; the enclosing wrapper records its paused backpressure summary instead. Checked, produced, queue depth, and expected interval remain null only when no payload work started. The separate telemetry database therefore owns both honest whole-run pre-payload skip evidence and actual payload exit/result evidence, so admission-table contention cannot make the fleet ledger share the primary writer it diagnoses.

Every externally retryable or timeout-prone logical mutation selected for receipt coverage carries an operation key and writes its receipt atomically with its effect. An unknown response is reconciled before replay. Projections define a source of truth, transactional maintenance where practical, an idempotent rebuild, and a drift audit. Backfills are resumable, chunked, observable, and reversible until verified; schema expansion, shadow/backfill, cutover, and contraction remain separate phases. The operation registry, receipt path, due-work and public projections, admission coordinator, artifact protocol, Sonar local replica, device derivation, and their fail-closed completeness tests implement those laws.

### Retry disposition and atomic receipts

[`database-operation-registry.ts`](../apps/web/src/lib/server/database-operation-registry.ts) is the executable retry-policy inventory for every recurring timer/CLI database operation and every incident mutation it names. A write is exactly one of `receipt-backed`, `replay-safe-idempotent`, or `deliberately-non-replayable`; reads and no-database work are `not-applicable`. Each disposition carries a checked-in mechanical source plus its proof or bounded reconciliation rule, and the completeness test fails when a write or incident lacks one. A replay-safe label does not authorize the generic database retry wrapper to retry writes: the owning caller must still use the registered stable-state proof. A deliberately non-replayable path must inspect its bounded queue item, artifact identity, or external publication state instead of blindly repeating the action.

`health.snapshot` is the sole receipt-backed operation. Each caller carries a bounded stable producer ID and derives `health.snapshot:<producer>:<canonical-UTC-at>` after normalizing the accepted timestamp to UTC. The caller and Worker compute the same SHA-256 digest over the normalized snapshot plus producer using canonical JSON with sorted object keys and stable array order; the Worker rejects a caller digest or operation key that does not match before executing the effect. Contract-bound operation keys use a printable ASCII grammar whose character cap equals the runtime UTF-8 byte cap. `operation_receipts.operation_key` is the unique logical identity. An `accepted` row has no result; a terminal `committed` or `rejected` row has a bounded stable `result_identity`, canonical `result_json`, and terminal timestamp. The snapshot's status rows, transition events, check samples, status-event/sample pruning, spent `rate_limit_counters` pruning, and terminal receipt share one libSQL write transaction. A rollback therefore leaves neither effect nor a false terminal receipt.

Same-producer/same-timestamp retries retain the same key. Same-key/same-digest replay returns the stored terminal result without running the effect. Same-key/different-digest is a conflict. An accepted receipt is in progress. Any transaction failure, transport failure, or ambiguous 5xx response (including 524) performs digest-bound reconciliation before the caller may decide what to do: terminal returns the original result, absence under the enabled health cutover is safely retryable, accepted remains in progress, and conflict, rejection, lookup failure, or an unreadable cutover never authorizes replay. Duplicate callers converge through the operation-key primary key and the same reconciliation path.

The `health_snapshot_receipts_enabled` setting is default-off and opens only for the exact value `true`; missing or malformed values keep the legacy writer, while a failed flag read fails closed because the Worker cannot safely select a write path. Flag-off accepts the legacy keyless body and ignores complete validated receipt metadata after verifying it. Flag-on rejects keyless writes. The healthcheck, Hermes pin-watch, sonar freshen, SSH freshen, and rave watchdog callers carry producer, key, and digest before the flag opens, so schema expansion, initialization/shadow, and caller cutover remain independently deployable. The legacy path remains the rollback path until contraction.

Inspection is available through `fluncle admin receipts get <operation-key> [--json]`. Inspection and digest-bound read-only reconciliation (`fluncle admin receipts reconcile <operation-id> <operation-key> <request-digest> [--json]`) use bounded POST bodies, never path or query coordinates. The keyed GET route is removed; the minimum compatible caller is commit `a58f9441088728efa03f8745813ac17425229c18`, or any build containing its POST inspection and reconciliation cutover. Before the contraction leg is deployed, the operator must prove every deployed CLI, healthcheck, pin-watch, Sonar freshen, SSH freshen, and watchdog caller meets that floor; rollback below it requires restoring the keyed route before rolling a caller back. The stale-key Sentry scrub remains as defense for delayed telemetry or an overlooked caller. `fluncle admin receipts repair --stale-before <ISO> [--limit 50] [--json]` is the explicit operator-only mutation: it rejects at most 100 accepted rows strictly older than the supplied fence. These commands return bounded state, operation ID, stable result identity, and timestamps, never the request digest or stored result payload. The Worker disables Sentry request-body capture. Reconciliation and repair emit low-cardinality spans and structured evidence containing the operation ID, outcome, state, and aggregate counts only; operation keys, digests, request/result bodies, secrets, and private topology never enter Sentry or logs.

### Due-work projection

Recurring track and graph-entity selectors materialize eligibility in `due_work`. One physical `work_kind` owns each eligibility and priority policy, while `subject_type` and `subject_id` identify the source row. `ready` rows are claimed through the ready-order index; future retry windows remain `scheduled` until a bounded promotion; leased rows carry an owner, token, and expiry; and `repair` rows are transactionally coupled proof that a source mutation still needs projection repair. An absent or terminal source has no projected row.

The source tables remain authoritative. Each registered definition provides a primary-key-ordered bounded reader, a pure evaluator, and an explicit source-version token. Rebuild checkpoints make zero-row, interrupted, and completed runs idempotent. A new generation upserts the rows it observes and deletes only older-generation rows after the source walk completes, while concurrent repair markers survive that contraction. Drift comparison reads bounded source and projection pages and reports missing, unexpected, and field-mismatched rows without mutating either side.

The local backfill command is `bun run --cwd apps/web db:backfill-due-work`; it rejects every non-local database URL before opening a client. Backfill and shadow comparison populate and verify the projection without changing selector behavior. The completed rebuild also caches the catalogue-rank fingerprint and finding counts, so a projected empty rank tick can preserve its response contract through one KV probe without recomputing the live corpus. Catalogue-rank rebuild generations use that rank-definition fingerprint rather than a producer's opaque marker token: a running generation retains its cursor and cached definition, each source page evaluates against that owned generation rather than the mutable cache, a newer marker version re-derives the live corpus once before the next page, a marker for the same definition coalesces without repeating source pages, and a changed definition restarts the running generation from page zero at once. The `track_work_due_cutover_enabled` setting opens runtime reads only for the exact value `true`; missing, malformed, and failed setting reads stay on the legacy path. With the flag open, every recurring consumer repairs a bounded marker page, promotes elapsed retries, and reads the maintained ready-order index without falling back to a source-table scan or second count. The legacy selectors remain as the ordered default-off rollout and rollback path; the [release manifest](./database-scale-release-manifest.md) forbids contracting that compatibility before the attended cutover evidence exists.

Eligibility-changing writers append a subject repair marker in the same libSQL write transaction as their source mutation. Repair debt is minted by real CHANGE, never by a visit: a writer that touches a row without moving any column a projection reads owes nothing, and the comparison is made in SQL inside the same write batch, immediately before the mutation, because that is the only place where the old and the new value are both authoritative — a TS-side snapshot can race. The comparison is null-safe (`IS NOT`) and compares the exact stored representation, with no epsilon on a float: a missed mark is a permanently stale projection row that nothing repairs, while a redundant mark costs one marker. The catalogue rank tick is the worked example. It rewrites every candidate it ranks, but of the six `tracks` columns it can move only five feed any projection a track source marker reaches (`capture_priority`, `duplicate_of_track_id`, `nearest_finding_score`, and — on the wrong-audio quarantine alone — `capture_status` and `has_embedding`); `nearest_finding_track_id`, `catalogue_ranked_at`, and `source_audio_rejected` are read by none. The sixth, `catalogue_rank_corpus`, is the only one of them any vendor EVALUATOR reads, and only `catalogue-rank`'s (`catalogueRankDueAt`); the tick settles that one projection itself in the same batch — after its write the row is not due in any branch, by construction of the queue predicate — instead of buying a whole-track repair for it. A pure corpus-fingerprint restamp therefore mints no source marker at all, which is what keeps the dominant restamp workload from outrunning the maintenance sweep's drain rate. The settled-row delete is fenced on the due row's `updated_at` against the instant the tick finished selecting candidates, because two of that predicate's inputs — `is_catalogue` and `dismissed_at` — belong to other producers and can legitimately re-project a due row inside that window; a row stamped after the fence is somebody else's and survives, and both columns also ride the changed-row comparison as the values observed at selection, so a concurrent move mints a marker rather than being absorbed by the delete. One residue is deliberate and bounded: `catalogueRankCorpus` is also a member of the broad `DUE_WORK_VENDOR_SOURCE_COLUMNS` hash, so the other vendor kinds carry it in their `source_version` label without any evaluator reading it, and a restamp leaves those labels behind the source. That is an audit-digest concern only — no queue answer, ordering, or eligibility depends on it, and the drift audit runs attended while the cutover is dark — and narrowing that column list is a queue-definition change, which by the rule below ships with its own attended rebuild rather than riding here. A source-repair page expands a bounded run of ordinary generic markers into the registered physical queues in one set-based batch, clearing each source marker in the same version-guarded transaction. The bound is stated in ROWS, not in markers: one track marker — the widest subject — multiplies into every registered track, vendor, and finding queue, and each of those outcomes is exactly one row in the batch, an upsert when the queue wants the subject and a delete when it does not, so the page's marker cap is the shared 500-row projection chunk bound divided by that fan-out width. `SOURCE_REPAIR_LIMIT` derives itself from the three registered inventories, so registering another physical queue narrows the page automatically instead of silently widening the batch past the bound. ROWS AND STATEMENTS ARE DIFFERENT COUNTS and only the row count is what the chunk bound governs: the page flushes as two to four STATEMENTS — a set-based guarded upsert, a set-based guarded delete, the marker clear, and the audit-fence advance — carrying at most 476 projection rows between them, which is a few thousand bound parameters in the upsert. Reading the bound as a statement count is the wrong mental model: widening the page adds rows and bound parameters to the same handful of statements, never more statements. The round trips a page pays are a property of the page and not of its width, so the divided bound is the drain rate the sweep and every guarded read get for free; and a physical repair chunk repairs at most 50 markers of one queue from the authoritative source rows. A guarded consumer read converges its subject family's source markers and then only the queue being read, under one drain budget shared by every guarded read in the Worker request: the first page and the first chunk always run, a further page starts only while the request has started fewer than 12 pages, a further chunk starts only once the source family is clean and the request has started fewer than four chunks, and neither starts once the request's cumulative guard drain time reaches 1.5 seconds. Residual debt does not by itself refuse the read. A source marker is transactionally coupled proof about ONE subject, so a ready page withholds exactly the subjects an outstanding source marker still owns — tested by that marker's own primary key over a bounded window of the ready index, four times the page plus one and never more than 1,000 rows — and serves the rest; a physical marker IS the queue row, held in `state = 'repair'`, so no ready read reaches it and it withholds nothing further. A request that spans two physical queues carries a deferral rather than raising it, so one half owing repair never discards what the other served. The read answers the typed `due_work_maintenance_pending` 503 only when the request has nothing servable while its subject family still owes repair, which is the honest answer for a queue whose whole head is withheld or whose rows are not projected yet. The rail the refusal exists to hold is unchanged and now exact: a worklist never serves a row whose eligibility changed and is not yet re-projected, because the storage and capture budgets behind it spend real money. Two answers sit OUTSIDE that rail because neither hands out a row. A COUNT is a gauge, AND THE CALLER ASKS FOR THAT READING: a worklist read that asked for the whole-backlog count AND set `debtAware` answers the count even while repair converges, with an empty page and `debtPending: true` rather than the refusal, so the operator and the gauge-publishing sweeps are not blinded exactly when debt is the thing to see; a consumer that eats the page keys its pause on `debtPending` exactly as it keyed it on the refusal. The opt-in exists because the box CLI is a pinned release that lags the Worker: a sweep baked before the flag does not send it and keeps receiving the typed refusal it already pauses on, so it can never read a withheld page as a drained queue and report no work against a real backlog — which is what makes the Worker safe to deploy ahead of the box. The flag is answered either way on an opted-in read, so its presence is also the caller's proof that the Worker understood it. A page-only read still refuses whatever the flag says, because there the page is the answer. An EMPTY PAGE spends nothing either, so the cost of a wrong empty is a missed tick rather than a wrong spend, and a queue whose consumer simply retries on its own cadence may opt into serving it. The render queues take that option: the conductor is a single-flight loop over roughly one finding a day, so its ready page is empty almost every tick and a permanently non-zero track family turned every one of those into a deferral instead of a render. A metered queue keeps the default refusal, because there an empty answer is read as a drained backlog by the sweeps that size a capture or GPU budget off it. The budget multiplies bounded transactions and never enlarges one: each page and chunk keeps its own guarded write batch, and a failed batch is never re-issued. A clean guard is two indexed reads. Hosted, a page is five indexed reads plus one write batch, so round trips dominate its cost and the wall bound is what binds in production, while the unit caps bound the transactions a request can issue against a fast database. A request's guards therefore hold its admission lease for at most one page and one chunk per guarded read, plus 1.5 seconds of further units and the one unit still in flight when the budget runs out; a catalogue-rank read adds exactly one rank rebuild chunk after its ordinary pages. Track projection maintenance splits each action into nonzero independent lanes while rank rebuilding is active: one bounded source-repair page, at most 500 catalogue-rank source rows, and at most 50 markers from one pending physical definition. One read of `due_work_repair_idx` that excludes source markers in SQL locates that physical definition. The index does not carry `work_kind`, so the read walks the source markers that sort ahead of the first physical marker once, with one row fetch each; a per-definition probe seeks only `state` and `subject_type` and repeats that walk for every registered definition, so it costs more under a source-marker burst as well as in round trips. A marker whose queue has no registered definition is excluded from the following read, so it cannot hide registered debt behind it in index order. A 500-row rank page is one indexed `track_id` range read, then one write batch of per-row guarded upserts (14 bound values each, no compound SELECT) plus one guarded checkpoint advance, and bounded cleanup deletes at most 500 primary keys per call: the page shape every other definition's rebuild action already runs at the shared due-work chunk bound. A running catalogue-rank generation keeps its durable cursor and owned corpus definition while that definition stays current. Every corpus mutation replaces the global marker's version, and the `due_work_catalogue_rank_corpus_check_v1` setting records the newest marker version whose live corpus matched a generation; a running generation re-derives the corpus only for a marker version it has not checked. A newer marker with the same definition therefore coalesces without replaying completed pages, a changed definition restarts from page zero immediately instead of scanning the rest of a generation that can never clear the marker, and a generation that completes under a checked marker version clears that marker in the same step. `due-work-registry.ts` owns the closed set of eligibility producers that append the global rank marker, which is narrower than the full eligibility-writer inventory. Catalogue-rank row versions depend centrally on only its queue predicate and order inputs (`capturePriority`, `catalogueRankCorpus`, `dismissedAt`, `hasEmbedding`, `isCatalogue`, and `trackId`) plus the global rank fingerprint; unrelated vendor eligibility fields cannot churn the rank queue's version. That fingerprint covers finding and embedded-finding counts, the exact qualified-artist set, and a constant-row finding-vector material revision. The sole vector upsert skips identical bytes; when an actual changed vector belongs to a finding, the same source transaction advances the revision and appends the global marker. Catalogue-only vectors remain row-local, and pre-audio rows use a material-independent fingerprint because their priority cannot depend on finding-vector bytes. A legacy material marker is adopted through an exact-marker-guarded revision write; if a semantic producer arrives first, the marker retains the material evidence but replaces its freshness suffix, so the clear guard still observes every mutation. Finding insertion through publish/certification changes the count, while same-size qualified-artist membership changes move the set digest. Artist-rule replacement retains its ordinary source marker but does not invalidate the corpus because it changes none of those inputs. Capture-verification quarantine remains conservatively registered because its catalogue classification precedes asynchronous work, so an intervening certification could make its later embedding clear affect the finding corpus. A physical repair page resolves its bounded subject set through one indexed source query and flushes the page as at most one set-based guarded upsert plus one set-based guarded delete; each candidate retains its source-version race guard and the same transaction advances the audit fence. The checked-in producer inventory parses every mutation site across the base and satellite eligibility tables, proves that the marker shares that site's write batch or explicit transaction, and follows statement builders through every callsite to a coupled producer. Exact SQL-fingerprinted dispositions cover serialization, fixtures, and fields no evaluator consumes, so another mutation in an already-reviewed file still fails closed. A NEW row's producer still appends a marker rather than projecting inline. Projecting a freshly written track inline would have to reproduce every registered queue's evaluator and its order encoding inside that write batch, and one of them cannot be exact there at all: `catalogue-rank`'s `source_version` folds the GLOBAL corpus fingerprint held in `settings`, which no per-track write transaction fences, so an inline row would carry a label that was already stale when it committed. A wrong label is a permanently stale projection row ordering the metered capture queue, which is the one failure this whole rail exists to prevent, so the marker stays and the drain is sized to absorb it. Rebuild and drift audit remain the independent convergence proof.

A CLIENT THAT DRIVES THIS DRAIN BOUNDS ITSELF BY WALL TIME, NEVER BY A STEP COUNT. One repair step is one HTTP round trip, and hosted round trips dominate a page's cost, so the same step count costs seconds against a warm database and minutes against a loaded one — a caller with a deadline of its own that sizes its step count from an assumed per-step cost eventually runs past that deadline, is killed mid-sequence, and reports nothing at all while having held the fleet's single write lease for the whole deadline. The budget therefore belongs where elapsed time can be measured between round trips: `fluncle admin projections advance --wall-ms <ms>` stops issuing steps once the budget is spent and returns what it did, with `wallStopped` distinguishing a spent budget from completion. A step ceiling stays as the hard cap on requests issued, and the driving process's own child deadline must clear its budget plus the step already in flight plus process startup with margin, because the margin between the two is what keeps an ordinary busy drain out of the blind killed state. A kill is reported as its own outcome rather than as zero progress: zero progress is a measurement, a kill is the absence of one. A pinned client that ships on a different cadence from the driver invoking it asks whether the flag exists before sending it — the client's own help page is that answer — and falls back to a step ceiling short enough to stay inside the deadline, reporting which bound ran; an unnecessary fallback only drains slower, while assuming a flag forward fails every call in the version-skew window.

THE CATALOGUE-RANK CORPUS MARKER IS NOT DEBT AGE. It is a resumable rebuild checkpoint wearing a source-marker row: it clears only when a whole rank generation completes against a corpus proven unchanged, and any corpus mutation restarts that generation, so at catalogue scale it legitimately holds `repair` for hours while every ordinary marker drains. Projection status therefore reports it as `trackDueWork.catalogueRankMarkerAgeMs` and excludes it from `oldestOutstandingMarkerAge`, which exists to answer whether ordinary debt is draining. Folding the two together makes a healthy long rebuild read as debt that never drains, which escalates any age-driven budget to its ceiling on every tick and marks a liveness row down for work that is succeeding. Reporting it separately rather than dropping it is what keeps a rank rebuild that has genuinely stalled visible.

### Crawl and public shadow projections

The crawler's separate `crawl_due_work` projection preserves its two-lane law: up to `ceil(limit / 2)` release slots use the storable-first release index, then the general breadth-first index fills the rest. Pending nodes are ready, retryable failures are scheduled at their failure-scaled due time, and every drained allowed MusicBrainz artist becomes a daily tail subscription once its allow has no unstamped rearm request. Claims carry an owner, token, ordered position, and expiry; promotion, lease reaping, direct node repair, and label/artist-rule fanout are bounded by the projection's partial and fanout indexes. The source frontier remains authoritative. The `crawl_due_cutover_enabled` setting is default-off and opens only for the exact value `true`; missing, false, malformed, and failed reads retain the unchanged legacy selector. An open pass runs forward seed/rule maintenance first, drains only bounded repair pages, promotes retries independently and tail-rearms at most the oldest ten due stale artists, claims the maintained two-lane order with one pass owner/token and a lease longer than the bounded HTTP pass, and hydrates only the claimed frontier primary keys in `claim_position` order. Stale-artist promotion atomically moves the authoritative row and its due row and preserves the pass counter even when the caller claims zero nodes, so the open path never executes the legacy double artist-rule probe or its sort. Success or failure settlement transactionally verifies the node/token lease, mutates the authoritative frontier row, deletes only that lease, and appends the exact repair marker; a stale token changes nothing and contributes no pass counters.

The public shadow projections materialize only the stable global facts: total tracks; exact non-NULL literal `substr(release_date, 1, 4)` and key buckets; the invalidation epoch for the default `release_date DESC, track_id DESC` hub order; and artist qualification. Qualification counts one certified finding per credited artist and enabled-label credits as two half-units for a primary artist or one for a remixer, with membership at any certified finding or six half-units. Per-track memberships and per-track/artist contributions retain the old side of every delta, label rulings fan out through `tracks_label_id_idx`, and repair epochs prevent a newer source marker from being consumed by an older repair.

The public invalidation contract follows source dependencies, never subject type. `public_aggregates` depends only on track existence, `tracks.track_id`, `tracks.release_date`, and `tracks.key`. `artist_qualification` depends only on `track_artists(track_id, artist_id, role)`, finding existence by `findings.track_id`, `tracks(track_id, label_id)`, and `labels(id, seed_state)` where the exact `enabled` value qualifies. The closed producer-impact registry covers every producer in `DUE_WORK_PRODUCER_INVENTORY` exactly once as aggregate-only, artist-only, both, neither, or one of three justified dynamic policies; missing, duplicate, unknown, or unjustified entries fail closed. `track-update` targets aggregates only when `key` is supplied, `label-seed-state` targets artist qualification only when a ruling supplies `seed_state`, and `hub-entity-relink` targets artist qualification only for label relationships. Static producers cannot override their registered impact.

The shadow maintenance contract remains a transactionally coupled rail beside independent legacy due-work eligibility maintenance. New-track and key writers target only aggregates; finding-existence certification, artist edge or role changes, and label link or enabled-state ruling changes target only artist qualification; `publish-track`, which inserts both its track and finding, targets both. Rank and capture metadata, anchors, covers, bios, artwork, notes, identity metadata, maintained hub counts, and social or publish bookkeeping target neither public projection, so they create no public repair and advance no public source epoch while still retaining their legacy source-repair marker. Explicit targets are validated against their subject family, selection markers preserve the same dependency policy, guarded source no-ops append no public work, and the synthetic catalogue-rank corpus subject never enters a public projection. For both targets the fixed statement order is legacy marker, aggregate epoch, aggregate repair, artist epoch, artist repair; every `changes()` admission gate, race token, bounded fanout, and rollback boundary remains intact. Every `crawl_frontier` mutation in the crawler appends the exact node repair in the same bounded write batch, and label seed/scope plus artist-rule verdict/rearm writes append indexed label-slug or artist-MBID fanout markers in their source transaction. The source tables remain authoritative throughout shadow operation.

Both projection families rebuild by stable sorted IDs with durable generation checkpoints, preserve live repairs newer than the rebuild start, compute exact source/projection digests, schedule only bounded drift repairs, and expose legacy shadow comparators. A logical public rebuild page carries at most 500 tracks, while source reads and writes execute in 50-track subpages and artist plans are packed under a fixed statement ceiling; the durable cursor moves only after every subpage commits, and execution-time live-generation guards preserve a repair that lands after the page snapshot. A logical crawl rebuild page also carries at most 500 frontier rows, resolves each artist rule through the covering MBID/verdict/rearm index, and packs projected rows into at most ten 50-row candidate statements plus one guarded checkpoint advance in a single atomic batch. A resumed crawl page reads its checkpoint without first acquiring the write lane; checkpoint creation or an explicit new generation remains conflict-safe. Once the source walk ends, generic due-work cleanup retains the existing scalar subject-ID lower bound so an older Worker can resume after rollback, while crawl cleanup retains that inherited lower bound for only its first pass and then runs cursor-free before completion to close any earlier race gap. Both paths seek only removable stale-generation and old-live candidates through their partial covering cleanup indexes and delete at most the requested limit per call. New cleanup pages advance by deleting candidates rather than persisting a cursor that disagrees with the index order. Current-generation rows, repair markers, and live rows newer than the rebuild start never enter a cleanup page. Default hub anchors are rebuilt deterministically outside request time into generation-addressed shards, and every shard is a self-describing run of the order: its fingerprint records the row the run starts strictly behind (`after`, null for the head of the order), its row count `n`, its leading non-NULL-key count `nn`, and the run's absolute start position `base` when its boundary rows were last computed, while its JSON body keeps the boundary rows at page-size ranks with the page each opens. A run's membership is its fixed key range `(after, next.after]`, so an earlier run growing or shrinking never changes which rows a later run holds; only prefix counts move. Each build call walks one bounded source page into one run plus a strictly validated constant-size cursor, and every walked run is written whether or not it holds a boundary row, so the runs cover the whole order; malformed or internally inconsistent state first purges its partial generation through the same bounded primary-key cursor, then restarts from source. The validity row publishes the generation only after the runs are proven from metadata alone to cover exactly the projected total, records the previous valid generation as the explicit rollback generation, and cursor-cleans every other superseded generation after publication. A numbered default page resolves through one prefix-count read over the generation's run metadata that returns only the run holding the page's first row, then seeks strictly behind the nearest boundary row inside that run, or behind the run's `after` row, with an offset below the page size; a page starting in a run's NULL-key tail seeks inside the NULL zone, behind a NULL boundary row or from the zone head the run itself opens. Readiness and the open gate prove usability from the same run metadata without concatenating the document; an older whole-document shard format still parses whole. Source traversal persists an explicit non-NULL/NULL phase, uses a row-value indexed range for resumed non-NULL pages and a `release_date IS NULL`/`track_id` range for NULL pages, so neither ties, restarts, nor the phase boundary can force a corpus scan or temporary sort. Arbitrary filtered public queries deliberately remain indexed source queries rather than a combinatorial aggregate cube. The `public_projection_cutover_enabled` setting is default-off and opens only for the exact value `true`; every other value or settings read failure retains the exact legacy query. Aggregate reads are usable only when the `tracks` state is `complete`, `aggregate_epoch = source_epoch`, and no `public_aggregates` repair exists. Artist qualification is independently usable only when its `artists` state is `complete`, `projection_epoch = source_epoch`, and no `artist_qualification` repair exists. Default release-hub anchors additionally require the exact hub/clause address, the current anchor format, a non-empty generation matching aggregate state, `order_epoch = release_hub_order_epoch`, runs whose metadata covers exactly the projected total (or, for the older format, a complete page-boundary document), and defensively valid JSON. Usable projections serve the default total, literal release-year and key buckets, qualified artist IDs, and default-hub anchors; filtered hub reads and every unusable/error case keep the legacy source query. Public requests only probe readiness and read projections; recurring repair authority is narrowed separately below.

An aggregate order-epoch change may retain its generation, and page-local maintenance is the standing path for it. Every subject-level public repair that changes the release-hub order writes, in its own transaction, one order-change ledger row keyed by the epoch it mints, naming the subject, the change kind (insert, delete, move, no-op, or unknown), and the subject's release date before and after. Anchor maintenance consumes the ledger in epoch order against the current generation's published document, or against the built prefix of an in-flight build: it locates the run holding each affected key by one prefix-count read, re-extracts that run over its fixed key range with one bounded source read, and publishes the amended runs under the same generation. A run that grows past 200 rows splits at its midpoint into two runs keyed to sort between their neighbours; an emptied run other than the head run is dropped, and the head run is never dropped because it is the one run whose range has no lower bound. One subject-level order change therefore rewrites at most four shards (the run it left and the run it entered, each possibly split once); a bounded step consumes at most eight changes against a published document. Each entry lands atomically: the validity row advances to the entry's epoch first, guarded by its previous epoch, the source-readiness predicate, and every touched run's fingerprint, and the run writes plus the ledger delete land only behind that advance, so the reader sees either the previous document or the amended one and serves the amended document only once it names the current epoch. During a build, an entry behind the durable cursor amends the built run and moves the walked row count, an entry ahead of the cursor is absorbed by the walk still to come, and the build state's epoch advances so the walk resumes from its cursor rather than restarting at shard zero. The full generation rebuild remains the path for an epoch the ledger does not represent (an older writer or a hand-set epoch), an unamendable entry, a backlog above the threshold of eight changes or eight percent of the projected total (whichever is larger), or a malformed document: before that same generation restarts from shard zero, anchor maintenance cursor-deletes every shard in the generation at no more than 100 rows per request and conditionally removes only the stale published identity once cleanup reaches its end. A fresh build and every publication purge the ledger up to the epoch they represent, so the ledger holds only unrepresented order changes. Published and interrupted rebuilds, including contraction to an empty corpus, therefore cannot retain trailing shards from a larger document; the rollback generation and complete-document publication boundary remain intact.

Source mutations append exact repair debt transactionally. Every five minutes the admission-wrapped `fluncle-projection-maintenance` host sweep reads bounded status once, then serially converges enabled families in the fixed order `track_due_work`, `crawl_due_work`, `public_aggregates`, and `artist_qualification`. Every repair request uses a 500-subject page; the two due-work families each receive at most 20 sequential steps per tick, while the two public families each receive at most four, with each family stopping early when it reports complete. Public aggregate repair continues through the bounded anchor cursor as soon as marker debt drains, including the request that repaired the final marker. An enabled family reports one outcome: `no_debt`, `useful_completion`, `partial_progress`, or `no_progress`; a dark family retains `outcome: null`. The run reports the worst enabled-family outcome in the order `no_progress`, `partial_progress`, `useful_completion`, then `no_debt`. `ok` and `errors` describe command execution for the run ledger, while `converged`, `budgetExhaustedFamilies`, and `oldestDebtAgeMs` separately describe whether bounded maintenance kept pace. A clean incomplete result remains execution-healthy, including `no_progress`; a thrown or malformed command result is an execution error. The `/status` row marks observed incomplete debt down after three maintenance cadences plus maximum timer jitter, which enters the normal transition alert path without treating one bounded tick as a failure. A dark family and an open idle family issue no mutation. The agent token can read status and invoke bounded repair for exactly those four families; rebuild, audit, and every cutover mutation remain attended operator work. The one thing a repair step also drives is the stale-definition re-projection described under the definition version below — server-side, only for a family whose stored definition version is not the running code's, and only with the page budget repair itself did not spend.

The local command is `bun run --cwd apps/web db:backfill-shadow-projections`; it resumes existing generations by default, accepts `--new-generation`, `--audit-only`, `--limit`, and `--repair-limit`, and refuses hosted or non-loopback database URLs before opening a client.

Production convergence uses the authenticated control plane, never the local backfill scripts or an interactive SQL client. The recurring agent exception is limited to the bounded status read and repair of the exact four runtime families described above; every other control remains operator-only. `fluncle admin projections get --json` returns fixed-schema backlog, rebuild, repair, digest, epoch, anchor, cutover, and `readyToOpen` evidence for track due-work, crawl due-work, public aggregates, and artist qualification. Growing backlog and repair totals are capped index probes represented as `{ "count": number, "truncated": boolean }`: `truncated: false` makes the count exact, while `truncated: true` makes it an observed lower bound and readiness still uses a bounded empty/non-empty proof. Each family also returns `oldestOutstandingMarkerAge` with `ageMs`, `reason`, and `truncated`. Every family measures debt age from an immutable repair-entry time within the same `PROJECTION_STATUS_COUNT_LIMIT + 1` index-ordered probe windows and reports the oldest observed age without an unbounded aggregate scan. Direct track and crawl repair rows retain `repair_entered_at` across re-marking until the version-guarded repair transaction clears or deletes them; fanout and public marker rows retain their creation time across re-marking. A direct repair row that predates `repair_entered_at` remains untimed and reports `ageMs: null`, `reason: "marker_timestamp_unavailable"`, and `truncated: true` until ordinary maintenance clears it, never substituting mutable `updated_at` or frontier discovery `created_at`. Timed debt alongside an untimed row keeps the oldest observed timed age with `truncated: true`; probe-window exhaustion has the same lower-bound signal. `fluncle admin projections advance --target <track_due_work|crawl_due_work|public_aggregates|artist_qualification> --action <rebuild|repair|audit> --limit <1-500> --json` still advances exactly one durable page by default. An optional `--max-steps <1-100>` makes the CLI issue that many sequential requests at most, stopping as soon as the server reports `complete: true`; `--limit` remains the page size for each request, while `--max-steps` is the client request budget. The recurring maintenance sweep sizes that budget per family from the debt its one opening status read measured: a bounded, fresh count buys the steps that count needs plus one for what producers append during the tick, while a TRUNCATED count — a floor, not a measurement — and debt older than an hour each spend the full ceiling, because both say the family's marker set is not emptying between ticks rather than that it is one page behind. The two public families carry a step FLOOR under that sizing, because an unmatched epoch and an invalid anchor document are repair work the marker count reports as zero. The sweep advances families OLDEST DEBT FIRST under one whole-run wall budget well inside the unit's own start timeout, so a busy family cannot spend the tick and leave a quiet one ageing behind it; a family the budget never reached keeps its debt, reports incomplete so it cannot read as converged, still contributes its debt age to the health bar that watches it, and sorts first on the next tick. Source-repair pages drain in primary-key order, so a family's oldest marker age measures whether its marker set EMPTIES between ticks rather than how far behind one page is. Drain capacity is therefore the lever; re-ordering the page by age would mean a new index on a populated table. Multi-step calls omit the global status snapshot from each intermediate response, use only target-local indexed preconditions, and fetch the global evidence exactly once after the serial budget completes, so every mutation keeps its hosted-safe bound without repeating the complete projection suite after every durable page. The default one-step operator contract remains status-bearing for existing callers; the statusless response is private to the bundled CLI's multi-step control path. The JSON result keeps that terminal status and adds exact aggregate `steps`, `processed`, and `scheduled` totals; when the budget ends before completion, `complete` remains false and the server-owned cursor makes the next invocation resumable. Rebuild cleanup, public hub-anchor extraction, superseded anchor cleanup, and exact audits retain their own cursors, so no request hides a corpus scan. Public anchor extraction remains independently capped at 100 rows per transaction. Rebuild and repair invalidate prior audit proof. Track and crawl repair consumption also advances a persistent monotonic audit fence in the same transaction as the guarded marker drain, so a source mutation cannot leave a previously matched digest reusable after its repair debt returns to zero. An audit runs only while the relevant cutover is dark, the rebuild is complete, and repair debt is zero. Public aggregate evidence is fenced by source epoch, aggregate generation, and release-hub order epoch, and its exact anchor lane compares every canonical source boundary's identity, key, page, and order with the published current generation: a run document is verified run by run against the source (range size, key phases, and stored boundary rows) and the boundaries it serves are re-derived from that read, while an older whole-document format is compared as stored. A digest mismatch returns a conflict and the next rebuild starts a fresh generation while source tables remain authoritative. Changing a queue's projected order or eligibility definition is not a source mutation and appends no marker, so nothing in the source tables can announce it. Each due-work family therefore carries a DEFINITION VERSION: a deterministic fingerprint of the code that decides that family's eligibility and `sort_key`, derived by running its own pure decision function over a fixed probe matrix at a frozen instant and hashing the transcript (`apps/web/src/lib/server/due-work-definition-fingerprint.ts`). It is never hand-bumped, and `due-work-definition-version.test.ts` pins every family's value, so a definition edit fails the build until that fixture moves in the same commit. The version is stored on the rebuild checkpoint. A checkpoint whose stored version is not the running code's is not complete — for the status read, for the audit's readiness gate, and for the cutover's open proof — and the next bounded rebuild step opens a fresh generation for that family and re-projects it, with no audit evidence, no cutover flip, and no operator ceremony. The audit digest, which covers `sort_key`, continues to fail closed until that rebuild has run.

The fingerprint is BEHAVIOURAL, and its blind spot is stated rather than hidden: it sees only what some probe answer shows it. The matrix moves ONE COLUMN AT A TIME off a small set of hand-written bases, so a branch that needs two columns together — a `failed` capture and a non-null attempt stamp, a vendor cooldown and its `*_attempted_at`, a finding render with its context note set and its video URL null — is unreachable unless a BASE already carries the companion column. Adding such a branch means adding a base, not only a ladder value. The numeric half of the ladder is derived from the constants themselves (`probeLadderCrossing` takes each compared threshold and emits it with both neighbours), so retuning a cap by one moves a probe answer and therefore the version; a constant an evaluator ADDS to a timestamp needs no ladder value, because it lands in the computed `next_due_at`, but it does need a base that reaches its branch. `due-work-definition-version.test.ts` holds a case table classifying every exported constant in the three definition modules as compared or additive, proves each one is actually crossed by a pair of probes drawn from the real matrix, and fails when a new exported constant appears unclassified. The matrix also TYPES its columns: a `*_at` column is probed only with `null`, two strings that are unambiguously not dates, and three fixed ISO instants, because `Date.parse` of anything else falls back to an implementation-defined parse read in the HOST'S LOCAL TIME — a bare integer in a timestamp column becomes a year, and the version would then be a function of the machine's UTC offset rather than of the code, flapping between a developer's laptop and the UTC Worker and re-projecting forever. A test pins that by rebuilding the transcript under three timezones, one of them on a half-hour offset, and requiring one fingerprint.

The re-projection drives itself. `--action rebuild` is operator-tier and no cron issues it, so the walk rides the agent-eligible REPAIR path instead: each repair step runs ordinary repair first and spends only the page budget repair left behind on one bounded rebuild page for the oldest stale family. Repair therefore always has first claim, and the walk cannot starve it. The safety property is enforced in SQL rather than by the caller: `startDueWorkRebuild`'s conditional upsert is false for a family that is complete on today's definition, so this path cannot start a needless re-projection even if asked. The maintenance sweep's gate advances a due-work family for repair debt OR an incomplete rebuild, which is what brings the call. Pacing follows from the existing budget: 500 rows per step, at most 20 steps per five-minute tick, so roughly 10,000 source rows a tick and 120,000 an hour — a full-generation walk over every family is therefore a matter of hours, not one long transaction, and it resumes from its own durable cursor after every tick. Each tick reports `rebuildStaleFamilies` and `rebuildRowsWalked` in the run ledger, so a stalled re-projection is visible instead of hiding inside `processed`.

`fluncle admin projections rekey --work-kind <queue> [--cursor <subjectId>] [--limit 1-500] [--max-pages 1-200] [--apply] [--json]` is the operator's lever for forcing ONE queue back onto today's definition now, instead of waiting for the self-driving walk to reach it. It seeks that queue's projected rows through the `due_work` primary key and marks them for repair in bounded, resumable pages, so the maintenance sweep's ordinary repair path re-keys them. A dry run is the default; each call reports `matched`, `marked`, its terminal `cursor`, and a bounded `remaining`. A repair marker withholds its own subject from that queue's reads until it is drained, so marking a whole queue at once takes that queue's servable rows to zero for the length of the drain — the paging exists so the operator can choose how much of a queue is in flight. Physical repair drains at most 50 markers per advance step and the sweep spends at most 20 steps every five minutes, so the honest ceiling is 1,000 markers per firing, or 12,000 an hour.

Flags are changed only through `fluncle admin projections set --target <track_due_work|crawl_due_work|public_projections> --enabled <true|false> --json`. An enable request uses one conditional database write that re-proves the matching current audit digest and its current source fence, zero repair debt, complete rebuilds, and, for public projections, both independent epochs plus the exact audited generation/order fence and a runtime-valid current anchor generation; a zero-row write fails closed if any proof changed after the preceding status read. A disable request remains an unconditional rollback write and always succeeds. The settings remain default-dark. Public reads retain the legacy fallback for absent, false, malformed, unreadable, or unusable projection state. Track and crawl consumers retain their legacy selectors while the corresponding flag is absent, false, malformed, or unreadable; once open, they perform bounded maintenance and answer the typed `due_work_maintenance_pending` deferral while relevant maintenance remains incomplete rather than run a legacy scan. The crawl claim drains both of its own lanes under one budget — bounded source-repair pages, then bounded node-repair chunks, with unit caps and a wall bound, the first page and the first chunk always running — so a claim it defers has still converged the repair its budget allowed. No operator endpoint accepts SQL, table names, database coordinates, or credentials. Exact digest readiness is first-open evidence and is intentionally invalidated by live repairs; steady-state health additionally requires useful consumer progress, bounded debt age, usable anchors, and the public latency budgets above.

### Mixable artist projection

The mix artist picker reads `artists.rankable_track_count`, the exact number of credited tracks whose key is non-NULL and whose embedding mirror is present. Key and embedding transitions move every credited artist in the same transaction, artist-edge writers carry the source track's rankability into their counter delta, guarded embedding clears run an exact difference-only artist repair after source-maintenance marker accounting, and the hub-count reconciliation pass repairs out-of-band drift. Post-deploy activation is a no-op when the readiness fence is already complete because production writers maintain the counter transactionally; an absent, dirty, or interrupted fence instead keeps reads on the legacy source query while activation keyset-reconciles bounded artist pages and repeats full passes until one complete stabilization pass observes zero corrections. ## Test-data laws

Raw production data and identifiers never enter the repository or CI artifacts. Fixtures are deterministic and synthetic while preserving audited cardinality, selectivity, null distribution, fan-out, and backlog distribution. Exact 1×, 2×, and 4× profiles derive only from the checked-in manifest. Local SQLite/libSQL is mandatory for correctness and deterministic plan tests. Hosted Turso is a separate scratch-only replay because local behavior is not hosted performance evidence.

Mutation contracts must operate only on a disposable harness database, use stable synthetic keys, and be idempotent or reset their fixture between samples. A timing contract must warm up explicitly, use deterministic iteration counts, report every distribution, and retain result/affected-row counts so a fast empty or wrong query cannot pass. A plan assertion must name every growing table and narrowly justify any allowed scan. Fixture changes update the manifest contract and determinism/selectivity tests in the same change.

## Local and hosted are different

Local libSQL is the correctness oracle, not a hosted-performance substitute. Four known divergences are mandatory interpretation context:

1. A query vector bound as text has a hosted probe-binding cliff that local `sqld` does not show. At 100,000 rows the observed hosted p50 was 26,700 ms for text versus 1,883 ms for a raw BLOB, while both were 175 ms locally. Bind vectors as raw BLOBs.
2. Do not build `libsql_vector_idx` on a populated table. Hosted creation can block writes while local creation can yield an empty index. Use an exact `vector_distance_cos` scan behind a B-tree prefilter.
3. The response cap fails loudly above 10 MiB in local development, while hosted queries can continue until they exhaust the Worker's 128 MB isolate. Rank growing vector columns in SQL instead of returning them for application-side ranking.
4. A flattened CTE fanned out by `UNION ALL` branches or outer cross-join rows is re-executed per branch or row. Fold multi-probe distances into one select expression; materialize bounded pair scans and pin the small findings relation as the driver.

Any query scanning a table that grows with the archive needs an attended hosted scratch replay before anyone claims that it scales. That replay confirms planner and network behavior; it never targets production or development databases.

## Worker placement

The web Worker runs beside the database. `apps/web/wrangler.jsonc` sets a Placement Hint (`placement.region`) naming the cloud region of the Turso primary, so each statement pays an in-region round trip rather than an intercontinental one. A request issues most of its statements in sequence, so that round trip multiplies across the request, and the public database-span and end-to-end budgets above assume it. When the primary moves to another region, the placement hint moves in the same change; `turso db show` names the primary's location.

Placement changes where the Worker executes and nothing else:

- Static assets are still served from the data center nearest the viewer; only non-asset requests and the paths in `assets.run_worker_first` invoke the Worker.
- The Worker's Cache API store (`caches.default`, `apps/web/src/lib/server/edge-cache.ts`) is local to the data center that runs the Worker, so it lives in the placed data center. Every viewer shares that one store, an edge-cache hit still pays the viewer-to-placed-data-center hop, and a purge's local `cache.delete` lands on the store the reads use. The zone purge-by-URL remains the global eviction for entries held in any other data center. Cache keys are the canonical origin and path, never the serving data center.
- Outbound calls from the Worker (sonar, third-party APIs) leave from the placed region, so a provider that answers by caller region or limits per egress address sees that region.

## Client bounds and mixed-load evidence

`@libsql/client`'s remote HTTP default is 20 operations per client, and `concurrency: 0` also resolves to 20. Local `:memory:` and `file:` clients ignore that option. The explicit numbers below bound one client instance. `getDb` and `getTelemetryDb` memoize their client promises inside the Worker's `AsyncLocalStorage` request scope, so co-called helpers in one request share one primary client and one telemetry client instead of multiplying those per-client caps. The Worker separately applies `WORKER_DB_AGGREGATE_CONCURRENCY = 4` at that instrumented chokepoint: one module-level gate queues `execute`, `batch`, and explicit transaction lifetimes above four operations across every client and concurrent request in one isolate. Worker isolates serve concurrent requests in one module instance, so this is a real request-wide bound there; queued callers poll from their own request context because Workerd does not permit one request to resolve another request's Promise, and the shared release path never settles a different request. The server entry registers its awaited response promise with `waitUntil`, preserving the `finally` releases if the client disconnects; any future deferred database work must register its own lifetime, as the existing edge-cache paths do. Eligible work competes opportunistically rather than receiving a FIFO guarantee, while the separate heavy lane guarantees that an ineligible queued heavy read cannot convoy public work. The gate does not coordinate across isolates, processes, timers, or fleet units, and cross-unit admission remains the coordinator's job. The value matches the tested primary fan-out rather than a production-tuned capacity claim, and changing it requires updating the deterministic contract rather than a Wrangler or production setting.

| Client class                         | Bound | Rationale                                                                                                                                                                                                                                         |
| ------------------------------------ | ----: | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Primary Worker client                |     4 | Preserves ordinary route fan-out while preventing one logical caller from issuing 20 remote operations. Known request fan-outs include three, five, and seven reads; four is the explicit compromise to test rather than a global capacity claim. |
| Fleet telemetry client               |     3 | The ledger reader intentionally performs page, rollup, and count concurrently; inserts remain a single statement.                                                                                                                                 |
| Catalogue public-entity count script |     3 | Its only deliberate direct-client fan-out is three concurrent counts.                                                                                                                                                                             |
| Maintenance/operator scripts         |     1 | One-shot migration, backfill, inspection, and destructive tooling is sequential or explicitly batched.                                                                                                                                            |
| Hosted benchmarks                    |     1 | Measurement must not accidentally manufacture same-client parallel load.                                                                                                                                                                          |
| Seed clients                         |     1 | Fixture and seed writes are ordered, chunked batches.                                                                                                                                                                                             |
| Readiness and smoke clients          |     1 | Readiness, migration, and smoke steps are serial.                                                                                                                                                                                                 |
| Local HTTP helpers                   |     1 | Local server setup and browser fixture paths are serial even though a local engine may ignore the transport option.                                                                                                                               |
| File clients                         |     1 | Restore, derivation, and other file-backed paths are serial; this records intent where the local driver ignores the option.                                                                                                                       |
| Test clients                         |     1 | Tests declare their expected shape and use a separate controlled scheduler for concurrency evidence.                                                                                                                                              |

The deterministic mixed-load contract starts one held 100 ms heavy reader, three 5 ms public reads, and two serialized write batches on the primary four-slot model. Its request-wide scenario also starts three concurrent public requests that each fan out four reads, plus held heavy-read and serialized-write work, behind the isolate ceiling. Both scenarios record per-class queue and latency p50/p95/p99; the request-wide report records the aggregate observed maximum as release evidence and names the runtime `request_in_flight_max` span metric. The request-scope regression independently co-calls six `getDb` helpers, proves they create one client, and observes a real admitted fan-out maximum of four. The runtime classifier assigns `vector_distance_cos` scans to `heavy-read`, and the gate admits at most one heavy reader at a time, so a held vector scan leaves three aggregate seats for public reads and another queued heavy reader cannot convoy them. Replacing the primary bound with one makes the per-client test report the avoidable public convoy; replacing the aggregate bound with the multiplied request-local capacity makes the request-wide observed maximum exceed four.

This evidence covers per-client bounds and request-wide admission inside one Worker isolate only. The mixed-load simulator's write lane models SQLite transaction serialization inside those scenarios; it must not be described as cross-unit admission evidence. Cross-unit FIFO fairness, writer/heavy-reader leases, fencing, guardrail yield, process containment, and recovery are proven separately by the admission model and source-shape checks against the implemented coordinator.

## Telemetry and privacy vocabulary

Database query spans and fleet run records share a bounded vocabulary: `operation_id`, `access_class`, `release`, `attempt_count`, nullable `batch_count`, `duration_ms`, and `outcome`. Database query spans additionally record the numeric `queue_wait_ms` and `aggregate_in_flight_max` from isolate admission plus `request_in_flight_max` from the current request scope; none of these fields is an identifier. Operation IDs are stable, validated, low-cardinality identifiers with a deterministic sanitized fallback. Access class is exactly `read`, `write`, or `heavy-read`. Release identifies committed code, attempts count actual attempts, batch count is null when unknowable, duration includes isolate queueing plus execution, and outcome is exactly `success` or `failure`.

SQL arguments, interpolated literals, raw rows, names, email addresses, track or user identifiers, secret values, tokens, hostnames, URLs, ports, and private topology never enter that vocabulary. `db.query` remains the Sentry operation, and `sendDefaultPii: false` remains mandatory. Query descriptions are normalized grouping labels rather than raw SQL when literals could leak. The runner's JSON contains plan text and aggregate counts only for registered synthetic or reviewed statements; a new contract must audit its statement and metadata before registration.

## Run and interpret the harness

Run the lightweight local suite, which materializes only a 512-track derivative:

```bash
bun run --cwd apps/web db:performance --profile 1x
bun run --cwd apps/web db:performance --profile 2x
bun run --cwd apps/web db:performance --profile 4x
```

Select or list contracts independently:

```bash
bun run --cwd apps/web db:performance --list
bun run --cwd apps/web db:performance --profile 2x --contract fixture.frontier-pending-claim
```

An exact local profile is explicit because it may write millions of rows while remaining memory-bounded:

```bash
bun run --cwd apps/web db:performance --profile 1x --full-fixture
bun run --cwd apps/web db:performance --profile 2x --full-fixture
bun run --cwd apps/web db:performance --profile 4x --full-fixture
```

Exact full-fixture local runs require `sqld` on `PATH`. The harness follows the repository's `turso dev` lifecycle pattern but launches the local libSQL server through its own offline supervisor, avoiding the Turso launcher's version check. It uses a fresh database on an ephemeral loopback port, requires a per-attempt Ed25519-signed token, proves readiness with a bounded authenticated `SELECT 1` plus sidecar ownership check, and retries a bind collision on a fresh port. Every HTTP request and exact-profile process has an absolute deadline. The HTTP client performs fixture and contract work, and the release runner places its database scratch outside the detached candidate source. Normal close, interrupt/termination, or abrupt benchmark-owner death causes the supervisor to terminate the sidecar process tree and remove the database directory; the supervisor owns and drains bounded log tails rather than forwarding into owner pipes, and parent cleanup retains a TERM-to-KILL process-group fallback. Isolation, readiness, census, and cleanup fail closed. Database pages therefore remain resident in the sidecar rather than being counted as application RSS, matching hosted Turso's process boundary; heap, raw client-process RSS, and wall thresholds remain hard and no baseline subtraction or missing-sample coercion is allowed. Lightweight non-`--full-fixture` commands retain the 512-track embedded fixture so CI stays small.

For one clean release proof, run the exact profiles and the real local component suites through the non-production release runner:

```bash
candidate_commit="$(git rev-parse --verify HEAD^{commit})"
bun run --cwd apps/web db:performance:release --candidate-commit "$candidate_commit"
```

The release runner executes sequentially and never accepts hosted or operator gates. It passes an allowlisted environment to child processes without credential values; it does not provide OS-level network isolation, so the local/offline command set is an execution contract rather than a sandbox. It first requires a clean invocation checkout, resolves the candidate, and creates a detached candidate worktree in a temporary execution root. Every proof child runs from that detached root, while the release artifacts, database scratch, and Cargo target remain outside its source directory. Before any proof child runs, the detached root receives its own dependency tree from a bounded `bun install --offline --frozen-lockfile --ignore-scripts --backend=copyfile`; an unavailable cache, changed lockfile, failed install, missing `node_modules`, or deadline is a no-go. Copy-file installation keeps the candidate independent of both the invocation worktree's mutable `node_modules` and mutable links into Bun's cache, while the frozen lock supplies package-integrity coordinates. The runner reuses its own Bun executable for install and Bun child commands, and the manifest records the exact install method, candidate `bun.lock` SHA-256, and Bun version. Live edits to either invocation source or invocation dependencies after isolation therefore cannot affect proof execution. The runner records the actual candidate commit, source-tree cleanliness, committed-tree hash, and index hash at detached execution start, immediately before and after every child, and at completion; the candidate defaults to the invocation `HEAD`, while `--candidate-commit` lets an attended run pin the intended full SHA explicitly. Dirty invocation evidence, unavailable or changed detached source, cleanup failure, or candidate mismatch is a machine-readable no-go even when every command passes. Worktree setup and removal, dependency installation, and filesystem cleanup are bounded, and cleanup failure is retained in the final verdict. Every child has an absolute command deadline and runs in an owned process group that receives TERM and then KILL if it does not exit. It runs exact full-fixture SQL at 1×, 2×, and 4×, then the actual dominant-regression inventory, operation-registry classification, rollback cutovers, mixed-load, admission schema/enforced/shadow, operation-receipt schema/ambiguity/restart, public-projection convergence, device derivation/mirror/scaled convergence/resource, and Sonar Rust/scaled delta-to-full-local-rebuild suites. The fast Sonar/device/admission checks embedded in each SQL report remain honest source-shape models; the separately captured component processes are the release evidence that executes those implementations.

By default, artifacts land under the operating system's temporary directory at `fluncle-db-performance-release/<run timestamp>/`. The destination must be new and outside the invocation repository; no Git pathspec is built from it. `profiles/{1x,2x,4x}.json` are the complete validated schema-version-six reports, `logs/<command>.{stdout,stderr}.log` preserves every child process, and `release-manifest.json` is the root evidence envelope: it records detached execution mode, candidate-local dependency install method, installer version and candidate lock hash, source freshness, commands and their deadlines, portable execution-root label plus relative working directories, exact expected and database-censused cardinality, category coverage, duration, exit status, portable relative artifact filenames, every child profile/log artifact's SHA-256 and byte size, the candidate commit in each profile envelope, warnings and thresholds, and the final `pass` or `no-go` verdict. Its `artifactRoot` is the SHA-256 of the candidate plus the complete sorted child-artifact descriptors; the manifest deliberately does not claim to hash itself. No absolute local source, dependency, scratch, or artifact directory enters the manifest. Pass `--output-dir <new-directory>` to choose another empty destination outside the repository. The runner exits nonzero for an in-repository artifact destination, dirty or mismatched invocation source, detached setup or cleanup failure, changed execution source, any failed or timed-out child, malformed profile report, inexact census, false `report.passed`, artifact-integrity drift, or missing/failed required category; a test command that has no JSON reporter is still represented by its exit status and duration with both logs retained while the top-level manifest remains JSON.

Each standalone SQL command writes one schema-version-six JSON document. `report.passed` is false for any required budget, correctness, resource, index-audit, census, or plan-law failure. It includes distributions, equivalence, queue convergence, mixed-client load, admission, ambiguity, projection, Sonar/device source-shape model checks, database process-boundary evidence, and process resource samples. `resources.availability` and `sampleSource` make missing measurements explicit; no missing sample is coerced to zero. Exact local reports name `process.memoryUsage.isolated-local-libsql-client`, `local-sidecar-process`, and `benchmark-client-process`; the release validator rejects embedded or adjusted evidence. At 4×, only the aggregate contract-phase `resources.peak.wallDurationMs` threshold becomes a warning curve. Projection contracts explicitly require 4×, so their p95 timing budget remains a hard failure there, as do correctness, invariants, plan violations, heap, and RSS limits. Inspect `criteria`, `durationMs`, `queueMs`, `resultRowCount`, plan `details`, `fullScans`, `tempSorts`, validation failures, `database`, `resources`, `indexAudit`, the fixture's `writeDurationMs`, post-write `census`, and `exactProfileCardinality` before comparing runs. Exact local fixture construction and census are reported but deliberately outside contract-phase wall and Worker-memory budgets; the sidecar owns its database resident pages while the measured client retains the same hard Worker/application thresholds.

The device resource proof is separate from the SQL report: `bun run --cwd apps/web scripts/db-performance/device-resources.ts --profile <1x|2x>` creates a fresh local source child per profile, validates manifest-derived source counts and observed minimum/maximum 4,096-byte embeddings, binds the report to the initial source-file fingerprint, and emits the OS RSS high-water alongside explicitly sampled heap/RSS, real pre-checkpoint and post-checkpoint replica WAL, target-stage disk, semantic candidate/last-verified generation overlap, separately labeled aggregate temporary disk, and incremental, full-rebuild, corrupt-replica, and interrupted-stage recovery measurements. Aggregate disk samples the complete physical directory awaited before rename while the populated derivation `.tmp`, target files and sidecars, and prior generation coexist; the two semantic generation labels intentionally exclude the temporary artifact. Each phase records its own start/completion before later work and directly checks target row-count/watermark parity after incremental refresh, full rebuild, and both recovery paths. The source replica is a local file-copy seam that executes the production sync/checkpoint wrapper, and the target is local Bun SQLite; the proof claims neither network replication nor hosted-libSQL behavior or timing. Each window carries its own sample count and is compared with the 3,430-second service deadline; the deadline is not a claim about any individual refresh or recovery window. `--ci` selects the explicitly inexact ratio-preserving fixture used by the bounded component test. A raw attended report from a dirty source tree is diagnostic only: the release validator accepts exact evidence only when its clean revision and candidate commit bind together.

The artifact write-transaction measurement is likewise separate from the SQL report: `bun run --cwd apps/web scripts/db-performance/artifact-transactions.ts --profile <1x|2x|4x>` seeds a fresh production-schema local libSQL file to the profile's exact manifest table counts, including real track-artist edges and findings attached across its 4,096-byte embedded-track population, plus the manifest's proportional artifact-log volume below the consumer's registration fence. Its census refuses to report unless every requested table count matches, and it asserts that measured snapshot pages exercise both matched and unmatched sides of the findings join. The pending-frontier, enabled-label-track, YouTube-provenance, MusicBrainz-ISRC, and full-analysis distributions stay unmodelled because neither measured transaction observes their fields. The harness then drives the real `checkpointArtifactRebuild` transaction across every `sonar.track` snapshot page and the real `acknowledgeArtifactChanges` transaction across maximum-size change pages (`--acknowledgements <n>`, default 7). Each sample records what the write transaction did while it held the lock: statements, base64 calls with vector-length calls counted separately, `JSON.parse` calls, SHA-256 calls, and wall time from `client.transaction("write")` through commit; `--markdown` prints the two-row summary table and the default JSON keeps every raw sample. The statement and encoder counts are the durable claim and are pinned by `artifact-changes.transaction-work.integration.test.ts`; local wall time is not a hosted claim. `--ci` selects the compact derivative used by the bounded test in `artifact-transactions.test.ts`.

## Add a contract

Register a stable lowercase ID in [`contracts.ts`](../apps/web/scripts/db-performance/contracts.ts), choose the matching work class, set deterministic warm-up and measured iteration counts, and provide either a SQL statement through `sqlContract` or one custom observation callback. A SQL contract adds its `EXPLAIN QUERY PLAN` statement and names growing tables, forbidden temporary sorting, required driver/index details, and any narrowly allowed scan. Its correctness hook asserts ordered values or a stable digest where needed and always asserts result cardinality. Add a focused test that demonstrates the intended result and that the old or malformed plan fails.

If the contract needs new fixture state, extend the one manifest/generator rather than adding a bespoke seed script. Preserve stable synthetic identifiers, exact distributions, chunking, and the 1×/2×/4× multiplication law. Do not add a production index, rewrite product SQL, or copy a row from any live database as part of a harness change.

## Operator-gated hosted replay

Hosted replay is inert unless `--hosted`, `--operator-approved`, and `--preseeded-fixture` are all present. Invalid combinations fail before the runner reads `FLUNCLE_DB_PERF_SCRATCH_URL` or `FLUNCLE_DB_PERF_SCRATCH_TOKEN`. It rejects missing values, local/file URLs, embedded credentials, and targets whose identifiers look like production, development, local, or the live product. The hosted runner creates no database or infrastructure. Its bootstrap performs no fixture reset, schema creation, or data writes: it first verifies the imported fixture's format/profile/integration-base/counts/schema identity, then runs the exact post-import census as one read statement per request over deterministic windows of at most 50,000 fixture rows plus separate rowid underflow/overflow sentinels. Ordinary tables use rowid windows; the wide embedding table uses its covering `track_id` primary-key index so counting never traverses the 4,096-byte embedding payloads. Registered contracts execute only after those proofs and may mutate their harness-owned rows, which is why every profile requires a fresh disposable scratch database.

The manifest's exact 1×/2×/4× censuses make 93/127/206 bounded requests respectively. The hosted whole-process deadline adds a positive scale-matched bootstrap allowance for those round trips; it does not loosen the fixed 60-second deadline on any individual request or any contract budget.

Hosted replay treats only the aggregate registry `resources.peak.wallDurationMs` threshold as a warning curve at every scale because it accumulates remote round trips across the complete contract set rather than measuring one route or queue SLO. The 60-second per-request timeout, bounded absolute profile process deadline, correctness and plan checks, aggregate heap/RSS limits, and every per-contract SLO required for the selected profile remain hard failures; no contract budget changes in hosted mode. Exact-local 1×/2× release evidence keeps resource mode `required`; exact-local 4× keeps its existing bounded-memory/timing-warning mode.

Build the deterministic import artifact locally into a **new absolute directory outside the repository**. The materializer refuses overwrite, uses the existing schema and generator, proves the exact census and `quick_check`, writes identity only after those proofs pass, checkpoints and closes the file, rejects WAL/SHM residue, and emits a manifest containing the database SHA-256, byte size, and identity. `PERFORMANCE_FIXTURE_FORMAT_VERSION` must increase whenever generated row or distribution semantics change, even when schema, counts, and integration base remain unchanged.

```bash
bun run --cwd apps/web db:performance:materialize \
  --profile 1x \
  --output-dir /absolute/new/outside-repo/profile-1x
```

Repeat with a different new output directory for `2x` and `4x`. Each profile requires a fresh disposable hosted database; never reuse a larger profile's target for a smaller proof. The authenticated Turso database creation and file-import command, concrete database topology, credentials, and any paid infrastructure effect belong only in the private attended operator harness, not this public repository. The import step must use the materialized `fixture.sqlite3` unchanged. Neither the materializer nor hosted replay runs `ANALYZE` or `VACUUM`, preserving the audited hosted planner conditions.

```bash
FLUNCLE_DB_PERF_SCRATCH_URL='libsql://<scratch-database>' \
FLUNCLE_DB_PERF_SCRATCH_TOKEN='<scratch-token>' \
bun run --cwd apps/web db:performance --profile 1x --hosted --operator-approved \
  --preseeded-fixture
```

The presence of credentials alone does nothing on normal/local/CI paths, and approval alone is rejected. Never use a production or shared development URL, never run the gate unattended, and never treat local timings as a substitute when the hosted confirmation remains pending. The public command above is only the post-import verification/proof step; it does not authorize or describe the authenticated import itself.

The older per-item `apps/web/scripts/bench-db-scale.ts` proof engine also mutates its supplied database by applying migrations, seeding synthetic rows, and trial-dropping indexes. Before that script constructs a client, `SCRATCH_TURSO_DATABASE_IDENTITY` must exactly match the canonical host parsed from `SCRATCH_TURSO_DATABASE_URL`; a production/development/local denylist remains defense in depth rather than the authority. ```bash
