## The runtime path — `expo-sqlite`

`expo-sqlite` (SDK 56, `~56.0.5`) ships libSQL support natively — `useLibSQL` and `syncLibSQL()` are in the SDK-56-versioned docs and the module is in `expo@56.0.17`'s `bundledNativeModules.json` — which is why nothing else was needed for slices 0 and 1 and why slice 2 has a first-party path to try. libSQL itself is feature-frozen in direction but maintained (`tursodatabase/libsql`'s README: new features go to Turso, libSQL is actively maintained), which is the branch you want under a shipping app. Every alternative failed on a hard fact rather than on taste: `@libsql/client` has no `react-native` export condition and its Node build pulls an N-API addon Hermes cannot load, while `@libsql/client/web` is hrana-over-network only (throws `URL_SCHEME_NOT_SUPPORTED` for `file:`), so no local DB and no offline; op-sqlite makes libSQL a BUILD-TIME flag that costs reactive queries, multi-statement strings, update/commit/rollback hooks, extension loading, local disk-encryption and custom tokenizers, with SQLCipher mutually exclusive — a one-way door, now ruled closed; and CR-SQLite (dead upstream), WatermelonDB (New-Arch/SDK-54+ issue open and unanswered), Legend-State (v3 beta 22 months, peers five SDK generations behind), Zero (peers a react the app is not on), Electric (read-path-for-Postgres only), PowerSync (Postgres/Mongo/MySQL sources only) and TanStack DB (RN adapters peer stale majors; `localStorageCollectionOptions` silently degrades to in-memory on RN; no durable offline mutation queue) are all out. Turso's own RN bindings remain undocumented in the `turso-docs` tree and `docs.turso.tech/sdk/react-native` 404s, so never infer an RN capability from a Turso docs page — read the RN binding's README for the version you are pinning.

## Turso sync mechanics (as of mid-2026)

- Conflict posture on `pull()` with unpushed local changes is a **rebase**: local rolls back to the last synced state, remote applies, local replays atomically on top. That is not a per-field merge, so the user-data union-merge law still needs app-level merge logic above it.
- **Sync is MANUAL in every Turso stack, by design, not as a limitation** (docs.turso.tech/sync/usage.md, read 2026-07-30): the new Turso Sync engine (`@tursodatabase/sync` — that page covers TS/Python/Go only, no RN) states that all reads and writes happen locally and the app controls when to sync with explicit `push()`/`pull()` calls, and expo-sqlite's surface is the same shape (`db.syncLibSQL()`, no auto-sync knob — its `libSQLOptions` is exactly `url`/`authToken`/`remoteOnly`, verified against the installed 56.0.5 types). For the shared read-only replica this is the wanted contract: pull on the app's schedule (foreground/timer), never inside the cold open.
- **Turso Sync's conflict rule is "last push wins"** (same page) — blunter than the rebase above, which strengthens keeping user-data merging at app level. Moot for slice 2 itself: devices never push the catalogue.
- `bootstrapIfEmpty` (start-offline: open without requiring initial remote connectivity), partial sync and checkpoints exist in the Turso Sync TS/Go/Python docs; NONE are exposed by expo-sqlite's `libSQLOptions` (verified 2026-07-30 against the installed types), and their availability in Turso's RN binding specifically is UNVERIFIED.

## The spike — CLOSED, with findings the docs did not carry

The gate cleared 2026-07-30 (see Ruled). What the spike established beyond the verdict, each item load-bearing for the slice-2 build: the real API is `libSQLOptions: { url, authToken, remoteOnly? }` on `openDatabaseAsync` plus `db.syncLibSQL()` as a METHOD on the handle — there is no `useLibSQL` open option and no top-level `syncLibSQL(db)`; `useLibSQL` is the config plugin's BUILD-TIME prop, and it is an ENGINE SWAP (the podspec excludes `SQLiteModule.swift` + bundled sqlite3 when set, so the whole app's SQLite, kv-store included, rides libSQL in that build) — Expo Go can never carry it and a dev client built without the prop opens a plain local file. The flag is gated behind `SPIKE_LIBSQL=1` in `app.config.js` (the `development` EAS profile pins it; production stays on the default engine until slice 2 rules otherwise). Build trap: flipping the flag rewrites `Podfile.properties.json`, which does NOT dirty the Podfile checksum, so `expo run:ios` skips pod install and silently rebuilds the OLD engine — force `pod install` in `ios/` after any flip. libSQL-mode limits for the slice-2 design: NO named parameter binding (positional `?` only) and NO `enableChangeListener`.

## Slice 2 — the synced replica

The libSQL engine + `db.syncLibSQL()` against **one shared public-catalogue replica** (server-authoritative, read-only on devices — ruled 2026-07-30), with user data union-merged at app level on top of the rebase posture above. The one remaining gate before the slice is built: **the sizing pass** — fix what actually ships to a device (**the MuQ embedding blobs never leave the server**), measure the on-device file size and first-bootstrap duration at real catalogue scale, and keep the bootstrap out of the cold open. The build must also decide when the production binary flips to the libSQL engine (today only spike/dev builds carry it) and design within the two libSQL-mode limits above.

The repo half of the device-replica mirror now exists: the hourly `fluncle-device-mirror` sweep reuses the derivation whitelist and anchored-cut SQL, full-diffs source and target rows, mutates the existing target schema with batched upserts and deletes, refuses schema-version drift, and emits its measured drift to the run ledger; operator-gated work remains creating the production derived database, provisioning the read-only source and write-scoped target URL/token environment variables on the box, rebuilding the image, and activating the timer.
