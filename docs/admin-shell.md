# The admin shell

The contract for every `/admin` surface. The workspace chrome splits across two levels so it stays mounted as the operator moves between stations. The **persistent shell** — the sidebar (`admin-sidebar.tsx`, the only navigation surface, with its live count query) and the full-viewport content plate (the translucent glass pane over the cosmos) — is mounted **once** in the `/admin` layout route (`apps/web/src/routes/admin/route.tsx`), wrapping the `Outlet`. It never re-mounts on navigation, so the sidebar's count badges never blink out and refetch and the plate's backdrop-blur never re-composites (no background flash). Each guarded page renders only its **header + body** through `AdminShell` (`apps/web/src/components/admin/admin-shell.tsx`) — the fixed header grammar (sidebar trigger, title + optional subtitle, the `headerActions` slot) plus an optional `subheader` and the page body. Login stays a bare centered card outside the shell (the layout bypasses it by path). The layout also owns the two cross-page structural bits the page can't set on a shared frame: it lights the active sidebar entry from the URL (`navKeyForPath`), and it switches the one viewport-height, self-scrolling station (the Studio) into fill mode by path.

## The persona law

**The web admin is the operator's platform · `fluncle admin` is the agents' tool · `fluncle` is the crew's toy.** One persona per surface, and the persona decides where an operation's primary home lives: an operator workflow becomes a button on the web admin, an automation verb lands on the `admin`-tier CLI/API for the box sweeps and agents, and the public `fluncle` CLI stays the crew's. The operator's enemy is tooling fragmentation, so machine-bound jobs centralize into the web admin — a headless poller behind the API does the machine's work; no machine needs a face (the live-show visuals stay the one local ritual). A job reachable from several surfaces still has exactly one primary home under this law; the others are conveniences.

## The placement contract

One home per kind of control. Put each control in its slot and nowhere else.

- **Page-level actions** go in the header slot, top-right (`headerActions`). One primary action per page keeps the One Sun budget (DESIGN.md).
- **Row actions** live inline on the row, right-aligned.
- **Bulk actions** live in a selection bar that appears with the selection and names its scope (`3 selected`).
- **Destructive actions** sit behind a confirm (`AlertDialog` from `@fluncle/ui`) that names the object it destroys.
- **A new page** gets exactly one sidebar entry, placed with its object group in `admin-sidebar.tsx`, and its route registered in `navKeyForPath` so the persistent sidebar lights the right entry from the URL (a page with no entry of its own — the Studio — maps to its parent object's entry).
- **Filters and view state** live in the `subheader` strip and deep-link through search params, so every view survives reload and pasteable URLs stay the operator's bookmarks.
- **Per-operator display preferences** live behind the sidebar's Display settings cog.

**The disclosure law — one primary per object, everything rare hidden by default.** When the operator lands on a page, the one thing they came to do is the loudest element and reads at a glance; nothing competes with it. Every infrequent or destructive action is demoted off the resting surface — behind a `⋮` menu (Phosphor `DotsThreeVertical`, `DropdownMenu` from `@fluncle/ui`), a hover card, an expand, or a dialog. Never surface two ways to do the same thing, and never let a control the operator uses once a week sit at the same weight as the one they use every visit. Progressive disclosure over density: show what's needed now, reveal the rest on intent. This is why the Renders row's cover IS the play button (no second Watch control) with Requeue/Purge in a `⋮`, why the Artists page collapses to summary rows with add/remove behind a dialog, and why a clip's TikTok and YouTube legs are separate one-action rows instead of one stuffed panel.

## The Object Row

Every index page — a page whose job is "see the objects, open one" (Renders, Mixtapes, Recordings, Playlists, Artists) — presents its objects through one shared primitive, `object-row.tsx` (`ObjectList` + `ObjectRow` + `ObjectLead` + `ObjectGlyph`), so a row reads and behaves the same wherever it lands: a bordered, divide-y list; each row a leading visual (a cover, or an `ObjectGlyph` fallback at the shared `size-11` footprint), an identity that grows, then a right-aligned zone for the object's quiet meta and its one primary action, with anything rare in a `⋮`. Track-shaped rows feed `FindingIdentity` as the lead (its `plate` cover doubles as the play button when the object has a clip); set-shaped rows use `ObjectLead`. An **editor** page (Playlists, Studio) is an accordion/builder by nature — its collapsed summary row still matches the Object Row look, but expanding reveals the editor, not a detail view. Do not reach for a card grid or a bespoke list; extend the primitive.

Per page, the primary goal decides the layout — what's loud, what's hidden:

## The nav model

The sidebar is a flat object nav: Dashboard, then the objects in pipeline order (Findings, Renders, Artists, Galaxies; the "Catalogue" group — Funnel, The Ear, Labels — the catalogue machine's own cockpit; the "Sets" group — Playlists, Mixtapes, Dream-weaver; the "Studio" group — Recordings, Clips; then the unlabelled publish pair — Newsletter and **Reach**), then an "Ops" group (Users, Costs, Usage & cost), then the System cluster pinned to the foot (**ChatDnB** — the admin-gated spike where Fluncle answers over his own archive tools — beside **Prompts** and `/status`). **Reach** (`/admin/reach`) sits beside Newsletter because it reads the other end of the same act: how each posted video is actually performing, day-over-day velocity and which creative axes land, read back off the social-metrics ledger. A read board — no count badge. The Ops group leads with **Users** (`/admin/users`), the account roster — the operator's read-only window on the gated rollout of the account-backed features (saved findings, saved sets, the Galaxy); it monitors the platform rather than moving a finding along, which is what puts it in Ops instead of the pipeline. Then the group pairs COST-02 and COST-01: **Costs** (`/admin/costs`) is the operator's private subscriptions ledger (recurring + one-off spend, entered by hand), and **Usage & cost** (`/admin/usage`) is COST-01's read on what the pipeline SPENDS per automation step and per finding, aggregated from the append-only `cost_events` ledger (docs/track-lifecycle.md). The two share only the operator's mental model, never data or a combined total: `/admin/usage` renders CASH (real incremental money — the headline) and SUBSIDIZED draw (fixed-plan usage — subscription LLM tokens + on-box compute) in SEPARATE columns, never summed, with unpriced rows counted rather than laundered to $0. No Ops entry carries a count badge — not Users, not Costs, not Usage & cost (a roster size and an aggregate are not cheap honest counts). Dashboard owns `/admin` — the attention queue: every action the system needs as a row, zero rows the success state, snooze/won't-do persisted client-side (one operator, one browser — a localStorage map, since a server column could not see this browser's working set). Its sources (each an `AttentionSource` in `lib/attention.ts`) span the pipeline: a fresh/bounced TikTok draft, a clip's TikTok/YouTube legs, a cue-less recording, a distributing mixtape, the empty IG drip, a **drafted-but-unsent newsletter edition**, an artist needing a link review, an **unruled label**, a **pending crew submission**, a **capture the verification gate flagged as suspect**, an **auto-note the echo gate held back**, an **observation script the same gate held back**, and a **suspected version mismatch** on a catalogue row’s Spotify anchor — fourteen sources in all. `AttentionSource` is an EXHAUSTIVE union mirrored in six places (the zod enum in `packages/contracts/src/orpc/admin-attention.ts`; the union + the priority order + the primary-action switch + the dispatch's phrase switch in `lib/attention.ts`; the dashboard's icon + label maps; the CLI's label map; the Raycast menu bar's meta map) — adding a source means all of them, or the build breaks. The newsletter row surfaces the Friday `fluncle-newsletter` sweep's persisted draft — it authored the edition and posted the send command to Discord, but `send_edition` is operator-tier, so the draft waits until the operator sends it; the row is anchored to when it was drafted and deep-links to `/admin/newsletter` where the review + Send control lives (the send authority stays on that page, never on the queue row, see [docs/agents/newsletter-agent.md](./agents/newsletter-agent.md)). The submission row deep-links to the exact candidate in the review tray (`/admin/findings?submission=<id>`) and carries the on-box `fluncle-triage` sweep's advisory verdict when it has one (the pre-chew read; approve/reject stays the operator's, see [docs/agents/triage-agent.md](./agents/triage-agent.md)). The **held-note** row is the auto-note's echo gate made visible: the gate refuses to STORE a note that echoes a sonic neighbour, but it no longer DESTROYS it — the line is kept with its reason and raised here, because a pipeline that throws work away without telling anyone cannot be supervised (nobody can tell a good rejection from a badly-tuned threshold once the evidence is gone). It deep-links to the finding's note dialog (`/admin/findings?note=<trackId>`), where the held note and the neighbour it echoed sit side by side with the lifted run marked in both, and the ruling lives — Keep it / Edit it / Bin it, operator-tier, since accepting publishes a line to `/log`. The gate's thresholds are operator-tunable at runtime through the `settings` KV (a flip, not a deploy) and render beside the score. See [docs/agents/note-agent.md](./agents/note-agent.md). The **held-observation** row is that gate's spoken twin, with the same shape and its own panel (`held-observation-panel.tsx` beside `held-note-panel.tsx`): a script the echo gate refused to store is kept with its reason and ruled on here, at the same low urgency — the finding is simply unvoiced, a state it can hold indefinitely while the sweep keeps trying a colder script. The **version-check** row is the same idea one layer down, on the catalogue's Spotify anchor: the anchor gate refuses a candidate whose version descriptor differs from the row's, which is right in general and permanently wrong for a row whose MusicBrainz metadata OMITS the version (a comp track billed plain at the remix's length). Those rows miss forever and retire under the retry cap, so the near-match is written onto the row instead of discarded and raised here — both titles side by side, the signed duration gap, and a link to the MusicBrainz recording so the metadata can be fixed at the source. It is the ONE queue row whose ruling is inline (there is no station: the decision is one tap on a candidate the server already holds) — **Use this match** writes the anchor, **Not a match** clears the note and leaves the row's retry lifecycle alone — both through the operator-tier `resolve_anchor_review` op, because a `spotify_uri` is the row's public identity and is permanent if wrong. Nothing auto-anchors. See [docs/catalogue-crawler.md](./catalogue-crawler.md). The **capture-suspect** row is the wrong-audio verification gate made visible: a capture whose fingerprint disagrees with the track's official reference opens on the catalogue workstation's quarantine lens (`/admin/catalogue?lens=quarantine`), where the operator auditions the bytes and rules — the row never flags inline, because accusing a public finding's audio is publish-class judgement and that authority never sits on a queue row. Labels owns `/admin/labels`, the record-label entity and the operator's CRAWL-SEED control: every label a finding has carried is a row, and its three-state ruling (`enabled`/`disabled`/`undecided`) says only whether the future catalogue crawler may seed from it — **crawl scope, never storage**: skipping a label removes it from the NEXT crawl's seeds and touches nothing already stored. A brand-new label enters `undecided` and surfaces as a queue row ("a new label to rule on"); ruling rides the operator-tier `update_label` op (an agent token 403s). See [docs/label-entity.md](./label-entity.md). Funnel owns `/admin/funnel`, the catalogue pipeline (crawl → anchor → capture → analyze/embed → rec-eligible → certified) on one page: proportional stage bars each linking to their operating surface, the spend-lever meters (capture budget, anchor bench, frontier pending), and the day-by-day growth + per-stage throughput charts off the `catalogue_snapshots` ledger; a read-only view, so it carries no count badge. The Ear owns `/admin/catalogue` — every track the archive knows and Fluncle never certified (a `tracks` row with no `findings` row), ranked by cosine similarity to its single NEAREST finding, with each row carrying the finding it matched as its WHY. It is a TELESCOPE, not a conveyor belt — a short, high-conviction list he wants to open — so it deliberately carries **no count badge** (the honest number is "how many are worth your time", and a `COUNT` cannot answer that; a telescope with a backlog badge is a conveyor belt). The lenses deep-link through `?lens=` — the telescope, the capture queue (the rows with no audio yet, which the ranking structurally cannot reach), the wrong-audio quarantine, and the dismissed restore pile — and the operator verdicts live on the rows: the cover is an inline 30s audition, **Log it** certifies the row in place (behind a confirm — certifying creates lore), **Not for me** dismisses it (restorable from the dismissed lens), and a wrong capture is flagged into the quarantine. Nothing on it is lit like a finding — no coordinate, no gold, no note — because those columns live on `findings` and a catalogue row has none. The ranking is PRECOMPUTED by the agent-tier `rank_catalogue` sweep (a request-time ranking would be a 10k × 60 cross join over 1024-d vectors, per page load), so the page does no vector math at all. See [docs/the-ear.md](./the-ear.md). Galaxies owns `/admin/galaxies`, the naming gate for the sonic map: the nightly on-box cluster sweep keeps the sound-derived galaxies assigned (the k-means fit itself is an operator act at the held k — [docs/agents/cluster-engine.md](./agents/cluster-engine.md)) and the Worker mints each new galaxy a permanent machine handle, and the operator names the unnamed ones here — after auditioning each galaxy's member covers through the shared `/api/preview` relay (the same preview singleton `/mix` uses) — via the operator-tier `update_galaxy` op (naming is publish-class, so an agent token 403s; a machine handle never renders publicly). The header carries the naming progress (n of N named) because the public `/galaxies` lens gates on a fully-named map; rename and request-a-split are the rare acts, off the resting surface behind the row's `⋮`. Findings owns `/admin/findings`, the pipeline board (the queue's deep-link target for the publish loop; the board's `?stage`/`?mix` deep-links survive — old `/admin?stage=…` links redirect). An entry whose station doesn't exist yet points at the best current home for that object and stays unlit there; it lights only on the page that declares it as owner. Count badges carry live, cheap, honest server counts (a scoped `COUNT` per number); a number that can only be estimated stays off the rail.

### Prompts (`/admin/prompts`)

**Prompts** owns `/admin/prompts` — the prompt registry, the station where the operator edits **what Fluncle tells the models**, with no deploy and no box rebake ([docs/agents/prompt-registry.md](./agents/prompt-registry.md)). Every prompt that authors a Fluncle artifact in production is a row: the finding note, the spoken observation, the Logbook entry, the triage verdict, the newsletter edition, the context distil, the search filter. Each row says where an edit LANDS ("Live on the next sweep, no rebake" for the on-box five; "Live on the next request" for the two the Worker runs) and whether the repo's baked default or an operator override is running.

A prompt IS code — a bad edit silently degrades every artifact it touches until a human notices — so this station's primary goal is not "edit" but **"see what changed and put it back."** Opening a prompt shows the `{{variables}}` it may reference, an editor with a **live diff against the running body**, and the full version history with a per-version diff. **Roll back** is one action behind an `AlertDialog` that names what it does; because the history is append-only a rollback MINTS a new version rather than rewinding, so nothing is lost and the rollback is itself undoable. Reset-to-the-repo-default is the rare act, demoted behind the row's `⋮` per the disclosure law. All three writes ride the single operator-tier `update_prompt` op. The station carries **no count badge** (there is no queue here — seven prompts, always).

## Metrics and charts

The read-only stations (Funnel, Usage & cost) render operational metrics, and two rules keep them actionable. **Aggregate, never enumerate:** a chart shows rolled-up shape — per-day, per-stage, per-step, p50/p95 — never one mark per run or per item, because per-run detail is noise the operator cannot act on (COST-01's processing-time view was rebuilt once for exactly this). **Prove the query returns rows against real prod data before building UI on it:** a metric read off a working-set column that clears on completion (`locked_at`, a `*_at` that nulls) renders as an empty chart, not an error, so a zero-row result is a query bug to fix, never a state to ship.

## Data loading

Every admin route uses the loader-seeded react-query hybrid from AGENTS.md — a `createServerFn` GET the route's `loader` calls, seeded into a `useQuery`/`useInfiniteQuery` as `initialData`, with `refetchOnWindowFocus: true` so an alt-tab back to a live board shows the current truth (exemplar `admin/labels.tsx`). **One documented deviation:** `admin/galaxies.tsx` sets `refetchOnWindowFocus: false` (plus a `staleTime` floor), because the galaxy map only changes on the nightly cluster sweep or an operator edit, and every edit already invalidates the query in its `onSuccess` — a focus refetch would re-run the k-vector scan on every alt-tab for byte-identical data. The reason is written at the call site; read it as the exception the rule allows, not a violation to fix. A new deviation earns the same treatment: justify it in code or inherit the default.

## Auth

**Two admin ROLES, three carriers** (`adminRole` in `env.ts` is the single source of truth both `requireAdmin` and `requireOperator` read from):

- **operator** — the human. Carried by the browser grant cookie OR the full `FLUNCLE_API_TOKEN` `Bearer` (the operator's own CLI). Can do everything.
- **agent** — the box sweeps and Hermes. Carried by `FLUNCLE_AGENT_TOKEN`, a SEPARATE `Bearer` value. Bounded to the reversible/internal surface: `requireAdmin` accepts it, `requireOperator` **403s** it on every publish-/irreversible-class route (it authenticated fine, it just lacks the role). That split is what makes the box gate non-load-bearing — a compromised box holds only the agent token, which the Worker refuses for publish actions.

The tier of every op is read off the composed oRPC router rather than a hand-kept list: `orpc-auth-coverage.test.ts` derives each op's tier from the middleware singletons on its chain and fails the build on any op that is not deliberately tiered — today 93 `adminAuth` ops (agent-allowed) and 70 `adminAuth` + `operatorGuard` ops (operator-only) beside the `/me` private-session and public tiers.

The browser proves identity with **Login with Spotify**, allow-listed to the operator through `ADMIN_ALLOWED_EMAILS` (+ optional `ADMIN_ALLOWED_SPOTIFY_IDS`) in `admin-auth.ts`; the login exchanges the code only to read the profile and discards the tokens — it never touches the publish refresh token in `spotify_auth`. On success it sets the grant cookie (`{ epoch, iat, role: "admin" }`, HMAC'd via `signAdminGrant` in `env.ts` — the key never reaches the client; `HttpOnly`, `Path=/`, 30-day window) and redirects to `/admin`. `ADMIN_SESSION_SECRET` is deliberately not `FLUNCLE_API_TOKEN`, so a leaked Bearer cannot forge session cookies. Login at `/admin/login`, sign out at `/api/admin/logout`; the gate is active in dev too (just without `Secure` on localhost).

`ADMIN_SESSION_SECRET` is a ROOT secret that signs nothing directly: `env.ts` derives one labeled subkey per purpose (`HMAC(root, "fluncle/admin-grant-cookie/v1")` for the grant, `HMAC(root, "fluncle/oauth-state/v1")` for OAuth state), so a credential minted for one purpose can never verify as the other even though one env var provisions both. Changing a label invalidates every credential signed under it.

**Revocation.** A signed grant is stateless, so the 30-day window used to be the only brake. The grant now bakes a **grant epoch** — one integer in the `settings` KV under `admin_grant_epoch` — and `verifyAdminGrant` refuses any grant whose epoch predates the current value. `fluncle admin auth revoke-grants` (the operator-tier `revoke_admin_grants` op, `POST /admin/auth/revoke-grants`) bumps it, signing every browser out at once with no deploy and no secret rotation; the Bearer carriers are not epoch-scoped, so the CLI still works when the browser session is precisely what is being cut. An unset key is epoch 0 (a fresh deploy behaves exactly as before); an epoch that cannot be read **fails closed**, because a revocation that fails open is not a revocation. The 30-day window stays as it is now that revocation exists — shortening it is a one-line operator choice, not a prerequisite.

**CSRF on admin mutations.** A state-changing admin request carried by the grant COOKIE must present an `Origin` (or, absent that, a `Referer`) matching the request's own origin — `requireAdminMutationOrigin` in `env.ts`, applied by the oRPC `adminAuth` middleware and by the two mutating file-route carve-outs (`POST /api/admin/chat`, `POST /api/admin/tracks/:id/preview`). The grant cookie's `SameSite=Lax` alone was not enough: Lax is site-scoped, so any `*.fluncle.com` host counts as same-site and carries the grant, and Chrome's Lax-allowing-unsafe intervention lets a top-level cross-site POST through for two minutes after the cookie is set. This is the cheap half of the `/me` stack, not the whole of it: admin still carries no per-session `x-fluncle-csrf` mutation token (`public-auth.ts`), deliberately — the admin identity is a single operator with no token-mint surface. A **Bearer** caller is exempt by carrier — the CLI, the agent box, and Raycast send no `Origin` and are unaffected.

**OAuth state binding.** Every auth start leg signs `{ bind, iat, nonce, purpose }` and sets a 10-minute HttpOnly `SameSite=Lax` cookie holding that nonce (`lib/server/oauth-state.ts`, one cookie per purpose so concurrent connects do not clobber each other). The callback refuses the token exchange unless the cookie matches, then clears it, so a state is single-use and useless in any other browser. `bind` has exactly one legal value, `"cookie"`, and the callback gate is **reject-unknown**: a missing, retired, or tampered binding is refused rather than waved through.

**The CLI handoff** (`lib/server/oauth-handoff.ts`) is what makes that "every" true. A Bearer-carried start used to receive the provider's authorize URL with a `bind: "none"` state — the operator opened it in a client that had never been handed a cookie, so the state was replayable for ten minutes by anyone who saw it. It no longer does: a Bearer start returns a **Fluncle-origin link** carrying a short-lived HMAC **ticket** (its own labeled subkey, `fluncle/oauth-handoff/v1`, so a ticket can never verify as a state or as a grant cookie; the ticket claims only a purpose and an issue time). `GET /api/v1/admin/oauth/handoff?token=…` demands the **grant cookie** — deliberately not `requireOperator`, since a Bearer caller is precisely the carrier that cannot hold the nonce — and then does what the board's connect button does: mint a bound state, set the nonce cookie, 302 to the provider. A leaked ticket mints nothing; it bounces to `/admin/login?handoff=…`, and the ticket rides through the login inside the signed state so the operator lands back on the connect. That return is a fixed path rebuilt from a ticket Fluncle signed, never a caller-supplied URL. The six platform connects share one purpose registry with the start routes; `admin-login` is deliberately not in it (logging in is what mints the cookie a handoff requires). The whole thing is a 302 file-route carve-out like its `auth/` siblings.

## The chrome gate

- Admin UI ships through the impeccable flow (`shape` → build → `audit`) and honors DESIGN.md, PRODUCT.md, and VOICE.md.
- Chrome is actions, data, and artwork. Every element is an action, a datum, or cover art.
- Components come from `@fluncle/ui` Shadcn exports. A missing component is added with `bunx --bun shadcn@latest add <component>` inside `packages/ui`, then aligned with the canon tokens.
- Interface icons come from Phosphor (regular idle, fill active); platform marks from `simple-icons` via `BrandIcon`.
- WCAG AA contrast, keyboard reach for every control, and reduced-motion fallbacks are part of done.

## Verifying

Browser-verification fixtures live in `apps/web/tests/browser/` (playwright-core driving the system Chrome). Every UI agent verifying `/admin` uses them:

- `admin.ts` — `loginAsAdmin(page, baseUrl)` mints the real admin grant through the production signing path (`signGrant` → the grant subkey derived from `ADMIN_SESSION_SECRET` in `apps/web/.dev.vars`, stamped with the current grant epoch read from the local DB) and sets the grant cookie; `launchBrowser()` + `newAdminPage()` wrap the launch/viewport/cookie boilerplate.
- `shell-smoke.ts` — clicks through every sidebar entry as the operator, past hydration (it proves interactivity by toggling the sidebar, retrying until a click sticks), at desktop and phone widths, screenshots each stop, and fails on any console or page error:

```bash
BASE_URL=http://127.0.0.1:3000 OUT_DIR=/tmp/shell-smoke bun tests/browser/shell-smoke.ts
```

- `queue-smoke.ts` — drives the `/admin` attention queue end-to-end (the j/k+Enter loop past hydration, a caption copy into the real clipboard, snooze, won't-do + Undo, [Show all], draining to the zero state, and the legacy `?stage`/`?mix` redirect to `/admin/findings`), desktop + phone, screenshots each stop. `SEED=1` self-seeds the local dev DB with rows for every queue source around the run (removed in a `finally`; it refuses a non-local database URL):

```bash
BASE_URL=http://127.0.0.1:3000 OUT_DIR=/tmp/queue-smoke SEED=1 bun tests/browser/queue-smoke.ts
```

- `admin-touch-smoke.ts` — pins the touch-comfortable-admin contract (DIST-02): on a coarse-pointer touch context (iPhone viewport, `hasTouch` + `isMobile`) every button-control on every admin surface is ≥44px and no surface bleeds horizontally, while on a fine-pointer mouse context the same controls stay their dense sub-44px selves — proving the 44px floor (`styles.css`, scoped to `.admin-workspace`) is touch-only and never bloats the desktop UI:

```bash
BASE_URL=http://127.0.0.1:3000 bun tests/browser/admin-touch-smoke.ts
```


- `admin-subscriptions-smoke.ts` — pins the Costs station CRUD (COST-02): drives the `/admin/costs` dialog end-to-end (add a throwaway line → edit its amount → delete it through the confirm), asserting each mutation reflects in the ledger. ```bash
