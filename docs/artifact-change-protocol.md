# Artifact change protocol

Fluncle exposes one versioned, bounded producer log for filesystemful consumers that rebuild derived artifacts without direct hosted-database access. The protocol is an application-owned outbox, not built-in CDC: a source writer appends its material revision in the same database transaction as the source mutation, and consumers bootstrap from deterministic source projections before they follow the global sequence.

The runtime and fail-closed registry live in [`apps/web/src/lib/server/artifact-changes.ts`](../apps/web/src/lib/server/artifact-changes.ts), the transport contract lives in [`packages/contracts/src/orpc/admin-artifacts.ts`](../packages/contracts/src/orpc/admin-artifacts.ts), the log/consumer tables and indexes come from migration [`0163_adorable_gladiator.sql`](../apps/web/drizzle/0163_adorable_gladiator.sql), and migration [`0165_lucky_earthquake.sql`](../apps/web/drizzle/0165_lucky_earthquake.sql) adds the compact producer-revision receipts that outlive event-body compaction. This protocol is the producer/runtime boundary for local-data consumers. The `sonar.track` source-writer coupling is live at the production embedding chokepoint; coupling the device streams and switching filesystemful consumers onto the log are separate integration phases.

## Registered contracts

A contract is the exact tuple `(stream, streamVersion, formatVersion)`. Version `1/1` is the only accepted tuple for every registered stream; an unknown stream or either unknown version fails at producer validation, consumer registration, snapshot reads, and acknowledgement. Adding a field, changing field semantics, or changing vector bytes requires a new registered format or stream version rather than a permissive decoder.

| Stream                | Subject                                  | Version | Upsert payload                                                                                                                                                                                              |
| --------------------- | ---------------------------------------- | ------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `sonar.track`         | `track` / `track_id`                     | `1/1`   | Canonical JSON with exactly `anchored`, `bpm`, `certified`, `dismissed`, `durationMs`, `hasFinding`, `isDuplicate`, `key`, and `nearestFindingScore`, plus the exact 4,096-byte `F32_BLOB(1024)` MuQ vector |
| `device.album`        | `album` / `albums.id`                    | `1/1`   | Every column in `DEVICE_DB_COLUMNS.albums`                                                                                                                                                                  |
| `device.artist`       | `artist` / `artists.id`                  | `1/1`   | Every column in `DEVICE_DB_COLUMNS.artists`                                                                                                                                                                 |
| `device.finding`      | `finding` / `findings.track_id`          | `1/1`   | Every column in `DEVICE_DB_COLUMNS.findings`                                                                                                                                                                |
| `device.label`        | `label` / `labels.id`                    | `1/1`   | Every column in `DEVICE_DB_COLUMNS.labels`                                                                                                                                                                  |
| `device.track`        | `track` / `tracks.track_id`              | `1/1`   | Every column in `DEVICE_DB_COLUMNS.tracks`                                                                                                                                                                  |
| `device.track-artist` | `track_artist` / `[track_id, artist_id]` | `1/1`   | Every column in `DEVICE_DB_COLUMNS.track_artists`                                                                                                                                                           |

[`DEVICE_DB_COLUMNS`](../apps/web/scripts/lib/device-db-schema.ts) remains the public-device security boundary and the exact device payload registry. A device upsert must carry every allowlisted column and no other column. A device delete carries only its primary-key fields; the composite `track_artists` subject ID is the canonical JSON array `[track_id,artist_id]`. Device snapshots use the existing anchored cut: every finding plus every catalogue track satisfying `REC_ELIGIBLE_WHERE`, then only the albums, artists, labels, findings, and artist edges reachable from those tracks. No embedding table or vector crosses a device stream.

The Sonar snapshot is the current engine projection: every track with a 4,096-byte embedding, with the same filter metadata the Rust loader reads. `bpm` and `nearestFindingScore` are rounded to f32 before JSON encoding so a rebuild and an incremental event share one representation. The vector is never parsed or rewritten: the database bytes become base64 on the wire and decode back to the exact original bytes.

## Producer rules

Every event is an immutable `upsert` or `delete` carrying `seq`, `stream`, `streamVersion`, `formatVersion`, `subjectType`, `subjectId`, `revision`, `producer`, `createdAt`, canonical `payloadJson`, optional `payloadBlobBase64`, and a payload digest. JSON object keys sort recursively, arrays retain order, non-finite numbers fail, and negative zero encodes as zero. A tombstone is explicit: `operation=delete`, no blob, and either `{}` for `sonar.track` or the exact device primary-key JSON. Visibility loss uses the same tombstone as physical source deletion, so an incremental consumer never has to infer absence.

The idempotence key is `(stream, stream_version, subject_type, subject_id, revision)`. A producer assigns a strictly increasing positive safe-integer revision per stream subject whenever the material projection changes. Retrying the same revision with the same operation, payload JSON, and blob returns the original sequence without consuming another sequence; reusing the revision for different immutable bytes or appending below the latest revision fails. `createdAt` and `producer` identify the original event and never mutate on retry. The revision ledger retains only the immutable content digest and original receipt metadata, not a second JSON/vector payload, so the same guarantee survives event compaction without defeating it.

The builders `buildSonarTrackArtifactChange`, `buildDeviceArtifactChange`, and `buildArtifactChangeInsertStatement` validate and construct low-level event-body statements for inspection and testing. A source writer must call `insertArtifactChangeInTransaction` so checked retry, revision enforcement, the event body, and its durable receipt all land inside the already-open source transaction; executing a builder alone omits the receipt. `insertArtifactChange` supplies the complete behavior when the append is the whole transaction. The source mutation and checked append must commit or roll back together; a successful source write without its event breaks the bootstrap-to-log guarantee.

The production `sonar.track` chokepoint is [`updateTrack`](../apps/web/src/lib/server/track-update.ts). An accepted embedding upsert or clear runs the existing ordered source statements inside one explicit libSQL `write` transaction: `tracks.has_embedding`, the `track_embeddings` satellite, the due-work and public-projection shadow maintenance, then `insertCurrentSonarTrackArtifactChangeInTransaction`. That helper re-reads the exact current Sonar source row by `tracks.track_id`, maps it through the same payload/blob semantics as the bootstrap snapshot, and emits a validated `1/1` upsert when the row carries a valid 4,096-byte vector or a delete tombstone otherwise. It allocates the next subject revision from the maximum across both live events and durable compacted receipts while the write transaction serializes producers. The transaction commits once after the receipt lands; any source, maintenance, snapshot, validation, event, or receipt failure rolls the whole unit back and closes it. A non-embedding `updateTrack` write preserves the existing write batch and emits no Sonar event.

## Digests and exact bytes

For a snapshot item, the payload digest is SHA-256 over the UTF-8 canonical JSON envelope `{formatVersion,operation,payloadJson,stream,streamVersion,subjectId,subjectType}`, followed by an unsigned big-endian 64-bit blob length and the raw blob bytes. For a change event, the envelope additionally includes `createdAt`, `producer`, `revision`, and `seq`. An empty running digest is the SHA-256 digest of zero bytes. A non-empty page or batch digest is SHA-256 over the previous digest bytes followed by each payload-digest byte string in sequence order; the source digest carries that chain across snapshot pages. These primitives let a consumer prove both the JSON representation and exact vector bytes without reparsing either.

## Bootstrap and lifecycle

Registration or re-registration declares one to seven exact contracts and creates a fresh `rebuilding` generation inside a write transaction. The transaction reads the monotonic log head from `sqlite_sequence` and stores it as `snapshotSeq`; re-registration discards every prior rebuild and incremental checkpoint. Each stream snapshot then walks its source by primary-key keyset with a hard page maximum of 200, stable ordering, `limit + 1` lookahead, and an opaque cursor. There is no offset scan or temporary sort.

After applying a snapshot page, the consumer posts the generation, page limit, page digest, running consumer digest, and running item count. The Worker re-runs that exact page inside a write transaction and advances the durable cursor only if the page digest and both running totals match. A crash before that commit returns the same page. A source mutation that changes the page between read and checkpoint rejects the checkpoint; the consumer lists and applies the page again. Inserts or mutations that fall outside an already-checkpointed key range remain safe because their source transaction emits an event above the registration fence.

A stream becomes rebuild-complete only on a terminal page whose source and consumer digests and counts match. Activation requires every declared stream to be complete, then installs `appliedThroughSeq=snapshotSeq`. The consumer reads all later events in global `seq` order, including events from undeclared streams, so its checkpoint advances over one common log. `supportedByConsumer` says whether to apply an event; `formatRegistered` lets the consumer reject database corruption or an unrecognized future tuple before it acknowledges anything. An event for a declared stream with a different contract blocks acknowledgement rather than being silently skipped.

Change reads use `seq > appliedThroughSeq order by seq limit ?`, with a hard maximum of 500 and `limit + 1` lookahead. The response includes the head, exact `fromSeq` and `throughSeq`, event count, canonical payloads, raw vector base64, per-event digests, and the ordered batch digest. Acknowledgement re-reads the exact next batch inside a write transaction and accepts only the current durable `fromSeq`, exact count, exact `throughSeq`, and exact digest. Regression, a checkpoint beyond the head, a skipped or unseen event, an unknown registered format, and version incompatibility all fail. A process death before acknowledgement simply redelivers the same immutable batch; repeating an already-committed acknowledgement fails as a regression.

Inactivation clears `snapshotSeq`, `appliedThroughSeq`, checkpoint time, and rebuild rows. It retains the declared contracts for introspection but contributes no compaction barrier, and the identity must register and bootstrap again before reuse. Status reports lifecycle timestamps, contracts, rebuild cursors/digests/counts, snapshot fence, durable incremental checkpoint, current and earliest retained sequence, head, and the current global compaction barrier.

## Bounded compaction

Compaction is operator-only and runs in one write transaction. Its safe barrier is the minimum `appliedThroughSeq` across active consumers and `snapshotSeq` across rebuilding consumers; inactive consumers do not participate. No active or rebuilding consumer means no safe barrier and no deletion. A rebuilding consumer at fence zero blocks the log, while one registered at fence `N` permits deletion at or below `N` because its source snapshot replaces that prefix and it will consume only `seq > N`.

One call selects at most 1,000 earliest rows at or below the barrier by the sequence primary key, deletes only that selected inclusive range with the barrier reasserted, compares every returned sequence with the selected set, and commits only on an exact match. Tombstones compact under the same rule as upserts. Durable revision receipts remain after their event bodies leave the log, so a producer retry still recovers the original sequence and an old revision still cannot resurrect a deleted subject. The result reports the barrier, exact deleted count, first and last deleted sequence, and `compacted`, `empty`, or `no_safe_barrier`; compaction never resets `sqlite_sequence`, so future events retain global monotonic order.

## Authenticated surfaces

The oRPC endpoints mount below `/api/v1`: `POST /admin/artifacts/consumers` registers, `GET /admin/artifacts/consumers/{consumerId}` reports status, `GET /admin/artifacts/snapshots` lists a source page, the rebuild checkpoint and activation endpoints advance bootstrap, `GET /admin/artifacts/changes` lists events, the consumer checkpoint acknowledges a batch, and the inactivation endpoint retires a consumer. These lifecycle and read operations use the existing agent-authenticated admin tier. `POST /admin/artifacts/changes/compact` additionally requires the operator tier.

The hidden CLI exposes the same protocol as `fluncle admin artifacts register|status|bootstrap|bootstrap-checkpoint|activate|list|checkpoint|inactivate|compact`. Consumers use `--json` for lossless payloads and digests. A contract flag uses `stream@streamVersion/formatVersion`, for example `--contract sonar.track@1/1`; the CLI rejects anything outside the same fail-closed registry before making a request.

## Verification

[`artifact-changes.integration.test.ts`](../apps/web/src/lib/server/artifact-changes.integration.test.ts) runs the protocol against a fully migrated libSQL database. It pins registry parity with the external contract, canonical payload validation, duplicate and conflicting retries, transaction rollback/retry, monotonic sequence and revision behavior, exact vector bytes, tombstones, deterministic device and Sonar snapshots, stale-page fencing, unknown versions, hard limits and query plans, snapshot-to-log race coverage, checkpoint rejection, process-death redelivery, lifecycle resets, and compaction barriers across active, rebuilding, inactive, and absent consumers. [`track-update-artifact.integration.test.ts`](../apps/web/src/lib/server/track-update-artifact.integration.test.ts) pins the production coupling: exact upserts, clear tombstones, revisions after event-body compaction, full rollback on append failure with retry from revision one, and no event for non-embedding writes. The oRPC naming/admin/auth inventory tests and [`admin-artifacts.test.ts`](../apps/cli/src/commands/admin-artifacts.test.ts) pin the reachable surface and every CLI request shape.
